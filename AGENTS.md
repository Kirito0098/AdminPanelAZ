# AdminPanelAZ — правила для агента

Веб-панель администрирования VPN-сервера AntiZapret: FastAPI (`backend/app/`), React + Vite SPA
(`frontend/`), Telegram-бот и Mini App, node/proxy-агенты, установка — `install.sh` + `scripts/`.
Архитектура — `docs/PROJECT_MAP.md`, пользовательские доки — `docs/README.md`.

Этот файл — выжимка для агента. Полные тексты правил (читать перед спорной задачей):

| Файл | О чём |
|---|---|
| `.cursor/rules/lean-code.mdc` | проверки только на границах доверия |
| `.cursor/rules/use-skills.mdc` | выбор skill'а, тесты только на критических узлах |
| `.cursor/rules/release-train-branching.mdc` | ветки `release/X.Y.Z` |
| `.cursor/rules/gitea-agent-sync.mdc` | что идёт в GitHub, что в личный Gitea |

Полный каталог скиллов с маршрутизацией — `~/.dsh/skills/skills-catalog/SKILL.md`.

## Проект лежит на сервере

Если в сессии есть инструменты `remote_ssh_*`, код живёт на удалённом сервере, а локальное
зеркало — пустышка без исходников. Адрес, пользователь и ключ берутся из локального профиля
Remote-SSH и в репозиторий не попадают. Тогда:

- читать/искать — `remote_ssh_cat`, `remote_ssh_grep`, `remote_ssh_glob`, `remote_ssh_ls`;
- править — `remote_ssh_write` / `remote_ssh_move` / `remote_ssh_delete`;
- запускать — `remote_ssh_exec` (ruff, pytest, npm, install.sh — всё на сервере).

Локальные `read`/`write`/`pwsh` видят только зеркало и к проекту отношения не имеют.
Если проект открыт локальным клоном — работай обычными файловыми инструментами.

## Мелочь ≠ фича

- **Мелочь** (1–2 файла без нового поведения: пункт меню, вкладки, подписи, вёрстка карточки,
  перестановка страницы, мелкий багфикс) — без `brainstorming`/`writing-plans`: план в чате
  2–5 пунктов → прогоны → коммит.
- **С процессом** (`brainstorming` → `writing-plans`, дождаться «да»): новый экран/поток, новая
  схема данных/эндпоинт, изменение поведения в нескольких модулях, новая фича.
- Задача выросла по ходу — вернуться к `brainstorming`, не раздувать план.
- План ≤5 шагов — максимум страница; полный код только для неочевидного (схема, миграция,
  правила доступа, парсинг). Вёрстку кодом не расписывать.

## Проверки — только на границах доверия

Данные проверяем один раз — там, где они входят в систему. Дальше доверяем типам и схемам.

- **Граница (проверять):** тело/параметры HTTP (Pydantic), ответы node/proxy agent, webhook
  Telegram, файлы и `.env` с диска, вывод внешних команд, права и auth.
- **Внутри (не проверять):** вызовы своих функций, атрибуты ORM, значения после Pydantic,
  типизированные пропсы и поля TS.
- `except Exception` — только на верхнем уровне фоновых циклов/обработчиков и в best-effort
  очистке; логируем, а не `pass`.
- Без «на всякий случай»: fallback для старых версий без потребителя, параметр с единственным
  значением, `try` вокруг кода, который не бросает.
- **Не трогать:** проверки на границах, обработку ошибок против потери данных, проверки прав.
  Существующий код массово не переписываем.

## Тесты — только на критических узлах

Пишем тест, только если ошибка кладёт сервер, открывает уязвимость или теряет данные:
auth/JWT/2FA/passkey/сессии/права/rate limit, публичная раздача конфигов, webhook Telegram,
nginx/firewall/systemd/install, бэкапы и миграции, node/proxy agent и синхронизация,
создание/блокировка/удаление VPN-клиентов, лимиты трафика.

- Вне списка (UI, тексты, вёрстка, формы, мелкие фичи) — новых тестов не писать:
  ruff / eslint / typecheck + прогон существующих + `webapp-testing`.
- Багфикс в критическом узле — ровно один регрессионный тест на баг.
- Существующие тесты не ломаем.

## UI проверяется браузером, не jsdom

Порталы, вложенные Radix-меню и `pointer-events` в jsdom не воспроизводятся: тест зелёный,
у пользователя не работает. Для UI-правок просить тестовый логин **до** правки
(`webapp-testing`, он же `playwright` MCP).

## Команды проверок

| Что | Команда | Время |
|---|---|---|
| Линт бэкенда | `backend/.venv/bin/ruff check backend/` | 1–2 с |
| Один тест-файл | `cd backend && .venv/bin/python -m pytest tests/<файл>` | 2–4 с |
| Срез без тяжёлых | `cd backend && .venv/bin/python -m pytest -m "not slow"` | ~48 с |
| Весь бэкенд | `cd backend && .venv/bin/python -m pytest` | ~75 с |
| Фронтенд | `cd frontend && npm run typecheck && npm run lint` | ~20 с |
| Сборка UI | `cd frontend && npm run build:all` | ~40 с |
| Проверка бандла | `cd frontend && npm run check:bundle` | ~3 с |

Один прогон на серию правок: полный `pytest` и `build:all` — по разу на этап, после последней
правки. Повторять уже зелёный прогон без новых изменений не нужно.

## Ветки (release train)

1. `main` — стабильная линия; фичи напрямую и PR «фича → main» не коммитим, пока релиз не готов.
2. `release/X.Y.Z` — здесь дорабатываем всё под релиз (актуальную ветку смотреть `git branch`).
3. Релиз готов → один PR `release/X.Y.Z` → `main`, затем тег `vX.Y.Z` и секция CHANGELOG
   вместо `[Unreleased]`.

- Перед правкой: `git branch --show-current`; целевая ветка — активный `release/X.Y.Z`.
  Если её нет — создать от `main` с номером из CHANGELOG; первым коммитом переключить
  `target-branch` в `.github/dependabot.yml` на неё.
- `feat/…` — только черновик; перед сдачей влить в текущий `release/…`.
- Тег версии — после merge в `main`, не вместо ветки `release/…`.

## Перед «готово»

Реальный прогон в чате **после последней правки**, по затронутой части, с показом вывода:

- мелочь (UI/один модуль) — ruff + точечный `pytest`/`vitest` + `npm run typecheck && npm run lint`;
- UI — плюс `npm run build:all` (иначе правка не видна в панели);
- полный набор (`pytest` всего, `check:bundle`) — перед коммитом релиза или когда правка
  задевает общий код.

«Комит и пуш» без правок с моей стороны (изменения уже лежат в дереве) — только `git add` /
`commit` / `push`, без прогонов. «Готово» без прогонов после правки — нельзя.

## Скиллы

Маршрутизация «ситуация → skill» — в скилле `skills-catalog` (читать перед задачей с процессом).
Коротко:

| Ситуация | Skill |
|---|---|
| Новая фича, экран, эндпоинт, изменение в нескольких модулях | `brainstorming` → `writing-plans` → дождаться «да» |
| Одобренный многошаговый план | `executing-plans` |
| Баг, красный тест, «не работает» | `systematic-debugging` |
| Багфикс с дешёвым тестом на критическом узле | `tdd` |
| Перед «готово», коммитом, PR | `verification-before-completion` |
| Свой новый код: «не переусложнено ли» | `ponytail-review` |
| UI, вёрстка, a11y | `web-design-guidelines` |
| Проверить UI в браузере | `webapp-testing` |
| React: ререндеры, бандл | `react-best-practices` |
| Атаковать свой дифф перед merge | `interrogate` |
| Что сломается за пределами диффа (nginx, install, agent) | `blast-radius` |
| Docs, README, CHANGELOG, PR-описание | `technical-writing` (+ `unslop`) |
| «Как работает X», «почему так» | `explain` |
| «Где я остановился» | `recall` |

- Глобальные скиллы — `~/.dsh/skills/` (DSH находит их без настройки).
- Проектные — `.cursor/skills/` (их же видит Cursor); если их нет в каталоге сессии,
  читать `SKILL.md` напрямую файловым инструментом.
- Security-пак (18 скиллов) в рабочем каталоге не подключён, чтобы не раздувать каталог:
  `~/.dsh/skills-extra/security/` — подключить копированием в `~/.dsh/skills/` на время аудита.

## MCP

Если в сессии есть инструменты `mcp__*`:

- `mcp__codebase_memory__*` — граф кода проекта (найти символ, связи, snippet) — сначала он,
  потом grep;
- `mcp__github__*` — issues/PR/releases репозитория `Kirito0098/AdminPanelAZ`;
- `mcp__context7__*` — актуальная документация библиотек;
- `mcp__playwright__*` — браузер для проверки UI;
- `mcp__siteaudit__*`, `mcp__lazyweb__*` — аудит сайта и референсы UI.

Серверы проекта запускаются на том же хосте, что и код (кроме context7/lazyweb — они внешние
HTTP), поэтому кодовая база для `codebase_memory` — серверная, а не локальное зеркало.
