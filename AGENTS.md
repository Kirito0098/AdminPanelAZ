# AdminPanelAZ — правила для агента

Веб-панель администрирования VPN-сервера AntiZapret: FastAPI (`backend/app/`), React + Vite SPA
(`frontend/`), Telegram-бот и Mini App, node/proxy-агенты, установка — `install.sh` + `scripts/`.
Архитектура — `docs/PROJECT_MAP.md`, пользовательские доки — `docs/README.md`.

Этот файл — выжимка для агента. Полные тексты правил (читать перед спорной задачей):

| Файл | О чём |
| --- | --- |
| `.cursor/rules/lean-code.mdc` | проверки только на границах доверия |
| `.cursor/rules/use-skills.mdc` | маршрутизация скиллов, режимы, запреты |
| `.cursor/rules/release-train-branching.mdc` | ветки `release/X.Y.Z` |

Скиллы — `.cursor/skills/`, маршрутизация — раздел «Скиллы» ниже.

Личная синхронизация с Gitea (адрес, pre-push хук, снимок агентских каталогов) — вне
репозитория: правило `.cursor/rules/gitea-agent-sync.mdc` лежит только на сервере.

## Проект лежит на сервере

Есть инструменты `remote_ssh_*` — код, ruff, pytest и npm живут на сервере: читать
`remote_ssh_cat` / `grep` / `glob` / `ls`, править `remote_ssh_write` / `move` / `delete`,
запускать `remote_ssh_exec`. Локальные `read`/`write`/`pwsh` видят пустое зеркало; при
локальном клоне — обычные файловые инструменты. Адрес и ключ — в профиле Remote-SSH.

## Мелочь ≠ фича

- **Мелочь** (1–2 файла без нового поведения: пункт меню, вкладки, подписи, вёрстка карточки,
  перестановка страницы, мелкий багфикс) — план в чате 2–5 пунктов → прогоны → коммит.
- **С процессом** (план в чате и «да» пользователя): новый экран/поток, новая
  схема данных/эндпоинт, изменение поведения в нескольких модулях, новая фича.
  Перед планом — скилл `brainstorming`: вопросы, 2–3 варианта, дизайн-док.
- Задача выросла по ходу — вернуться к плану в чате, не раздувать его.
- **Доработка — правка на месте.** Существующую кнопку, эндпоинт, обработчик или ветку
  переписываем, а не добавляем рядом вторую; заменённое удаляем в том же диффе, вызовы обновляем
  сразу. Второй путь данных допустим только для миграции/внешнего потребителя — и это названо
  в плане. Скилл — `surgical-edits`, после кода — `code-simplifier`.
- План ≤5 шагов — максимум страница; полный код только для неочевидного (схема, миграция,
  правила доступа, парсинг). Вёрстку кодом не расписывать.

## Проверки — только на границах доверия

Проверяем один раз там, где данные входят: Pydantic, ответы node/proxy agent, webhook Telegram,
файлы и `.env`, вывод внешних команд, права и auth. Внутри доверяем типам, ORM и схемам.
`except Exception` — только в фоновых циклах и best-effort очистке, с логом. Подробно и с
примерами — [`.cursor/rules/lean-code.mdc`](.cursor/rules/lean-code.mdc:1).

## Тесты — только на критических узлах

Пишем тест, только если ошибка кладёт сервер, открывает уязвимость или теряет данные:
auth/JWT/2FA/passkey/сессии/права/rate limit, публичная раздача конфигов, webhook Telegram,
nginx/firewall/systemd/install, бэкапы и миграции, node/proxy agent и синхронизация,
создание/блокировка/удаление VPN-клиентов, лимиты трафика.

- Вне списка (UI, тексты, вёрстка, формы, мелкие фичи) — новых тестов не писать:
  ruff / eslint / typecheck + прогон существующих + `webapp-testing`.
- Багфикс в критическом узле — ровно один регрессионный тест на баг.
- Существующие тесты не ломаем.

## UI проверяется браузером, не jsdom

Порталы, вложенные Radix-меню и `pointer-events` в jsdom не воспроизводятся: тест зелёный,
у пользователя не работает. Для UI-правок просить тестовый логин **до** правки
(`webapp-testing`, он же `playwright` MCP).

## Команды проверок

| Что | Команда | Время |
| --- | --- | --- |
| Линт бэкенда | `backend/.venv/bin/ruff check backend/` | 1–2 с |
| Один тест-файл | `cd backend && .venv/bin/python -m pytest tests/<файл>` | 2–4 с |
| Срез без тяжёлых | `cd backend && .venv/bin/python -m pytest -m "not slow"` | ~48 с |
| Весь бэкенд | `cd backend && .venv/bin/python -m pytest` | ~75 с |
| Фронтенд | `cd frontend && npm run typecheck && npm run lint` | ~20 с |
| Сборка UI | `cd frontend && npm run build:all` | ~40 с |
| Проверка бандла | `cd frontend && npm run check:bundle` | ~3 с |

## Ветки (release train)

Работаем в активном `release/X.Y.Z`, не в `main`; перед правкой — `git branch --show-current`.
Тег `vX.Y.Z` — только после merge релиза в `main`. Полный регламент, `feat/…` и dependabot —
[`.cursor/rules/release-train-branching.mdc`](.cursor/rules/release-train-branching.mdc:1).

## Перед «готово»

Реальный прогон в чате **после последней правки**, по затронутой части, с показом вывода:

- мелочь (UI/один модуль) — ruff + точечный `pytest`/`vitest` + `npm run typecheck && npm run lint`;
- UI — плюс `npm run build:all` (иначе правка не видна в панели);
- полный набор (`pytest` всего, `check:bundle`) — перед коммитом релиза или когда правка
  задевает общий код.

Один прогон на серию правок: полный `pytest` и `build:all` — по разу на этап, после последней
правки; повторять зелёный прогон без новых изменений не нужно.

«Комит и пуш» без правок с моей стороны (изменения уже лежат в дереве) — только `git add` /
`commit` / `push`, без прогонов. «Готово» без прогонов после правки — нельзя.

## Скиллы

Источник — `.cursor/skills/<name>/SKILL.md`. Zoo Code видит их через симлинки по режимам:

| Каталог Zoo | Когда активен | Что внутри |
| --- | --- | --- |
| `.agents/skills/` | любой режим | `karpathy-ponytail`, `cli-toolbox` |
| `.agents/skills-code/` | Code | `react-best-practices`, `vercel-composition-patterns`, `web-design-guidelines`, `webapp-testing`, `tdd`, `tui-design`, `surgical-edits`, `code-simplifier` |
| `.agents/skills-architect/` | Architect | `brainstorming`, `split-design-spec` |

Cursor режимов не знает: он видит весь `.cursor/skills`. Поэтому описания в frontmatter короткие
(одна триггерная строка) — каталог скиллов попадает в каждый запрос, тело скилла читается только
при вызове.

Маршрутизация «ситуация → скилл» — [`.cursor/rules/use-skills.mdc`](.cursor/rules/use-skills.mdc:1).
Процесс отдельными скиллами не описан: фича — план в чате и «да» (раздел «Мелочь ≠ фича»),
баг — сначала root cause, «готово» — прогоны из раздела «Перед «готово»».

Паки в `~/.agents/skill-packs/` в автопоиске отключены и в репозиторий не входят, читаются
вручную: security-пак (18 скиллов) — для точечного аудита поверхности, `systematic-debugging` —
для тяжёлых багов с воспроизводимым путём.

## Граф вместо повторного чтения

Кодовая база ~1 100 файлов — не перечитывать её заново каждую сессию:

- сначала `mcp__codebase_memory__*`: `search_graph` (символ), `trace_path` (кто вызывает),
  `get_code_snippet` (исходник), `get_architecture` (слои и точки связности);
- карта проекта и известный долг — [`docs/ADR-001-architecture.md`](docs/ADR-001-architecture.md);
- `rg`/`bat -r`/`read` — только если граф не ответил или файл вне индекса (`deploy/`,
  `frontend/nginx.conf`, частично `types.ts`, `pytest.ini`, SQL-фикстуры, YAML и доки);
- файл целиком не читать, если хватает `get_code_snippet` или диапазона строк;
- чем заменить `find`/`grep`/`cat`/`sed` — скилл `cli-toolbox`.

## MCP

Cursor берёт серверы из локального `.cursor/mcp.json` (шаблон — `.cursor/mcp.json.example`);
Zoo Code — из настроек MCP своего клиента. Настройки в репозиторий не попадают.
Зачем нужен каждый сервер и как проверить его из терминала — [`CONTRIBUTING.md`](CONTRIBUTING.md).

Если в сессии есть инструменты `mcp__*`:

- `mcp__codebase_memory__*` — граф кода (см. раздел выше);
- `mcp__github__*` — issues/PR/releases репозитория `Kirito0098/AdminPanelAZ` (только чтение);
- `mcp__context7__*` — актуальная документация библиотек;
- `mcp__playwright__*` — браузер для проверки UI.

`siteaudit` и `lazyweb` описаны в профиле, но по умолчанию не нужны: держать их выключенными и
включать только на время аудита сайта и подбора референсов UI — иначе висят в каждом запросе впустую.

Серверы проекта запускаются на том же хосте, что и код (кроме context7 — он внешний HTTP),
поэтому кодовая база для `codebase_memory` — серверная, а не локальное зеркало.
