# Защита входа (безопасность)

## Зачем этот раздел

Защита **самой панели** от посторонних: ограничение по IP, блокировка подозрительных подключений, активные сессии, смена секретных ключей.

## Кто может пользоваться

Только **администратор**.

## Как открыть

**Настройки** → **Защита входа**.

---

## Пошаговые сценарии

### Ограничить вход только с ваших IP

1. В блоке **Кто может открыть панель** включите **Разрешать вход только с указанных IP-адресов** (переключатель сохраняется сразу)
2. В поле **Разрешённые адреса** перечислите через запятую ваши IP или подсети (домашний, офисный, VPN админа), например `192.168.1.0/24, 203.0.113.10`
3. Нажмите **Сохранить**
4. Для разового входа с чужого адреса используйте блок **Временный доступ по IP**: выберите срок (1, 12 или 24 ч) и нажмите **Текущий IP** или **Указанный IP**

> Узнайте свой IP заранее (например, через сайт «мой IP»). Иначе можете **заблокировать себя**.

Если панель открывается без Nginx, можно дополнительно включить **Дополнительная блокировка на уровне сервера** — тогда порт панели закрывается firewall для всех адресов не из списка.

### Автоматически блокировать подозрительные подключения

1. В блоке **Защита от перебора и сканирования** включите **Автоматически блокировать подозрительные подключения**
2. Задайте **Неудачных попыток**, **Блокировка, сек** и **Окно, сек** и нажмите **Сохранить**
3. При включённом ограничении по IP можно включить **Блокировать «зависших» на странице отказа** и задать **Макс. время на странице блокировки, сек**

Бан срабатывает, когда адрес **не из списка разрешённых** слишком часто обращается к панели или слишком долго остаётся на странице «Доступ запрещён». Поэтому бан работает только при включённом ограничении по IP. После 5 банов адрес по умолчанию блокируется на год (в списке помечен «долгий»).

Публичные IP банятся ещё и в **firewall сервера** (ipset `aa_scanner_v4` / `aa_scanner_v6` и правило DROP): такой адрес не достучится до сервера вообще, включая SSH и VPN. Локальные и частные адреса, адреса из [`TRUSTED_PROXY_IPS`](#trusted_proxy_ips) и диапазоны Cloudflare в firewall не попадают — их блокирует только сама панель. Работает ли firewall, показывает проверка «Баны сканеров в firewall» в [diagnostika.md](diagnostika.md).

### Снять бан

1. Блок **Активные блокировки** — адреса, которые сейчас не могут подключиться к панели
2. Нажмите **Разблок.** у нужного адреса или **Снять все**

После **Разблок.** адрес по умолчанию 30 минут не банится повторно, а счётчик банов для него обнуляется.

### Посмотреть и завершить активные сессии

1. Блок **Активные web-сессии** — кто сейчас залогинен в панель: логин, IP, браузер, время последней активности (ваша сессия помечена «вы»)
2. При подозрении на взлом нажмите **Отозвать** и подтвердите

Сессия завершается на сервере сразу: её токены отзываются, и устройство разлогинивается при следующем же обращении к панели. Отзыв своей сессии (кнопка **Отозвать и выйти**) выводит из панели вас самих.

### Сменить секретные ключи (ротация)

1. В блоке **Ротация секретов** нажмите **Открыть мастер ротации**
2. Выберите секрет и нажмите **Далее**:
   - **SECRET_KEY (JWT)** — подпись сессий и шифрование секретов в БД (`backend/.env`);
   - **NODE_AGENT_API_KEY** — ключ локального node agent (`backend/node_agent.env`);
   - **Telegram bot token** — токен бота из @BotFather (хранится в БД панели)
3. Оставьте поле пустым, чтобы сгенерировать случайное значение, или вставьте своё (токен Telegram — только вставить) и нажмите **Предпросмотр**
4. Проверьте предупреждения, нажмите **К подтверждению**, введите `ROTATE` и нажмите **Записать**
5. Выполните шаги, которые покажет мастер

Что происходит после записи:

- **SECRET_KEY** — API-ключи и SSH-ключи узлов (с паролем ключа) и секреты 2FA перешифровываются новым ключом автоматически. Завершаются **все сессии всех пользователей**, включая вашу: refresh-токены и токены Telegram Mini App. Затем перезапустите панель: `sudo systemctl restart adminpanelaz` или [**Перезапуск и пересборка**](perezapusk-i-peresborka.md) → **Перезапустить панель**
- **NODE_AGENT_API_KEY** — перезапустите агент: `sudo systemctl restart adminpanelaz-node`
- **Telegram bot token** — зарегистрируйте webhook заново ([Telegram.md](../Telegram.md))

Автоматической отмены нет — только повторная ротация.

### После обновления: смените SECRET_KEY при прямой публикации

До 2.26.0 при прямой публикации (uvicorn слушает `0.0.0.0`, без Nginx) через специально составленный URL можно было скачать любой файл сервера, включая `backend/.env` с `SECRET_KEY` и базу данных. За Nginx такие запросы отклонялись.

Как понять, что это ваш случай: в `backend/.env` стоит `BACKEND_HOST=0.0.0.0` и `BEHIND_NGINX=false`, а в **Настройки** → **Адрес сайта и HTTPS** → **Текущий доступ** указан режим «HTTPS напрямую на uvicorn (без Nginx)» или «Прямой HTTP к приложению».

Что сделать после обновления: смените **SECRET_KEY** через мастер ротации (см. выше) и перезапустите панель. Все пользователи войдут заново.

## TRUSTED_PROXY_IPS

`TRUSTED_PROXY_IPS` — список прокси, которым панель доверяет заголовки с настоящим IP клиента. Задаётся в `backend/.env`, по умолчанию `127.0.0.1`.

**Как панель определяет IP клиента.** Если запрос пришёл с адреса из списка, панель берёт IP из `X-Forwarded-For` — самый правый адрес, которого нет в списке. Запрос с любого другого адреса считается пришедшим от самого клиента, а заголовок игнорируется. Для Telegram webhook заголовок `X-Real-IP` тоже учитывается только от доверенного прокси.

**Что зависит от этого IP:**

- ограничение по IP и временный доступ ([выше](#ограничить-вход-только-с-ваших-ip));
- баны сканеров и «зависших» на странице отказа;
- лимит попыток входа (по умолчанию 10 неудачных за 5 минут с одного IP, затем «Слишком много попыток входа. Повторите позже.») и капча после нескольких неудачных попыток;
- общий лимит запросов к API и лимит на публичные ссылки скачивания и клиентский портал;
- проверка, что webhook пришёл с адресов Telegram;
- IP в **Активные web-сессии**, журнале действий и уведомлениях о входе.

**Когда менять.** Стандартная установка с Nginx на том же сервере (в том числе с Cloudflare перед ним: реальный IP восстанавливает сам Nginx) и прямая публикация без прокси — ничего менять не нужно. Менять нужно, если перед панелью стоит **свой прокси, который подключается к панели не с `127.0.0.1`**: Nginx/HAProxy/Caddy на другом сервере, прокси в Docker-сети и т. п. Признаки: у всех сессий в **Активные web-сессии** один и тот же IP (адрес прокси), неудачные входы одного пользователя блокируют вход всем, ограничение по IP пускает всех или никого, Telegram webhook отклоняется.

**Как поменять:**

1. Добавьте адрес, с которого прокси подключается к панели, в `backend/.env`:

   ```bash
   TRUSTED_PROXY_IPS=127.0.0.1,10.0.0.5
   FORWARDED_ALLOW_IPS=127.0.0.1,10.0.0.5
   ```

   `FORWARDED_ALLOW_IPS` — такой же список для uvicorn (он по нему принимает `X-Forwarded-For` и `X-Forwarded-Proto`); держите оба списка одинаковыми.
2. Перезапустите панель: `sudo systemctl restart adminpanelaz`
3. Проверьте, что в **Активные web-сессии** у вашей сессии («вы») виден ваш настоящий внешний IP

> В `TRUSTED_PROXY_IPS` пишите **точные адреса через запятую** — подсети (`10.0.0.0/24`) панель не понимает. Не добавляйте адреса, с которых к панели напрямую подключаются обычные клиенты: подделав `X-Forwarded-For`, они обойдут ограничение по IP и лимиты.

> Повторная публикация (`nginx-setup.sh`, публикация из панели, `install.sh`), `nginx-repair.sh` и переключатели **Cloudflare proxy-mode** / **Доступ только через Cloudflare** (они запускают `nginx-repair.sh`) сбрасывают оба параметра к `127.0.0.1`. После них верните свои адреса.

Текущее значение видно в **Настройки** → **Адрес сайта и HTTPS** → **Текущий доступ** (в режиме за Nginx).

## Частые вопросы

**Включил ограничение по IP и не могу войти**  
Заходите с IP, который добавили в список. Если заблокировали себя — по SSH на сервере:

```bash
cd /opt/AdminPanelAZ
sudo ./scripts/disable-ip-whitelist.sh disable
```

Или добавьте свой текущий IP, не выключая ограничение:

```bash
sudo ./scripts/disable-ip-whitelist.sh add-ip ВАШ.IP.АДРЕС
```

Проверка: `sudo ./scripts/disable-ip-whitelist.sh status`.  
То же из меню: `sudo ./scripts/adminpanel-menu.sh` → **Диагностика** → **Отключить IP-whitelist (аварийно)**.

**Откуда берутся баны?**  
При включённом ограничении по IP панель банит адреса не из списка, которые много раз подряд стучатся в панель или долго сидят на странице отказа. Неудачные попытки входа не банят адрес, а включают лимит входа и капчу.

**Когда менять секреты?**  
При подозрении на утечку, после увольнения администратора, раз в несколько месяцев для профилактики. После обновления до 2.26.0 — обязательно для **SECRET_KEY** при прямой публикации.

## Будьте осторожны

- **Ограничение по IP** без запасного IP — риск потерять доступ к панели
- **Бан в firewall** закрывает адресу весь сервер, включая SSH — не проверяйте защиту со своего рабочего IP
- **Ротация SECRET_KEY** — все выйдут из системы, включая вас; запланируйте время и перезапустите панель
- **Ротация Telegram token** — бот перестанет работать, пока не обновите токен в BotFather и в панели
- **TRUSTED_PROXY_IPS** — добавляйте только свои прокси
