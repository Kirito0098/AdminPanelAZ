# Диагностика

## Зачем этот раздел

Проверка, что панель **запускается и открывается правильно**: служба, файлы, HTTPS, порт, Nginx и firewall — с подсказками, что исправить.

## Кто может пользоваться

Только **администратор**.

## Как открыть

**Настройки** → **Проверка работы**.

---

## Пошаговые сценарии

### Запустить диагностику

1. Нажмите **Запустить диагностику** (повторно — **Запустить снова**)
2. Дождитесь результата — несколько секунд
3. Шаги с ошибкой или предупреждением раскрываются: в каждой проверке есть подробности и блок **Что можно сделать**
4. Если есть ошибки, ниже появится блок **Рекомендуемые команды** — скопируйте команду и выполните её в SSH-терминале на сервере панели

Проверяются: служба systemd, файлы проекта (`.env`, база, venv, скрипты), HTTPS и домен, порт backend, доступность панели, Nginx (в том числе доступ к панели по IP сервера) и средства firewall (iptables и ipset). Полный отчёт — кнопка **JSON-отчёт**, скопировать его — **Копировать**.

> Диагностика проверяет сервер панели, не VPN-узлы и не клиентов на телефонах. Для узлов и WARP используйте разделы NOC.

То же по SSH: `sudo ./scripts/site-diagnostics.sh` или меню `sudo ./scripts/adminpanel-menu.sh` → **Диагностика** → **Диагностика запуска сайта**.

### Проверить баны сканеров в firewall

В шаге **Firewall tools** есть проверка **Баны сканеров в firewall**. Она появляется, когда iptables и ipset готовы к работе, и показывает, на месте ли наборы ipset и правила DROP, через которые панель банит сканеры на уровне сервера ([bezopasnost.md](bezopasnost.md#автоматически-блокировать-подозрительные-подключения)).

Если проверка с предупреждением — перезапустите панель (`sudo systemctl restart adminpanelaz`): наборы и правила создаются при старте.

### Закрыть доступ к панели по IP сервера

В шаге **Nginx reverse-proxy** есть проверка **Доступ к панели по IP сервера**. Она выполняется, только когда панель опубликована через Nginx, и показывает, стоит ли сервер по умолчанию `00-adminpanelaz-default-deny` ([set-i-publikaciya.md](set-i-publikaciya.md#доступ-по-ip-сервера-закрыт-nginx)):

| Результат | Что значит |
|-----------|------------|
| **Запросы по IP сервера отклоняются** (OK) | Сервер по умолчанию стоит и совпадает с портами панели и портала |
| **Запросы по IP сервера обрабатывает ваш сервер по умолчанию** (OK) | На портах панели уже есть свой `default_server` — панель его не заменяет |
| **Панель открывается по IP сервера** (Внимание) | Сервера по умолчанию нет: по голому IP открывается страница входа панели |
| **Сервер по умолчанию nginx устарел** (Внимание) | Файл есть, но не совпадает с текущими портами панели и портала |
| **Запросы по IP сервера отклоняются только по HTTP** (Внимание, без кнопки) | nginx старше 1.19.4, а сертификат-заглушку для HTTPS создать не удалось: HTTP по IP закрыт, HTTPS — нет. Обновите nginx или установите `openssl`, затем выполните `sudo ./scripts/nginx-default-deny.sh --apply` |
| **…: проверить не удалось** (Внимание, без кнопки) | Панель опубликована через Nginx, но скрипт проверки не отработал (nginx не найден, нет скрипта, тайм-аут) — причина в подробностях. Запустите `sudo ./scripts/nginx-default-deny.sh --check` по SSH |
| **…: панель по IP не отвечает**, **…: vhost панели в nginx не найден** (OK) | Закрывать нечего: по IP отвечает другой сайт или панель встроена в чужой сайт |
| **…: проверка пропущена** (OK) | Панель опубликована без Nginx. Ограничьте вход в **Защита входа** или firewall'ом |

Если проверка с предупреждением:

1. Нажмите **Закрыть доступ по IP** в этой проверке
2. Подтвердите: nginx будет отклонять запросы по IP сервера и к чужим именам (HTTP — соединение закрывается без ответа, HTTPS — отклоняется рукопожатие); домены панели и портала продолжают работать
3. Панель ставит только сервер по умолчанию, проверяет `nginx -t` и делает `systemctl reload nginx` — без перезапуска nginx, без перезаписи vhost панели и без изменений в `backend/.env` (`TRUSTED_PROXY_IPS` не сбрасывается). Если `nginx -t` не прошёл, изменения откатываются и показывается ошибка
4. Проверка обновится на месте — должна стать **Запросы по IP сервера отклоняются**

Пока идёт публикация панели, настройка или подготовка портала, кнопка отвечает «дождитесь завершения» — эти задачи сами переписывают nginx. Действие записывается в журнал действий. То же по SSH: `sudo ./scripts/nginx-default-deny.sh --check` (только проверка) и `sudo ./scripts/nginx-default-deny.sh --apply`.

После закрытия панель открывается только по своему домену (`DOMAIN` в `backend/.env`). Поэтому кнопка отказывает с объяснением, если:

- панель сейчас открыта по IP сервера или по другому имени — откройте её по домену (ссылка в сообщении) и нажмите кнопку там;
- панель открыта через ещё один reverse proxy перед nginx этого сервера (например, nginx на хосте перед виртуальной машиной с панелью). Такой прокси обычно подключается по IP без имени домена в TLS и после закрытия потеряет связь с панелью. Сначала добавьте в его блок с `proxy_pass` строки `proxy_ssl_server_name on;`, `proxy_ssl_name <домен панели>;` и `proxy_set_header Host <домен панели>;`, перезагрузите его nginx и закройте доступ по SSH: `sudo ./scripts/nginx-default-deny.sh --apply`.

### Вернуть доступ по IP

Если после закрытия панель перестала открываться (зашли по IP или через свой прокси без передачи домена), на сервере с панелью по SSH:

```bash
cd /opt/AdminPanelAZ
echo 'NGINX_DEFAULT_DENY=0' | sudo tee -a backend/.env
sudo ./scripts/nginx-default-deny.sh --apply
```

Скрипт уберёт сервер по умолчанию и перечитает nginx. С флагом `NGINX_DEFAULT_DENY=0` его не ставят и публикация панели, `nginx-repair.sh` и переключение режима Cloudflare, а проверка показывает «закрытие отключено». Чтобы снова закрыть доступ по IP, настройте свой прокси, как описано выше, удалите строку из `backend/.env` и ещё раз выполните `--apply`.

На 2.26.0 скрипт флаг не знает — там удалите файл вручную: `sudo rm -f /etc/nginx/sites-enabled/00-adminpanelaz-default-deny /etc/nginx/sites-available/00-adminpanelaz-default-deny && sudo nginx -t && sudo systemctl reload nginx` (публикация панели поставит его снова).

### Восстановить nginx после поломки StatusOpenVPN

Если удалили StatusOpenVPN и пропал доступ к панели (его `uninstall` часто ломает общий nginx), через браузер уже не зайти. Подключитесь по SSH:

```bash
cd /opt/AdminPanelAZ
sudo ./scripts/nginx-repair.sh
```

Либо из меню на сервере: `sudo ./scripts/adminpanel-menu.sh` → **Диагностика** → **Восстановить nginx для панели**.

Скрипт восстановит выделенный vhost панели по настройкам `backend/.env`. После этого снова откройте панель и при необходимости настройте публикацию. Если Status был подключён блоком `location /status/` в сайт панели (способ 2), скрипт этот блок уберёт — добавьте его снова. Совместная работа со Status на одном домене: [set-i-publikaciya.md](set-i-publikaciya.md#совместно-со-statusopenvpn-на-одном-домене).

## Частые вопросы

**Есть ошибки — панель сломана?**  
Не обязательно полностью. Раскройте шаг с ошибкой и прочитайте **Что можно сделать** — часто это одна настройка (например, домен или сертификат).

**Рекомендуемые команды — для кого?**  
Для администратора сервера с доступом по SSH. Обычным пользователям VPN не нужны.

**Чем отличается от страницы «Сервер»?**  
**Сервер** — нагрузка VPN-узла. **Проверка работы** — здоровье **самой панели** и её окружения.
