# Обновления панели

## Зачем этот раздел

Обновление AdminPanelAZ до **новой версии** с GitHub — новые функции и исправления ошибок.

## Кто может пользоваться

Только **администратор**.

## Как открыть

**Настройки** → **Обновление панели**.

---

## Откуда берётся новая версия

Панель обновляется с **upstream текущей ветки** git на сервере: обычно это `main` → `origin/main`, на ветке релиза — её upstream. Для `main` без upstream используется `origin/main`. Проверка и счётчик «отставание» считаются по той же ветке.

Обновление отказывается и ничего не меняет, если:

- рабочая копия не на ветке — «Рабочая копия не на ветке (detached HEAD): обновите вручную»;
- у ветки нет upstream — «У ветки … нет upstream: обновите вручную или привяжите её (`git branch -u origin/<ветка>`)»;
- история расходится с upstream, а в локальной ветке есть коммиты, которых нет на сервере git, — «В локальной ветке есть коммиты, которых нет на сервере git: … — синхронизируйте вручную».

Обновление идёт только ускоренным слиянием (`merge --ff-only`). Если история upstream переписана (force-push), рабочая копия чистая и все её коммиты уже есть на сервере git (в какой-либо ветке `origin` или были в upstream до переписывания), панель делает `git reset --hard` на upstream **той же** ветки. Неотправленные локальные коммиты так не стираются: обновление отказывается, как и при локальных изменениях в рабочей копии. Если отставания нет, а локальные коммиты есть, обновлять нечего — рабочая копия не меняется.

Блок с составом версии («Что нового в доступной версии» / «Состав последнего обновления») берётся из `CHANGELOG.md` ветки `origin/main`, даже если сервер обновляется с другой ветки.

## Пошаговые сценарии

### Обновить панель из интерфейса

1. **Сделайте бэкап** — [rezervnye-kopii.md](rezervnye-kopii.md)
2. Откройте **Обновление панели**. Если страница открыта давно, нажмите **Проверить снова**
3. Сверху видно «установлено», «на сервере» и «отставание»; при новой версии — статус **Доступно обновление**
4. В карточке **Установить обновление** нажмите **Применить обновление** и подтвердите в диалоге
5. Дождитесь завершения — прогресс в строке состояния вверху страницы, обычно до 15–20 минут. Панель выполняет шаги по порядку:
   - **Загрузка кода** — `git fetch` и обновление с upstream текущей ветки
   - **Зависимости** — `pip install` и `npm ci` (строго по `package-lock.json`)
   - **Сборка UI** — `npm run build:all`
   - **Перезапуск** — `adminpanelaz` через systemd, автоматически через несколько секунд
6. Проверьте, что панель открывается и основные функции работают

Во время сборки панель продолжает работать со старым интерфейсом, новый встаёт на место в конце сборки — подробнее в [perezapusk-i-peresborka.md](perezapusk-i-peresborka.md).

Если шаг не удался, следующие шаги и перезапуск не выполняются, в уведомлении — текст ошибки. Код к этому моменту может быть уже обновлён: исправьте причину и запустите обновление снова или соберите интерфейс через меню (`--update`, см. ниже).

### Обновить через SSH (меню)

```bash
sudo adminpanelaz --update
sudo adminpanelaz --restart
```

В интерактивном меню (`sudo adminpanelaz`; если команды ещё нет — `sudo ./scripts/adminpanel-menu.sh`) — **1 Обновить и перезапустить**. Если код обновился или интерфейс пересобран, меню спросит «Перезапустить панель сейчас? [Y/n]» и после перезапуска до 30 с ждёт ответа панели. Перезапуск отдельно — **4 Перезапустить панель**.

Что делает `--update`:

1. `git fetch origin` и сравнение с **upstream текущей ветки** — те же правила, что у обновления из панели: на ветке релиза — её upstream, для `main` без upstream — `origin/main`. Если рабочая копия не на ветке (detached HEAD) или у ветки нет upstream, меню отказывается с объяснением и ничего не меняет — обновите вручную или привяжите ветку: `git branch -u origin/<ветка>`
2. При отставании — fast-forward (`git merge --ff-only`) до этого upstream. Если история на GitHub переписана, локальных изменений нет и все локальные коммиты уже есть на сервере git, — `git reset --hard` на тот же upstream (никогда на `main`, если сервер на другой ветке). Если есть локальные изменения: «Обновление не удалось: … обновите вручную»; если есть неотправленные коммиты: «В локальной ветке есть коммиты, которых нет на сервере git: … — синхронизируйте вручную»
3. Дальше шаги выполняет уже обновлённый скрипт: `pip install -r backend/requirements.txt`, сборка интерфейса `npm ci` + `npm run build:all` (только если интерфейс на этом сервере уже собирали — есть `frontend/dist`), обновление systemd units
4. Панель **не** перезапускается — после `--update` выполните `--restart`

> **Меню 2.25.1 всегда тянет `origin main`**, независимо от текущей ветки. Это касается первого обновления с 2.25.1: его выполняет старое меню. На сервере с другой веткой (например, релизной) первое обновление сделайте вручную (`git pull --ff-only`), дальше меню 2.26.0 обновляет текущую ветку из её upstream.

Если новых коммитов нет, но какой-либо файл `frontend` из git новее собранного `frontend/dist/index.html`, `--update` пересоберёт интерфейс, а `--restart` предупредит, что интерфейс собран до последнего обновления кода.

Если сборка не удалась: «Код уже обновлён, интерфейс — нет». Повторный `--update` попробует собрать снова; вручную — `cd frontend && npm ci && npm run build:all`, затем `--restart`.

Если не удалась установка Python-зависимостей (`pip install`), обновление останавливается: интерфейс не собирается, systemd units не обновляются, панель перезапускать нельзя — новый код без зависимостей не запустится. Исправьте причину (текст ошибки pip выше), затем `backend/.venv/bin/pip install -r backend/requirements.txt && sudo ./scripts/adminpanel-menu.sh --after-pull` и `--restart`.

### Полное обновление (код + конфигурация сервера)

```bash
cd /opt/AdminPanelAZ
sudo ./install.sh --update       # план и вопрос «Продолжить? [y/N]»
sudo ./install.sh --update -y    # без вопроса
```

В меню `sudo adminpanelaz` — пункт **9 Полное обновление (код + конфигурация сервера)**; если на сервере панель и агент — **10**, в меню агента — **6**. Перед запуском меню спрашивает `[y/N]`.

Обычное обновление (кнопка в панели, `--update` меню) меняет код, Python-зависимости, интерфейс и unit'ы. Полное обновление вдобавок заново применяет конфигурацию сервера по текущим настройкам — нужно, если в новой версии изменились шаблоны nginx, правила firewall, список пакетов или unit DDNS. Мастер установки не запускается; роли сервера (панель, агент узла, proxy-агент) определяются по установленным unit'ам systemd. Вместе с `--reinstall`, `--uninstall`, `--purge-all`, `--node-only`, `--proxy-only` и `--with-node-agent` не используется.

Шаги по порядку:

1. **Бэкап** (только на сервере с панелью) — `backup-cli.py create --no-prune --keep-running`: старые архивы не удаляются, панель не останавливается.
2. **Код** — как `--update` меню: fast-forward из upstream текущей ветки. Если код обновился, остальные шаги выполняет уже новый `install.sh`.
3. **Пакеты** — доустанавливаются только недостающие пакеты apt установщика (`apt-get install --no-upgrade`); установленные не обновляются. Node.js не трогается.
4. **Python** — `pip install -r backend/requirements.txt`.
5. **Интерфейс** — `npm ci` и `npm run build:all` (только на сервере с панелью).
6. **systemd** — unit'ы всех установленных ролей из шаблонов (`scripts/refresh-systemd-units.sh`), `daemon-reload`.
7. **nginx** — только если панель опубликована через nginx и vhost панели свой (`/etc/nginx/sites-available/<домен>`, точки в имени заменены на `_`, например `panel_example_com`). Vhost панели и портала пересобираются по `.env`, пути сертификатов берутся из текущего vhost. Старый файл сохраняется рядом как `<имя>.bak-ГГГГММДД-ЧЧММСС`, путь печатается. Если `nginx -t` не проходит — старый файл возвращается, nginx не перезагружается. Панель в подпути чужого сайта — шаг пропускается (`sudo ./scripts/nginx-repair.sh`).
8. **firewall** — только если правила AdminPanelAZ уже есть (ufw или iptables): применяются заново по портам из `.env`. Выключенный ufw не включается. Если на сервере агент, а IP панели не записан в `node_agent.env` / `proxy_agent.env`, правила не меняются.
9. **DDNS** — только если есть `/etc/adminpanelaz/ddns.env`: unit и таймер из `systemd/`, `systemctl enable --now adminpanelaz-ddns.timer`.
10. **Перезапуск** — панель с ожиданием ответа до 30 с, агенты — проверка через 5 с.

Ошибка шагов 1, 2, 4 или 5 останавливает обновление до перезапуска — панель продолжает работать на прежнем коде. Ошибки остальных шагов попадают в итог, следующие шаги выполняются.

В конце — итог по шагам:

```text
Полное обновление
  Бэкап      ok        adminpanelaz_20261011-1230.tar.gz
  Код        ok        cef39ac → 1a2b3c4
  Пакеты     ok        доустановлено: 0
  Python     ok
  Интерфейс  ok
  systemd    ok        adminpanelaz, adminpanelaz-node
  nginx      ошибка    конфиг не обновлён, старый восстановлен (nginx -t: …)
  firewall   пропущен  не настроен
  DDNS       пропущен  не настроен
  Перезапуск ok        панель отвечает
```

Код выхода: 0 — все шаги `ok` или `пропущен`; 1 — обновление остановлено или хотя бы один шаг с `ошибка`; 2 — неверный аргумент или нет терминала для вопроса (запустите с `-y`). Если панель не ответила после перезапуска, под итогом — имя бэкапа шага 1 и подсказка: `sudo adminpanelaz` → **6 Бэкап и восстановление**.

Не меняются: база данных и настройки в ней, `backend/.env`, `node_agent.env`, `proxy_agent.env`, сертификаты (`/etc/letsencrypt`, SSL uvicorn) — они не перевыпускаются, PKI mTLS (`/etc/adminpanelaz/mtls`).

> Полное обновление появилось в 2.26.4. На сервере с более ранней версией `install.sh` такого флага ещё нет: сначала обычное обновление (`sudo adminpanelaz` → **1**), затем `sudo ./install.sh --update`.

## Обновление с 2.25.1 до 2.26.0

Что сделать администратору при переходе с 2.25.1 на 2.26.0 (node agent — `1.11.0`). Полный список изменений — в [CHANGELOG.md](../../CHANGELOG.md).

1. **Бэкап** — [rezervnye-kopii.md](rezervnye-kopii.md).
2. **Node.js 22+.** Проверьте `node -v`. Установщик теперь требует Node.js 22+ и ставит его из apt (если там 22+), иначе 24.x из NodeSource, но на уже установленной панели Node сам не обновится: повторите `sudo ./install.sh` или обновите Node через NodeSource.
3. **Обновите панель.**
   - **Из интерфейса** — как обычно (**Применить обновление**). Это обновление ещё выполняет код 2.25.1: он тянет `origin main` и ставит зависимости через `npm install`. Если после этого `git status` показывает изменённый `frontend/package-lock.json`, верните его (`git checkout -- frontend/package-lock.json`), иначе следующее обновление споткнётся о локальные изменения.
   - **Через меню** — старое меню 2.25.1 обновит только код (pip и units, без сборки интерфейса) и тянет `origin main`, на какой бы ветке ни был сервер. Выйдите из меню и выполните `sudo ./scripts/adminpanel-menu.sh --update` **ещё раз** — новое меню пересоберёт интерфейс. Затем `sudo ./scripts/adminpanel-menu.sh --restart`.
4. **Первый запуск.** Панель строит новые индексы БД: около 1 с для индекса лимитов трафика и ещё ~2 с и ~60 МБ для индекса трафика за период на 1,1 млн выборок. Не перезапускайте панель в это время.
5. **Node agent `1.11.0`.** На каждом удалённом VPN-узле нажмите **Обновить** в карточке узла — агент перезапустится сам через несколько секунд. Без нового агента на удалённых узлах не работают новые функции AZ-WARP, OpenVPN Buffer Guard и новые файлы редактора. Тестовые узлы, которые показывают `1.9.0` или `1.10.0`, обновите ещё раз. Подробнее — [uzly.md](../uzly.md).
6. **Ключи агентов.** Смените API-ключи:
   - VPN-узел — кнопкой **Ключ** в карточке узла ([uzly.md](../uzly.md));
   - прокси-узел — вручную: новый `PROXY_AGENT_API_KEY` в `backend/proxy_agent.env` на прокси-узле, `sudo systemctl restart adminpanelaz-proxy` и тот же ключ в карточке узла в панели ([proxy-agent.md](../proxy-agent.md)).
7. **`SECRET_KEY` при прямой публикации.** Если панель открывается без Nginx (`BACKEND_HOST=0.0.0.0` в `backend/.env`), смените `SECRET_KEY`: **Настройки** → **Защита входа** → **Открыть мастер ротации**. Все пользователи войдут заново, затем перезапустите панель — [bezopasnost.md](bezopasnost.md).
8. **Nginx.** Обновление из интерфейса nginx не перегенерирует, и панель за Nginx по-прежнему открывается по IP сервера.
   - **Из интерфейса.** После **Применить обновление** откройте **Настройки** → **Проверка работы** → **Запустить диагностику** и в проверке **Доступ к панели по IP сервера** нажмите **Закрыть доступ по IP** — [diagnostika.md](diagnostika.md#закрыть-доступ-к-панели-по-ip-сервера). Ставится только сервер по умолчанию nginx, nginx перечитывает конфигурацию без перезапуска; vhost панели, `backend/.env` и `TRUSTED_PROXY_IPS` не меняются. Панели, встроенной подпутём в чужой сайт, кнопка не вредит: там по IP отвечает ваш сайт, и проверка сообщит, что закрывать нечего.
   - **Полная перегенерация** (ещё и реальный IP клиентов за Cloudflare): **Настройки** → **Адрес сайта и HTTPS** → **Применить настройки**, либо `sudo ./scripts/nginx-repair.sh` или в меню **3. Диагностика** → **2. Восстановить nginx для панели** — [set-i-publikaciya.md](set-i-publikaciya.md). Эти способы записывают в `.env` `TRUSTED_PROXY_IPS=127.0.0.1` (шаг 10). Если панель встроена подпутём в чужой сайт на том же домене, `nginx-repair.sh` не запускайте — он заменит чужой vhost выделенным vhost панели; выполните шаг 9.
9. **Панель по подпути на домене с чужим сайтом, поставленная `install.sh`.** Опубликуйте панель с подпутём ещё раз — в разделе **Адрес сайта и HTTPS** или через `scripts/nginx-setup.sh`. Выделенный vhost панели на этом домене будет удалён, чужой сайт снова откроется — [set-i-publikaciya.md](set-i-publikaciya.md).
10. **`TRUSTED_PROXY_IPS`.** По умолчанию доверенный прокси — только `127.0.0.1`. Если перед панелью стоит прокси на другом адресе, добавьте его в `TRUSTED_PROXY_IPS` в `backend/.env` и перезапустите панель — [bezopasnost.md](bezopasnost.md#trusted_proxy_ips).

## Частые вопросы

**Обновление прервалось с ошибкой**  
Не паникуйте. Прочитайте текст ошибки в уведомлении и журнал (`journalctl -u adminpanelaz -n 50`). Интерфейс остаётся прежним, пока новая сборка не завершилась. При необходимости восстановите бэкап — бэкап перед обновлением обязателен.

**«Рабочая копия не на ветке» или «нет upstream»**  
Переключитесь на ветку (`git switch main`) или привяжите текущую к удалённой: `git branch -u origin/<ветка>`. Затем нажмите **Проверить снова**.

**Нужно ли обновлять VPN-сервер отдельно?**  
AntiZapret на VPN-узлах обновляется отдельно. Node agent на удалённых узлах — кнопкой **Обновить** в карточке узла; начиная с агента `1.11.0` он обновляется по тем же правилам ветки, что и панель.

**Как узнать, что версия новая?**  
После обновления смотрите [CHANGELOG.md](../../CHANGELOG.md) в репозитории.

## Будьте осторожны

- **Всегда делайте бэкап** перед обновлением
- Не обновляйте в часы пик — клиенты панели заметят краткий простой при перезапуске
- Не запускайте одновременно обновление и **Пересборку интерфейса** — вторая задача получит отказ «уже выполняется»
- На production-сервере лучше обновляться в спокойное время
