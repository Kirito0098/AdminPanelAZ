# Кодревью AdminPanelAZ (сентябрь 2026): что исправлено и что осталось

Ревью всего проекта провели шесть параллельных ревьюеров. Нашли 5 критичных проблем и около 60 важных. Исправления лежат в ветке `release/2.26.0` и задеплоены на рабочий сервер. Пользовательское описание каждого изменения есть в `CHANGELOG.md`, раздел `[Unreleased]`. Этот документ объясняет логику: как было, как стало и что ещё предстоит сделать.

**Состояние на 26.09.2026:**

- Критичные проблемы: закрыты все 5.
- Важные: закрыто около 30, открыто около 30, см. часть 2.
- Надёжность бэкенда (раздел 2.1) закрыта целиком. Мелкие остатки из повторных ревью перечислены в конце раздела 2.1.
- Что сделать на сервере после обновления — часть 3.

Каждое исправление сделано по одной схеме:

1. Сначала регрессионный тест, который падает на старом поведении.
2. Затем исправление.
3. Мутационная проверка: если откатить ключевую строку, тест снова падает.
4. Повторное ревью пачки исправлений.

---

## Часть 1. Исправлено

### 1.1. Критичные

#### Чтение любого файла сервера через раздачу фронтенда

- **Было.** Обработчик, который отдаёт файлы SPA, склеивал путь из URL с каталогом `frontend/dist` и не проверял, что результат остался внутри него. Запрос вида `/..%2f..%2fbackend%2f.env` без авторизации отдавал `.env` с `SECRET_KEY`, базу данных и любые другие файлы. Уязвимы были установки с прямой публикацией (uvicorn на `0.0.0.0`). Nginx такие пути отклонял сам.
- **Стало.** Путь приводится к каноническому виду, и файл отдаётся, только если он действительно лежит внутри `frontend/dist`. Всё остальное получает `index.html` (обычный клиентский маршрут). Путь с нулевым байтом раньше давал ошибку 500, теперь тоже `index.html`.
- **После обновления.** На установках с прямой публикацией нужно сменить `SECRET_KEY`: Настройки → Безопасность → ротация секретов.

#### Скачивание чужих VPN-профилей

- **Было.** У download, QR-кода и одноразовой ссылки есть параметр `path`. Роль «Пользователь» могла подставить туда путь к профилю другого клиента и получить его вместе с приватным ключом.
- **Стало.** Для не-администратора `path` должен входить в список файлов его собственного конфига, иначе `403`. У администратора поведение не менялось.

#### Сбор трафика в HA-группах

- **Было.** Состояние сессий трафика было уникально по ключу сессии (публичный ключ WireGuard) глобально. В HA-группе один клиент подключён и к primary, и к реплике, поэтому вторая запись нарушала уникальность. Транзакция после ошибки не откатывалась, и все следующие узлы в цикле падали каскадом. В итоге учёт трафика, лимиты и алерты тихо останавливались.
- **Стало.** Уникальность считается по паре «узел + ключ сессии» (миграция при старте). Ошибка БД на одном узле откатывает только его транзакцию и пишется в лог как warning, остальные узлы собираются нормально. Недоступный узел, как и раньше, логируется на уровне debug.

#### `SECRET_KEY` при переустановке

- **Было.** «Переустановка» и повторный запуск мастера с `--force` генерировали новый `SECRET_KEY`. Зашифрованные этим ключом данные в сохранённой БД становились нечитаемыми: API-ключи узлов, SSH-ключи транспорта, секреты 2FA.
- **Стало.** Прежний ключ сохраняется при сбросе `.env`.

#### Права на секретные файлы

- **Было.** `.env` и файлы БД создавались с правами `644`, то есть их мог прочитать любой локальный пользователь. Резервные копии `.env` при переустановке были такими же открытыми.
- **Стало.**
  - При каждом старте панель выставляет `600` на `.env`, `adminpanel.db`, `cidr.db` и их WAL/SHM-файлы.
  - Установщик сразу создаёт `.env` с правами `600`.
  - Каталог резервных копий переустановки получает `700`, файлы в нём `600`. Восстановление из него тоже ставит `600`.

#### Запуск после обновления с 2.25.1

- **Было.** Миграция погашений промокодов (`_migrate_unlock_redemptions_user_scope`) загружала узлы через ORM, а ORM выбирает все колонки модели `Node`. Колонку `nodes.api_key_rotated_at` общий блок миграций добавлял позже, поэтому на БД 2.25.1 запуск падал с `no such column`, и панель не стартовала. То же было после восстановления любого бэкапа до 2.26. Ещё две старые миграции (`vpn_configs` и политики доступа по узлам) тоже обращаются к `Node` через ORM раньше колонок `nodes`; на 2.25.1 они не срабатывают, но упали бы на БД постарше. Этот сервер не пострадал, потому что обновлялся промежуточными коммитами.
- **Стало.**
  - Все колонки `nodes` добавляются первым шагом миграций, до любых обращений к `Node` через ORM.
  - Тест поднимает БД по настоящей схеме чистой установки 2.25.1 (`tests/fixtures/schema_2_25_1.sql`, снята с кода `6dfda3f`) с узлами, пользователем и погашениями, запускает миграции как при старте и проверяет: миграции проходят, у каждой таблицы есть все колонки моделей (новая колонка без миграции тоже уронит тест), данные сохраняются, повторный запуск схему не меняет.
  - На копии рабочей БД миграции схему не меняют.

#### Промокод в портале менял сроки всем клиентам владельца

- **Было.** Если у клиента был владелец (обычно администратор), погашение промокода в портале клиента выставляло владельцу `access_until = max(сейчас, текущий срок) + N дней` и каскадом проставляло этот срок всем его клиентам. Бессрочные клиенты становились срочными, более долгие сроки сокращались, а в день окончания воркер блокировал всех. Погашение записывалось на владельца, поэтому второй клиент того же владельца многоразовый код уже не погашал («уже использован вами»). В портале пользователя каскад тоже выравнивал сроки всех клиентов по подписке, в том числе сокращая более долгие. Имя клиента сравнивалось через `LIKE`, и `_` или `%` в имени совпадали с другими клиентами.
- **На этом сервере.** 23.09 клиент `alina` погасил 30-дневный код 6. Погашение продлило подписку Claymore до `2027-01-08 20:22` и проставило этот срок всем его клиентам: 12 политикам OpenVPN, 3 WireGuard и 3 AWG2 (`updated_by = unlock_codes`). Прежний срок подписки (`2026-12-09`) дало разовое заполнение из раздела 2.7 п.4: это срок клиента `test1` после 90-дневного кода 10.09. Если ничего не менять, 08.01.2027 все клиенты Claymore будут заблокированы. Список клиентов со сроками до погашения по журналу — часть 3.
- **Стало.**
  - Портал клиента продлевает только этого клиента, как и клиента без владельца. Погашение записывается на клиента, поэтому другой клиент того же владельца может погасить тот же многоразовый код.
  - Портал пользователя передаёт пользователя явно. С подпиской она продлевается от `max(сейчас, текущий срок)`, а сроки клиентов только поднимаются до неё: бессрочные остаются бессрочными, более долгие не сокращаются. Без подписки продлеваются клиенты со сроком по протоколам кода. Если все профили бессрочные, погашение отклоняется («продлевать нечего»), и код не расходуется. Изменённые сроки реплицируются в HA-группы.
  - Имя клиента сравнивается точно, без учёта регистра (`lower(...) =`), в погашении и в проверке конфликта срока с владельцем.

#### Разовое заполнение подписки пользователей

- **Было.** При обновлении `users.access_until` заполнялся максимальным сроком среди профилей пользователя. Бессрочные профили не учитывались, уже истёкшие сроки учитывались. Подписка ограничивает все профили: когда она заканчивается, `apply_user_subscription_expiry` проставляет её срок профилям без срока и блокирует их. Поэтому пользователь с одним срочным и десятью бессрочными клиентами через какое-то время терял всех.
- **На этом сервере.** Так появилась подписка Claymore `2026-12-09 20:22`: это срок клиента `test1` после 90-дневного кода. Большинство клиентов Claymore, судя по журналу, были бессрочными. Затем погашение 23.09 (предыдущий подраздел) продлило эту подписку и проставило её срок всем клиентам. Что поправить вручную — часть 3, п.10.
- **Стало.**
  - Подписка заполняется, только если срок есть у каждого профиля пользователя (узел, клиент, протокол) и самый поздний из них ещё не наступил. Бессрочный профиль, в том числе бессрочный второй протокол срочного клиента, или одни истёкшие сроки оставляют пользователя без подписки.
  - Заполнение по-прежнему разовое (маркер в `app_settings`). Уже заполненные подписки исправление не трогает.

### 1.2. Безопасность доступа

#### WebSocket мониторинга сервера

- **Было.** Сокет принимал любой расшифровываемый JWT. Подходили промежуточный токен 2FA (выдаётся до ввода кода) и токен отключённого пользователя.
- **Стало.** Сокет принимает только access-токен активного администратора.

#### Область действия токена Telegram Mini App

- **Было.** Вход в Mini App по данным Telegram, без пароля и без 2FA, выдавал обычный токен панели. С ним были доступны все разделы: настройки, узлы, бэкапы, SSH-ключи.
- **Стало.**
  - У токена отдельный тип. Он принимается только в `/api/tg-mini` и в тех эндпоинтах панели, которые вызывает сама Mini App: конфиги, пользователи, шаблоны, client-access, unlock-ключи. Остальные разделы отвечают `401`.
  - Токен отзывается при отвязке или перепривязке Telegram.
  - Вход отклоняется для отключённого пользователя и для данных Telegram без ID.

#### IP клиента за прокси

- **Было.** Адрес клиента брался из самого левого элемента `X-Forwarded-For`. Этот элемент задаёт сам клиент, поэтому IP-ограничения и лимиты входа можно было обойти подделкой заголовка. От подделки защищали только флаги запуска uvicorn.
- **Стало.** Берётся самый правый недоверенный элемент (его дописывает nginx), доверенные прокси пропускаются. Тот же адрес использует подсказка гео-маршрутизации узлов.

#### Агент узла: доступ к файлам

- **Было.**
  - Эндпоинт скачивания бэкапа AntiZapret отдавал любой файл узла по абсолютному или относительному пути. Достаточно было знать API-ключ узла.
  - Чтение и запись профилей проверяли путь сравнением строк, поэтому проходили соседние файлы, например `antizapret/client.sh`.
- **Стало.**
  - Скачивание принимает только имя архива `backup*.tar.gz`, лежащего прямо в каталоге AntiZapret или в `/root`. Пути, `..` и symlink наружу отклоняются.
  - Профили должны лежать внутри каталога `client`. Записывать можно только `.ovpn` и `.conf`.
- **После обновления.** Перезапустить node agent на удалённых узлах.

#### Баны сканеров в firewall

- **Было.** Наборы `aa_scanner_v4` и `aa_scanner_v6` создавались без опции `timeout`, а бан добавлялся с `timeout N`. Ядро отвечало «Timeout cannot be used: set was created without timeout support», поэтому ни один бан не попадал в firewall: сканер блокировался только ответами панели. IPv6-набор подключался через `iptables`, который наборы IPv6 не принимает, и правила для него не было вовсе. `ipset create -exist` не может изменить опции существующего набора, так что повторный старт ничего не исправлял. Подтверждено на claymore-dev.com: оба набора без `timeout` и пустые, правила `ip6tables` нет.
- **Стало.**
  - Наборы создаются с `timeout 0` (у каждой записи свой срок). Старые наборы без поддержки timeout при старте панели заменяются через `ipset swap`: правило iptables остаётся подключённым. IPv6-набор подключается через `ip6tables`.
  - В firewall попадают только публичные адреса. Loopback, частные сети (в том числе адреса VPN-клиентов), link-local, доверенные прокси (`TRUSTED_PROXY_IPS`) и диапазоны Cloudflare из `cloudflare-realip.conf` по-прежнему блокируются только панелью. Раньше это не имело значения, потому что бан не срабатывал вовсе. С рабочим баном ошибочное определение IP клиента (например, `127.0.0.1` за nginx) отрезало бы панель целиком.
  - В диагностике сайта появилась проверка «Баны сканеров в firewall»: наборы, поддержка timeout и правила DROP для обоих семейств.

### 1.3. Telegram

#### Экранирование HTML в уведомлениях

- **Было.** Логин, User-Agent, имена клиентов, узлов и архивов, тексты ошибок вставлялись в HTML-сообщения администраторам как есть. Логин вида `<a href=…>` превращался в ссылку в уведомлении, а ошибка узла с символом `<` ломала отправку.
- **Стало.** Все значения, которые приходят от пользователя или извне, экранируются.

#### Проверка IP на вебхуке

- **Было.** Вебхук проверял, что запрос пришёл с IP Telegram, и доверял заголовку `X-Real-IP` от кого угодно. При прямом доступе к uvicorn проверку обходили подделкой заголовка.
- **Стало.** `X-Real-IP` учитывается только от доверенного прокси: адрес должен точно совпадать со значением из `TRUSTED_PROXY_IPS`.

#### Бот в группах

- **Было.** Бот отвечал на команды в группах и каналах, поэтому конфиги, QR-коды и ссылки уходили в общий чат.
- **Стало.** Интерактивный бот работает только в личных чатах.

#### Повторная доставка update

- **Было.** Если обработчик работал медленно или падал, Telegram присылал тот же update повторно. Команды «восстановить бэкап» или «перезагрузить сервер» могли выполниться дважды.
- **Стало.**
  - Каждый `update_id` обрабатывается не больше одного раза. Учёт ведётся в таблице БД, поэтому он общий для нескольких воркеров uvicorn.
  - Ошибка обработчика пишется в лог, а Telegram получает `200`, чтобы не присылать update повторно.
  - Записи старше 2 суток удаляет фоновая очистка вместе с остальными служебными таблицами, а не каждый запрос вебхука.
  - При восстановлении БД из бэкапа и при откате к копии перед восстановлением обработанные `update_id` переносятся из текущей базы в восстановленную. Иначе команда «Восстановить» из бота, на которую Telegram не получил ответа из-за перезапуска панели, после повторной доставки выполнялась бы второй раз. Если в архиве нет таблицы, она создаётся. Сбой переноса не отменяет восстановление и пишется в лог.

#### Бэкапы в боте по номеру в списке

- **Было.** Кнопки «Восстановить» и «Удалить» ссылались на номер архива в списке. Если между подтверждением и выполнением появлялся новый авто-бэкап, список сдвигался, и действие применялось к другому архиву.
- **Стало.** Кнопки ссылаются на хэш имени файла. Кнопки из старых сообщений отвечают «Архив не найден».

#### Видимость VPN-профилей при отправке файлов

- **Было.** Отправка конфига в чат (inline-режим, кнопка в боте, Mini App) не учитывала настройку «Видимость VPN-профилей». Скрытый вариант профиля уходил, если он был первым файлом или если его путь передавали явно.
- **Стало.** Отправка всегда фильтрует файлы по видимости отправителя. Явно указанный скрытый путь отклоняется, по умолчанию уходит первый видимый файл.

#### Напоминание «Доступ скоро истечёт» после истечения

- **Было.** Воркер напоминаний отбирал пользователей по «осталось не больше N дней», а для прошедшей даты `days_remaining_until` возвращает `0`. Дедупликация действует 24 часа, поэтому пользователь с истёкшим доступом каждый день получал «Доступ скоро истечёт, осталось 0 дн.», а администратор — «Доступ пользователя», если это событие включено. Так же каждый день приходило «Сертификат скоро истечёт» по истёкшему сертификату OpenVPN.
- **Стало.** Истёкший доступ и истёкший сертификат пропускаются: напоминание не отправляется и в журнал дедупликации не пишется. В последние сутки до истечения («осталось 0 дн.») напоминание по-прежнему уходит. На этом сервере истёкших пользователей нет, журнал напоминаний пуст.

### 1.4. HA и узлы

#### Снятие блокировок WireGuard на репликах

- **Было.** При синхронизации крипто-состояния с primary (создание или удаление клиента, лечение дрейфа, Push full) реплика применяла конфиги primary целиком. Peer'ы, удалённые из runtime ручной или временной блокировкой, возвращались, и заблокированный клиент снова получал доступ.
- **Стало.**
  - После синхронизации блокировки переприменяются на реплике по её политикам доступа.
  - Push full делает это после копирования политик, для WireGuard и AWG2.
  - Если Push full прервался после восстановления, блокировки WireGuard всё равно возвращаются.
  - Сбой блокировки одного клиента не останавливает остальных и не отменяет копирование профилей. Синхронизация при этом помечается как неуспешная, с именами клиентов.

#### Импорт PKI, профилей и восстановление реплики из архива

- **Было.** Импорт easyrsa3 на реплику (синхронизация крипто-состояния с primary) сначала удалял `/etc/openvpn/easyrsa3` и только потом открывал архив. Битый, обрезанный или не тот архив оставлял узел без PKI, а OpenVPN читает CA прямо оттуда (`ca ../easyrsa3/pki/ca.crt`) и после перезапуска не поднялся бы. HA-restore при Push full удалял PKI, конфиги WireGuard и профили клиентов до распаковки архива primary. Импорт профилей OpenVPN и WireGuard удалял каталоги профилей перед распаковкой: сбой посередине (например, кончилось место) оставлял часть профилей удалённой.
- **Стало.**
  - Архив сначала целиком распаковывается во временный каталог рядом с целевым (та же файловая система) и проверяется: каталог easyrsa3 на месте, в архиве профилей есть файлы нужного типа, в архиве primary есть easyrsa3. Повреждённый архив отклоняется (`400` для импорта, ошибка Push full для реплики), текущие файлы не трогаются.
  - Заменяемые пути переименовываются в скрытые копии рядом, новые файлы ставятся на их место. При любом сбое записанное удаляется и копии возвращаются, в том числе для путей, которых раньше не было. После успеха копии удаляются.
  - Посторонние элементы архива (не easyrsa3 и не нужные каталоги профилей), как и раньше, игнорируются, даже если у них опасные имена (`../`, абсолютные пути).
  - `config/` и `knot-resolver` при HA-restore по-прежнему перезаписываются поверх, без отката: они не удаляются заранее, и сбой не оставляет узел без них.
  - Тесты больше не могут изменить файлы хоста: `conftest.py` отклоняет запись, удаление, переименование и распаковку в `/etc` и `/root/antizapret`. Защита появилась после того, как тест на старом коде (жёстко заданный `/etc/openvpn`) перезаписал `ca.crt` и `index.txt` рабочей PKI. Файлы восстановлены из архива `client.sh 8` от 25.09 и сверены с CA в клиентских профилях и выданными сертификатами; остальная PKI совпадала с архивом, запросов на изменение клиентов за эти две минуты не было.

#### Группа зависала в `pending`

- **Было.** Статус `pending` ставился до запуска задачи настройки группы (общий домен → Push full → проверка) или применения общего домена. Если задача падала с исключением, итоговый статус не записывался. Хватало обычного отказа проверки связи («узел недоступен») или ошибки агента при создании бэкапа на primary. То же случалось, если панель перезапускали посреди задачи. Группа оставалась в `pending` навсегда: повторная настройка и применение домена отвечали `409` «синхронизация уже выполняется», автолечение такие группы пропускало.
- **Стало.**
  - Обе задачи при любом исключении откатывают незафиксированные изменения шага, переводят группу в `failed` с текстом ошибки и завершаются ошибкой как задача.
  - Группа в `pending`, у которой задача уже не в очереди и не выполняется (или задачи нет), переводится в `failed` с ошибкой задачи, например «прервана перезапуском панели». Это делается при старте панели сразу после пометки прерванных задач и в каждом проходе воркера сверки HA-групп.

#### Одна недоступная реплика обрывала репликацию

- **Было.** Почти во всех циклах по репликам адаптер узла создавался до обработки ошибок этой реплики. Для узлов с транспортом SSH при создании адаптера поднимается туннель, при отсутствии API-ключа сразу выдаётся ошибка. Если так падала одна реплика, падала вся операция: реплики после неё не получали изменение, итоговый статус группы не записывался. Это касалось создания, удаления и перевыпуска сертификата клиента, отключения OpenVPN, копирования ключей, политик доступа, настроек AntiZapret, списков провайдеров, Push full, проверки группы и применения общего домена (второй этап).
- **Стало.**
  - Адаптер создаётся внутри обработки ошибок каждой реплики. Сбой записывается по этой реплике, цикл продолжается, итоговый статус группы отражает частичный сбой (`failed` с ошибкой первой реплики, как и раньше при частичных ошибках).
  - Push full обнуляет адаптер в начале каждой реплики: после сбоя подключения блокировки не переприменяются через адаптер предыдущей реплики, а только через адаптер той реплики, на которой был сбой, если он успел создаться.
  - Проверка группы помечает недоступную реплику расхождением `node_status` с текстом ошибки (в интерфейсе «Узел недоступен») и сверяет остальные.
  - Лишнее создание адаптера при отключении OpenVPN на репликах убрано: адаптер создаётся внутри самого отключения.

#### Перезапуск OpenVPN на репликах при операциях с клиентами

- **Было.** После каждого создания, перевыпуска сертификата или удаления OpenVPN-клиента реплика получала PKI primary и перезапускала все активные `openvpn-server@*` (при multihome — через повторное применение multihome с перезапуском). У всех клиентов на реплике обрывались соединения, при массовых операциях — на каждого клиента. На primary `client.sh` серверы не перезапускает: при удалении он делает `revoke` и `gen-crl` и отключает только этого клиента через management-сокеты.
- **Стало.**
  - Перед импортом панель читает архив PKI реплики и сравнивает CA, сертификат и ключ сервера (`antizapret-server`) с архивом primary. Серверы загружают их только при старте, поэтому перезапуск (и multihome) выполняется, только если они изменились, отсутствуют или состояние реплики прочитать не удалось.
  - `crl-verify` OpenVPN перечитывает сам при каждом новом подключении (файл читается от `nobody`, права 755/644 приходят из архива primary, как и на primary после `client.sh`).
  - Клиенты, отозванные с прошлой синхронизации и не выпущенные заново, отключаются на всех четырёх серверах (`kill` через management). Агенты до этой версии не умеют отключать по серверу — тогда используется общее отключение клиента. Если отключить не удалось, синхронизация реплики помечается неуспешной: в конфигах `reneg-sec 0`, и без отключения сессия отозванного клиента не закрылась бы.
  - Push full, применение общего домена и изменения конфигов по-прежнему перезапускают серверы: там меняется конфигурация, а не только клиенты.

#### Пул SSH-туннелей

- **Было.** Пул выдавал сохранённый туннель, не проверяя, живо ли SSH-соединение. Keepalive был выключен, поэтому обрыв без трафика не замечался вовсе. Мёртвая сессия не истекала по простою: регулярные проверки состояния узла обновляли её время использования, и все запросы к узлу шли в закрытый локальный порт до перезапуска панели. Открытие туннеля выполнялось под общей блокировкой пула: пока панель до 30 с ждала недоступный узел, запросы ко всем остальным SSH-узлам, даже через уже открытые туннели, стояли. Закрытие сессий (при очистке по простою и `drop`) тоже шло под этой блокировкой с тем же таймаутом. У `asyncssh.connect` не было `connect_timeout`, а соединение, открытие которого прервали по таймауту, не закрывалось.
- **Стало.**
  - Перед выдачей туннель проверяется (`is_closed()`); мёртвый закрывается и открывается заново. Keepalive 15 с × 3 замечает обрыв примерно за 45 с.
  - Общая блокировка защищает только словарь сессий. Открытие туннеля держит блокировку своего узла: параллельные запросы к одному узлу открывают один туннель, другие узлы не ждут.
  - Фоновая очистка (раз в 30 с) закрывает простаивающие и мёртвые сессии; запрос к узлу чужие сессии не закрывает. Закрытие идёт вне общей блокировки и ограничено 5 с.
  - Подключение ограничено `connect_timeout` (30 с); при отмене по таймауту и при остановке пула во время открытия соединение закрывается.

#### Переприменение блокировок WireGuard и AmneziaWG

- **Было.** Вернуть блокировки после синхронизации реплики, после снятия блокировки с одного клиента или при сверке политик можно было только по одному клиенту. На каждого заблокированного уходил отдельный запрос к агенту (на реплике до 30 с каждый), агент заново разбирал все конфиги интерфейсов и вызывал `wg set`/`awg set` на каждый пир. При сотнях заблокированных это сотни запросов и тысячи команд.
- **Стало.**
  - Все заблокированные клиенты уходят одним вызовом: локально или через новый эндпоинт агента `POST /clients/wireguard/runtime/block-batch` (и `/clients/amneziawg2/...`). Агент один раз читает конфиги и удаляет пиры одной командой `set` на интерфейс, до 200 пиров в команде.
  - Если команда на интерфейсе не прошла, пиры этой пачки удаляются по одному, чтобы ошибка одного пира не оставила подключёнными остальных. Результат по каждому клиенту такой же, как раньше при поштучной блокировке.
  - Агенты до этой версии отвечают `404`, и панель переходит на поштучную блокировку. Если пакетный запрос упал по другой причине (таймаут, агент недоступен), ошибка записывается каждому клиенту, и синхронизация реплики помечается неуспешной, как раньше.

#### Отчёт об ошибке Push full

- **Было.** Шаг упавшей реплики попадал только в поле `failed_step` результата. Синхронизация AZ-AWG2, копирование политик доступа и возврат блокировок записывались как шаг перезапуска. В `last_sync_error` и в уведомлении было только «реплика: ошибка», а ошибка агента выглядела как `502: {'code': ..., 'message': ...}`. Окно результата список упавших реплик не читало: реплика, упавшая на восстановлении бэкапа, не появлялась ни в одной секции. Заголовок был «HA-группа настроена» или «Полная синхронизация завершена» даже при ошибке, а уведомление могло сообщить «синхронизирована и готова» по результату прошлой проверки. Если падал бэкап primary, интерфейс показывал общее «Ошибка синхронизации HA-группы» без текста.
- **Стало.**
  - У каждого шага реплики свой код и подпись (восстановление бэкапа, OpenVPN-профили, очистка, перезапуск OpenVPN, применение WireGuard, AZ-AWG2, клиенты и политики, возврат блокировок). В `failed` добавлена подпись шага, в `last_sync_error` пишется «реплика (шаг «…»): ошибка», из ошибки агента берётся только текст сообщения.
  - Сбой бэкапа primary сообщает шаг и узел: «Push full: ошибка на шаге «бэкап primary» (имя узла): …».
  - Окно результата первой секцией показывает упавшие реплики с шагом и ошибкой. Заголовок берётся из сообщения задачи, отчёт помечается как ошибка. Уведомление после синхронизации и применения домена сообщает об ошибке, а при сбое задачи показывает её текст.

#### Удаление узла отвечало `409`

- **Было.** Worker OpenVPN Buffer Guard каждые 20 секунд вызывал для каждого online-узла `get_settings()`, а та при отсутствии строки создавала её. `purge_node_related` таблицы Buffer Guard не чистил, внешний ключ без `ON DELETE`, поэтому любой узел, побывавший online, удалить было нельзя: `409 «на него ссылаются связанные данные»`. Так же мешали портальные ссылки клиентов (`client_portal_tokens`) и погашения промокодов (`unlock_code_redemptions`) на этом узле. На этом сервере у удалённого узла уже была такая строка (охрана выключена).
- **Стало.**
  - Вместе с узлом удаляются настройки и события Buffer Guard, портальные ссылки его клиентов и погашения без владельца.
  - Погашения с владельцем переносятся на оставшийся узел (локальный, иначе первый по id): повторное погашение проверяется по паре «код + пользователь», и после удаления записи владелец смог бы погасить тот же код ещё раз.
  - Worker выбирает online-узлы с включённой охраной одним запросом и строк не создаёт. Строка настроек по-прежнему появляется, когда настройки открывают или сохраняют в интерфейсе.
  - Тест берёт из моделей все таблицы со ссылкой на `nodes.id`, вставляет строку в каждую и удаляет узел через маршрут. Если появится новая таблица, а в `purge_node_related` её забудут, тест упадёт. Исключения — `nodes.linked_vpn_node_id` (обнуляется) и группы синхронизации (узел из HA-группы маршрут не удаляет).

#### WARP на узлах со старым агентом

- **Было.** В этом релизе `ANTIZAPRET_WARP` и `VPN_WARP` стали выбором из режимов `1`–`4` (None, All, Domain, Custom). Панель отправляла их агенту числами. Агент 2.25.1 (1.8.0) знает эти ключи как флаги и пишет `normalize_flag(value)`: `1` (None) становилось `y`, то есть WARP включался, а `2` (All) — `n`. Так происходило при репликации настроек AntiZapret, при лечении дрейфа и при сохранении настроек, когда активен удалённый узел со старым агентом.
- **Стало.**
  - Удалённому агенту режимы None и All отправляются как `n` и `y`. Старый агент записывает их как есть, новый переводит обратно в `1`/`2` (или оставляет y/n, если `setup` ещё в старом формате). Локальный узел по-прежнему пишет числа напрямую.
  - Domain и Custom в y/n не выражаются и уходят числами; старый агент записывает `n`. Реплика после записи перечитывает настройки: если режим не совпал, реплика попадает в ошибки репликации с текстом «обновите node agent» (для активного узла это предупреждение было и раньше).

#### Отзыв OpenVPN-клиента при повторной синхронизации

- **Было.** Отключение на реплике считалось по разнице PKI реплики до и после импорта: отключались клиенты, отозванные с прошлой синхронизации. Если попытка срывалась уже после импорта (не скопировались профили, агент не ответил на отключение), PKI реплики уже совпадала с primary, и повторная попытка получала пустой список. Отозванный клиент оставался подключённым к реплике (`reneg-sec 0`, сессия сама не переустанавливается).
- **Стало.**
  - К вновь отозванным добавляются отозванные клиенты без действующего сертификата, которые сейчас подключены к реплике (статус OpenVPN реплики). Статус читается, только если в `index.txt` есть отозванные.
  - Если статус прочитать не удалось, отключаются вновь отозванные, как раньше, а синхронизация не прерывается.

#### Блокировки при частичном сбое синхронизации

- **Было.** Блокировки WireGuard и AWG2 живут только в runtime, и применение конфигов primary на реплике их снимает. Push full при сбое реплики возвращал только блокировки WireGuard (`awg2=False`), даже если состояние AZ-AWG2 с primary уже было импортировано и применено, а упал, например, шаг копирования политик. При синхронизации клиента WireGuard возврат блокировок стоял после копирования профилей: сбой копирования (или исключение при применении конфигов) оставлял заблокированных клиентов подключёнными. Синхронизация AWG2 для клиента так же теряла блокировки, если применение runtime падало с исключением.
- **Стало.**
  - Push full при сбое после начала синхронизации AZ-AWG2 возвращает и блокировки AWG2. Если AZ-AWG2 на реплике не установлен (отдельная ошибка, состояние не тронуто), возвращаются только блокировки WireGuard, как раньше.
  - Синхронизация клиента WireGuard возвращает блокировки при любом сбое после начала копирования конфигов, AWG2 — после начала импорта состояния. Наружу уходит исходная ошибка; сбой возврата блокировок в этом случае пишется в журнал.

#### Проверка узла из вкладки после выполненного действия

- **Было.** `X-Expected-Node-Id` сверялся при каждом вызове `get_active_node` в запросе. Многие маршруты обращаются к активному узлу несколько раз: до действия и после него (например, сохранение настроек AntiZapret: проверка HA-реплики, адаптер, запись на узел, затем поиск HA-группы для репликации). Если узел переключали в другой вкладке, в боте или другим администратором между этими обращениями, запрос отвечал `409` «Действие не выполнено» уже после записи на узел, изменения в базе откатывались, репликация не запускалась.
- **Стало.**
  - Узел, прошедший проверку, закрепляется до конца запроса: повторные обращения возвращают его же, без повторной проверки и без перехода на новый активный узел. Запрос, который сам меняет активный узел, по-прежнему дальше работает с новым.
  - Если закреплённый узел тем временем удалён, узел ищется и проверяется заново, как раньше.
  - Запросы без заголовка работают как раньше. Фоновые задачи закреплённый узел не наследуют и проверяют ожидаемый узел заново при запуске.

#### Срок подписки нового профиля на репликах

- **Было.** При создании профиля (в панели и импортом CSV) срок подписки владельца записывался в политику на primary и сразу реплицировался, ещё до репликации самого профиля. Операция над политикой на реплике ищет shadow-профиль, его ещё не было: реплика попадала в ошибки («shadow VpnConfig not found»), а возвращённые ошибки каскад сроков не читал, он ловил только исключения. Создание профиля на реплике политику не копирует, поэтому срок на реплику не попадал вовсе: после его истечения клиент, заблокированный на primary, продолжал подключаться через реплику.
- **Стало.**
  - Срок записывается на primary до репликации профиля, как раньше, а на реплики уходит после неё. Импорт CSV делает так же.
  - Ошибки, которые вернула репликация политики, попадают в `replicate_errors` и в предупреждение («HA: N сбой(ев)…») при создании профиля и во всех каскадах срока подписки.
  - Погашение кода в портале пользователя уже реплицирует срок каждого продлённого профиля (исправлено вместе с блокером 3, раздел 1.1 «Промокод в портале менял сроки всем клиентам владельца»); это закреплено тестом.

#### Отключение OpenVPN-клиента, ротация ключа и пакетная блокировка

- **Было.**
  - `/openvpn/management/kill` в агенте проверял имя клиента только по длине (до 32 символов), а сервис подставлял его в `kill <имя>` и отправлял в management-сокет как есть. Имя с переводом строки (`bob\nsignal SIGTERM`) давало вторую команду management: остановить или перезапустить OpenVPN, отключить всех клиентов. Нужен API-ключ агента.
  - Ротация API-ключа собирала адаптер сама из `host:port` узла и учитывала только mTLS. Для узла с SSH-транспортом запрос шёл на порт агента напрямую, а не через туннель: на узле, где агент слушает только localhost, ротация не проходила (и автоматическая, и из карточки узла).
  - Пакетная блокировка WireGuard/AWG2 уходила на агент одним запросом, а агент принимает не больше 5000 имён. При большем числе заблокированных клиентов агент отвечал `422`, и панель записывала ошибку для всех клиентов: после перезапуска интерфейса или синхронизации ни один из них не блокировался. Переход на поштучную блокировку был только для `404`/`405` (старый агент без пакетного маршрута).
- **Стало.**
  - Имя в `kill` должно быть одним словом без пробелов и управляющих символов. Агент отвечает на другие имена `422`, а сервис не отправляет такую команду в сокет, кто бы его ни вызвал (панель, реплика, защита буфера OpenVPN). CN с точками и `@` по-прежнему можно отключить.
  - Ротация берёт адаптер узла так же, как остальные запросы: через SSH-туннель, по mTLS или по HTTP.
  - Панель делит пакетную блокировку на части по 5000 имён (лимит агента и панели задан одной константой) и собирает результаты всех частей. Старый агент без пакетного маршрута по-прежнему получает блокировки по одной.
  - Проверка имени в агенте работает после обновления агента на узле; до этого панель сама `kill` с такими именами не отправляет: отключает она только клиентов из PKI и из статуса OpenVPN.

### 1.5. Авторизация

#### Повторное использование refresh-токена

- **Было.** Refresh-токен менялся при каждом обновлении, но предъявление уже заменённого токена ни на что не влияло. Если cookie украли, злоумышленник и владелец могли жить параллельно. Два одновременных запроса с одним токеном получали две живые сессии.
- **Стало.**
  - У каждого входа своя «цепочка» токенов. Замена атомарная: условное обновление в БД, выигрывает ровно один запрос.
  - Если кто-то предъявляет заменённый токен, это признак кражи: вся цепочка этого входа отзывается.
  - Вкладки одного браузера делят cookie и иногда обновляются одновременно. Поэтому 30 секунд после замены старый токен ещё принимается: выдаётся access-токен без новой cookie. Работает это, только пока цепочка жива. После выхода, смены пароля или обнаруженной кражи окно не действует.
  - Токен, отозванный выходом, сменой пароля или ещё до обновления, просто получает `401` и не завершает другие сессии.
  - Неудачный refresh удаляет cookie, чтобы браузер не присылал мёртвый токен при каждом открытии страницы.

#### Смена пароля не отзывала выданные токены

- **Было.** После смены пароля старые access-токены панели и Mini App работали до истечения срока. Украденный токен переживал смену пароля.
- **Стало.**
  - У пользователя есть версия токенов. Она вшивается в access-токены и токены Mini App.
  - Любая смена пароля увеличивает версию и отзывает все refresh-токены. Это касается смены в настройках, принудительной при первом входе, администратором в карточке пользователя, через `reset-password.py` и пересоздания администратора установщиком. Все ранее выданные токены сразу получают `401`.
  - Текущая вкладка после смены пароля получает новый токен и остаётся в системе.
  - Токены, выданные до обновления (без версии), работают до первой смены пароля. Принудительного разлогина при обновлении нет.
  - Ту же проверку проходят потоки SSE (AWG2, AZ-WARP), мониторинг, документация OpenAPI и учёт активных веб-сессий. Функция, которая расшифровывала токен без проверки версии, удалена.
  - Версия увеличивается одной операцией в БД, так что две одновременные смены пароля не оставят рабочих старых токенов.

#### Смена своего пароля через карточку пользователя

- **Было.** `PATCH /api/users/{id}` с полем `password` для своей учётной записи менял пароль без проверки текущего: любой, у кого оказался чужой access-токен, мог сменить пароль и выкинуть владельца. Все сессии, включая текущую, завершались, а нового токена этот путь не выдавал. Не сбрасывался и `must_change_password`, не очищался bootstrap-пароль администратора из `.env`, в аудит не попадало `password_change`. В интерфейсе поля пароля в карточке сейчас нет, но API это позволял.
- **Стало.** Свой пароль через карточку сменить нельзя: `400` с подсказкой сменить его в настройках профиля, где нужен текущий пароль и выдаётся новый токен. Сброс пароля другого пользователя администратором работает как раньше и завершает только сессии этого пользователя.

#### Веб-сессия определялась по заголовку

- **Было.** Какую веб-сессию обновлять, закрывать или показывать как текущую, сервер брал из заголовка `X-Web-Session-Id`, который клиент может подставить любым.
  - `POST /auth/logout` удалял запись сессии из этого заголовка без всякого токена. Удаление отозванной записи снимало отзыв: access-токены с этим `sid` снова принимались до истечения. Сама сессия пользователя при выходе не отзывалась, её access-токен продолжал работать.
  - Middleware и heartbeat создавали и обновляли запись по заголовку. Украденная refresh-cookie с произвольным заголовком давала в списке сессий чужую строку, а её отзыв не касался настоящего семейства токенов.
  - У refresh-токенов, выданных до обновления, нет `family_id`. Обновление такого токена создавало новое случайное семейство, но в access-токен клало `sid` старого (пустого), поэтому такие сессии нельзя было отозвать на сервере. На этом сервере так выданы 9 из 10 живых refresh-токенов.
- **Стало.**
  - Сессия определяется только по токену: `sid` проверенного access-токена (middleware, heartbeat, признак «текущая» в списке сессий) или семейство refresh-cookie. Заголовок сервер больше не читает, фронтенд по-прежнему его отправляет.
  - Выход отзывает сессию, которую доказывает refresh-cookie или Bearer-токен: помечает запись отозванной вместе с refresh-токенами семейства, и её access-токены сразу получают `401`. Без cookie и токена выход сессий не трогает, просто очищает cookie.
  - Обновление токена без семейства кладёт в новый access-токен `sid` нового семейства. Следующий запрос создаёт запись сессии под этим id, и её можно отозвать вместе с refresh-токенами.

#### Гонка обновления токена с отзывом сессии, портал отключённого пользователя

- **Гонка refresh и отзыва.** Обновление токена фиксировало захват старого токена отдельной транзакцией и только потом вставляло новый. Отзыв сессии, попавший между ними, отзывал семейство без нового токена, и тот оставался живым в отозванной сессии (7 дней с продлением). Теперь захват и новый токен фиксируются одной транзакцией. Параллельный отзыв ждёт блокировку записи SQLite и отзывает уже оба. Проигравший захват сразу закрывает транзакцию, чтобы не держать блокировку. Тест воспроизводит гонку двумя потоками на файловой БД.
- **Портал пользователя.** Ссылка `u_…` продолжала работать после отключения пользователя (`is_active = false`), а ответ портала содержал внутренний `user_id`. Теперь ссылка отключённого пользователя получает `403 «Портал пользователя отключён»`, а `user_id` из ответа убран (фронтенд его не использовал). На этом сервере все пользователи активны.

### 1.6. Nginx и Cloudflare

#### Реальный IP клиента за Cloudflare

- **Было.** Подстановка реального IP из `CF-Connecting-IP` работала только на вебхуке Telegram. Остальная панель видела адреса узлов Cloudflare. Лимиты входа и блокировки считались по ним, так что один атакующий мог заблокировать вход администратору, а аудит показывал адреса Cloudflare.
- **Стало.** Подстановка работает во всех location'ах панели и клиентского портала. Заголовок принимается только от диапазонов Cloudflare, поэтому при прямом обращении к серверу подделать IP нельзя.

#### «Доступ только через Cloudflare» (origin lock)

- **Было.** Защита была сделана списком `allow` (диапазоны Cloudflare, localhost, RFC1918) и `deny all` в тех же location'ах, где работает подстановка IP. Nginx подставляет IP раньше, чем проверяет `allow/deny`, поэтому проверялся уже адрес посетителя, и все получали `403`, включая вебхук. Мы проверили это на реальном nginx.
- **Стало.**
  - Проверяется адрес самого TCP-соединения, до подстановки: `geo` в `conf.d/adminpanelaz-cloudflare-origin.conf`, который генерируется из того же allow-списка.
  - Location'ы подключают короткую проверку «соединение не от Cloudflare → 403».
  - Автообновление списков IP Cloudflare перегенерирует `geo` и откатывает все файлы, если `nginx -t` или reload не прошли.

#### `nginx-repair` удалял vhost портала

- **Было.** Скрипт искал vhost'ы панели по `server_name` регулярным выражением с границей слова. Точка тоже считается границей, поэтому под поиск попадали `portal.<домен>` и другие поддомены. `nginx-repair` удалял их, в том числе при каждом переключении Cloudflare proxy-mode в настройках. 19.09 так пропали портал и `test.claymore-dev.com`, 26.09 снова портал (восстановлен из бэкапа).
- **Стало.** Совпадает только точное имя в `server_name`. Закомментированные строки не учитываются, а точка в домене не означает «любой символ».

#### Флаги Cloudflare при ручном запуске скриптов

- **Было.** Флаги proxy-mode и origin lock скрипты nginx читали только из переменных окружения. Панель их выставляет, а при ручном `nginx-repair` или установке origin lock молча выключался, хотя в настройках (БД и `.env`) был включён. Поэтому на рабочем сервере он не действовал.
- **Стало.** Если переменная не передана, значение берётся из `.env`. Явно переданное значение по-прежнему важнее.

#### Панель открывалась по IP сервера

- **Было.** `nginx_install_site` удалял `sites-enabled/default`, а своего сервера по умолчанию не ставил. Nginx отдаёт запрос с неизвестным `Host` (в том числе голый IP) первому vhost'у на порту, то есть панели: `http://IP` редиректил на `https://IP`, и после предупреждения браузера о сертификате открывалась панель.
- **Стало.**
  - Вместе с vhost панели (установка, `nginx-repair.sh`, переключение Cloudflare proxy-mode, portal) ставится `sites-available/00-adminpanelaz-default-deny` на те же порты: HTTP — `return 444`, HTTPS — `ssl_reject_handshake on` на nginx ≥ 1.19.4, на старом nginx — свой самоподписанный сертификат (`/etc/ssl/…/adminpanelaz-default-deny.*`, ключ `600`) и `return 444`.
  - Сервер по умолчанию ставится только туда, где без него по IP отвечала бы панель: на порт, где первым vhost'ом идёт панель или портал. Порядок берётся из `nginx -T`, без него — как в `nginx.conf` Debian: `conf.d`, затем `sites-enabled`. Если первым идёт чужой сайт или на порту уже есть любой `default_server`, порт не трогается, и поведение чужих сайтов не меняется.
  - Порты собираются со всех vhost панели и портала сразу, поэтому установка портала не затирает порты панели. Адрес и IPv6 из `listen` панели повторяются в сервере по умолчанию.
  - Если в `server_name` панели IP-адрес (публикация без домена), HTTPS-порт не закрывается. Клиент, подключаясь по IP, не передаёт SNI, и `ssl_reject_handshake` отклонял бы саму панель.
  - У файла своя проверка записи и `nginx -t`: при ошибке откатывается только он, публикация панели не падает.
  - При переходе на прямую публикацию файл удаляется и nginx перезагружается без него, иначе он занял бы HTTPS-порт uvicorn. Подсчёт «других сайтов» перед остановкой nginx теперь читает настраиваемый каталог сайтов, а не жёстко `/etc/nginx/sites-enabled`. `uninstall.sh` удаляет файл и сертификат.
  - Shell-тест проверяет выбор портов, чужие `default_server` и порядок загрузки сайтов, IP-режим, объединение портов панели и портала, откат и прямую публикацию на подменённом nginx. При наличии nginx он ставит default-deny по живому серверу во временном каталоге: голый IP отклоняется по HTTP и HTTPS, домен панели отвечает, а панель с IP в `server_name` открывается.
  - Чтобы закрыть доступ по IP на уже опубликованной панели, нужно перегенерировать nginx (часть 3).

#### Сервер по умолчанию и чужой HTTPS-сайт по IP

- **Было.** HTTPS-порт не закрывался сервером по умолчанию, только если IP стоял в `server_name` файла панели или портала. Чужой сайт вида `server_name 203.0.113.20;` на том же HTTPS-порту, объявленный после панели, после установки `00-adminpanelaz-default-deny` по `https://IP` не открывался: без SNI рукопожатие доставалось серверу по умолчанию и отклонялось (на старом nginx клиент получал чужой самоподписанный сертификат).
- **Стало.** IP в `server_name` (IPv4 и IPv6) проверяется у всех загруженных файлов, и HTTPS-порт с таким сайтом не закрывается. HTTP-порт закрывается как раньше: запрос с `Host: IP` находит сайт по `server_name`. Сайт по IP на другом порту не мешает закрыть порты панели. На этом сервере сайтов с IP в `server_name` нет.

#### Geo Cloudflare при неудачной установке сайта

- **Было.** `conf.d/adminpanelaz-cloudflare-origin.conf` (geo для «Доступа только через Cloudflare») nginx подключает глобально, но при установке сайта он перезаписывался без отката. Если `nginx -t` не проходил, откатывались vhost и `server_names_hash`, а новый geo оставался; прежний лежал только в `/etc/nginx/backups` с отметкой времени. Обновление списка IP Cloudflare (`nginx_cloudflare_snippets_apply`) geo уже откатывало.
- **Стало.**
  - Перед изменением geo сохраняется копия рядом (`….conf.apaz-install.bak.<PID>`, не `*.conf`, поэтому nginx её не подключает), а если geo не было — метка `….apaz-install.new.<PID>`. Состояние хранится в файлах, потому что geo пишется и в подоболочке `conf="$(nginx_render_template …)"`.
  - Неудачный `nginx -t` в `nginx_install_site` (выделенный vhost панели, портал, установщик, `nginx-repair`) и в режиме subpath (`nginx-setup.sh`) возвращает geo к виду до установки или удаляет созданный. Копия берётся при первом изменении за запуск, поэтому повторное изменение не подменяет исходный вид.
  - После успешного `nginx -t` копия удаляется; история в `/etc/nginx/backups` пишется как раньше.
  - Shell-тест проверяет выделенный vhost, портал и subpath с подменённым nginx: откат прежнего geo, удаление созданного, неизменный актуальный geo, отсутствие временных файлов после успеха.

#### NAT порта 80 во время certbot standalone

- **Было.** Перед certbot standalone установщик снимал правила NAT для порта 80 внешнего интерфейса, но перед этим сохранял полный снимок `iptables-save` и после certbot возвращал его целиком через `iptables-restore`. Это откатывало все таблицы, в том числе правила, которые за время certbot добавили fail2ban, VPN или docker. Ошибки восстановления глушились. Если установку прерывали во время certbot, правила не возвращались вовсе. Отбор правил шёл по подстроке: `eth0` совпадал с `eth01`, `--dport 80` с `--dport 8080`.
- **Стало.**
  - Снимаются только правила `nat PREROUTING` с точным совпадением интерфейса по умолчанию, `-p tcp` и `--dport 80`, и возвращаются только они, одной транзакцией `iptables-restore --noflush`, на прежние позиции. Остальные правила, в том числе появившиеся за время certbot, не трогаются. Правило, которое кто-то уже вернул сам, не дублируется.
  - Правила возвращаются и при прерывании: общая обёртка `nginx_certbot_standalone` ставит EXIT-trap (bash выполняет его и при SIGINT/SIGTERM), затем выполняет прежний trap и восстанавливает его.
  - nginx обёртка останавливает сама, уже под этим trap'ом. Если установку прервали во время certbot или ожидания освобождения порта, nginx, остановленный для certbot, запускается обратно. Nginx, который до этого не работал, не запускается.
  - Если вернуть правила не удалось, установщик выводит готовые команды `iptables -t nat -A PREROUTING …` для ручного восстановления.
  - Shell-тест с подменёнными `iptables`/`iptables-restore` проверяет отбор правил, порядок, одновременные изменения цепочки, сбой и прерывание certbot, сохранность прежнего trap. При запуске от root он дополнительно проверяет настоящий iptables в отдельном сетевом namespace, не трогая файрвол сервера.

#### Shell-тесты трогали сервер

- **Было.** `test-nginx-portal-readiness.sh` не подменял `systemctl`, и при запуске от root делал настоящий `systemctl reload nginx` на сервере, где запущен (26.09 так перезагружался nginx рабочего сервера, конфиг не менялся). `test-nginx-portal-hardening.sh` создавал `/var/www/html/.well-known/acme-challenge`. ### 1.7. Установщик

- **SIGPIPE при выборе Python.** Установщик мог завершиться с кодом 141 ещё до появления меню: `head -n1` в конвейере с `pipefail` обрывал канал. Заменено на чтение первой строки без обрыва канала ([PR #14](https://github.com/Kirito0098/AdminPanelAZ/pull/14)).

#### API-ключи агентов в unit-файлах systemd

- **Было.** Установщик подставлял `NODE_AGENT_API_KEY` и `PROXY_AGENT_API_KEY` в строку `Environment=` unit-файлов `adminpanelaz-node.service` и `adminpanelaz-proxy.service`. Unit-файлы лежат в `/etc/systemd/system` с правами `644`, а переменные `Environment=` любой пользователь видит и через `systemctl show`. С ключом можно управлять агентом узла. При этом агент брал ключ из `node_agent.env` (`EnvironmentFile=` в systemd перекрывает `Environment=`), поэтому после ротации в unit-файле оставался старый ключ.
- **Стало.**
  - Ключа в шаблонах unit'ов больше нет. Установка unit'а записывает ключ в `backend/node_agent.env` / `proxy_agent.env` с правами `600` (общая функция в `scripts/lib-agent-key.sh`), и только если там его нет или стоит плейсхолдер. Ключ, сменённый ротацией, не затирается.
  - `refresh-systemd-units.sh`, который вызывается при обновлении панели и агента, берёт ключ из старого unit'а, переносит его в env-файл и переустанавливает unit без ключа.
  - Unit с `AGENT_API_KEY=` считается устаревшим: при старте панели, node agent и proxy agent он переустанавливается из шаблона, даже если обновление шло вручную (`git pull` и перезапуск). Обновление через интерфейс переустанавливает и unit proxy agent, в том числе на серверах только с прокси.
  - `lib-agent-key.sh` сохраняет symlink на env-файл, узнаёт те же плейсхолдеры, что `install.sh`, и не перезаписывает файл, если его не удалось прочитать. Временный файл называется `.tmp_*` и игнорируется git.
  - Ключ, лежавший в unit'е, мог прочитать любой локальный пользователь, поэтому после обновления его нужно сменить (см. часть 3).
  - Скрипты установки unit'ов принимают `SYSTEMD_UNIT_DIR`. Shell-тест ставит unit'ы во временный каталог с подменёнными `id` и `systemctl` и отказывается запускаться, если скрипт эту переменную не поддерживает.

#### Firewall при смене режима публикации

- **Было.** В режимах `http_direct` и `uvicorn_*` порт панели открывался правилом `iptables -A … -j ACCEPT` (или `ufw allow`), в режимах `nginx_*` закрывался правилом `DROP` (`ufw deny`), тоже дописанным в конец. Правило прежнего режима никто не удалял. После перехода на Nginx старый `ACCEPT` стоял выше и срабатывал первым, так что `IP:8000` оставался открыт; при обратном переходе старый `DROP` закрывал панель снаружи. То же при переустановке `install.sh` в другом режиме (там порт открывается веткой HTTPS).
- **Стало.**
  - Открытие порта (`firewall_iptables_open_port`, `firewall_ufw_open_port`) сначала удаляет все `DROP` для этого порта, закрытие — все `ACCEPT`, затем добавляет своё правило, если его ещё нет.
  - Для ufw правило удаляется по описанию (`ufw delete allow|deny <порт>/tcp`): так снимается и пара `(v6)`, и это работает на неактивном ufw, где `ufw status numbered` пуст. Удаляются только правила «со всех адресов»: разрешения с IP панели для агентов не трогаются.
  - Shell-тест с поддельными `iptables` и `ufw` (shell-функции, настоящий файрвол тест изменить не может) проверяет обе стороны перехода, переустановку, повтор, дубли и сохранность чужих правил.

#### Права каталога бэкапов

- **Было.** Архивы бэкапов создавались по umask: файлы `644`, каталог `BACKUP_ROOT` `755` (так было и на рабочем сервере). В архивах лежат БД панели и `.env`, поэтому их мог прочитать любой локальный пользователь.
- **Стало.**
  - `BackupManager` делает каталог `700`. Архив, его метаданные и временные файлы создаются сразу с `600` (`os.open` с режимом, без окна с `644`). Загруженный с компьютера архив после переноса тоже получает `600`.
  - При старте панели `restrict_backup_dir_permissions` закрывает каталог и уже лежащие архивы `adminpanelaz_*` вместе с их `.json`. Посторонние файлы в каталоге не трогаются.

#### Неатомарная запись `.env`

- **Было.** `EnvFileService` (все сохранения настроек панели, включая Cloudflare, публикацию и ротацию секретов), запись настроек mTLS в `node_agent.env` и сохранение ротированного ключа агента перезаписывали файл на месте через `write_text`. Сбой или нехватка места посреди записи оставляли обрезанный файл, и панель или агент не поднимались.
- **Стало.**
  - Общий `app/services/atomic_file.py`: запись во временный файл в том же каталоге (`600`), `fsync`, `os.replace`, `fsync` каталога. При ошибке временный файл удаляется, прежний остаётся нетронутым. Symlink на `.env` сохраняется, обновляется целевой файл.
  - Им же пользуются восстановление бэкапа (раньше там была своя копия без `fsync` каталога) и метаданные бэкапов.
  - Временный файл называется `.tmp_*` и игнорируется git: остаток после сбоя с секретами внутри не попадёт в коммит и не помешает `git pull` на узле.
  - Если сбоит только `fsync` каталога после `rename`, это пишется в журнал, а не возвращается ошибкой: новые данные уже на месте.
  - `EnvFileService` читает и пишет `.env` под `flock` (`.env.lock`), поэтому воркеры, одновременно сохраняющие разные ключи, не теряют изменения друг друга.
  - Агент создаёт `node_agent.env`, если его нет: ключа в unit'е больше нет, и без файла ротированный ключ пропал бы после перезапуска.

Тест исправлен, а `tests/conftest.py` теперь роняет любой тест, который пишет в `backend/.env`, `node_agent.env` или `proxy_agent.env`.
#### Повторная установка агента

- **Было.** `setup_node_env` и `setup_proxy_env` пересоздавали `node_agent.env` / `proxy_agent.env` из примера и генерировали новый ключ, если его не передали явно; мастер тоже по умолчанию предлагал сгенерировать ключ. Настройки mTLS из файла пропадали. `install.sh --reinstall` вызывал `uninstall.sh --remove-system-config`, который удалял `/etc/adminpanelaz/mtls`. После любой из этих операций панель не могла достучаться до узла, пока его не перепривяжут вручную.
- **Стало.**
  - Перед пересозданием env-файла установщик забирает из него ключ (если это не плейсхолдер) и строки mTLS. Явно переданный ключ (`NODE_AGENT_API_KEY=…` или ввод в мастере) по-прежнему важнее.

  - Если на сервере уже есть настоящий ключ, мастер первым вопросом предлагает оставить его (по умолчанию «да»).
  - `uninstall.sh` получил флаг `--keep-agent-pki`, и `--reinstall` его передаёт: `/etc/adminpanelaz/mtls` остаётся, остальная системная конфигурация удаляется как раньше. Обычное удаление с `--remove-system-config` по-прежнему убирает и PKI.

#### Firewall и SSH, nginx и чужие сайты

- **Было.**
  - С включённым в мастере ufw установщик сначала выполнял `ufw --force enable` (входящие по умолчанию запрещены), а разрешающие правила добавлял потом. Правила для SSH не было вовсе: если ufw до этого не был настроен, после установки на сервер нельзя было войти по SSH, а порт панели открывался уже после включения.
  - Порт backend, node agent или proxy agent мог совпасть с портом SSH, и правило `DROP`/`deny` закрывало SSH.
  - `uninstall.sh` искал правила панели в `ufw status numbered` по шаблону `[N]` и пропускал номера 1–9 (ufw выводит `[ 1]`), а на неактивном ufw не находил ничего.
  - Перед остановкой nginx при переходе на прямую публикацию чужие сайты искались только в `sites-enabled`. Сайт в `conf.d` или в другом include не замечался, и nginx останавливался вместе с ним.
- **Стало.**
  - Порты SSH определяются по текущей сессии (`SSH_CONNECTION`), `sshd -T`, слушающим сокетам (`ss`) и активному `ssh.socket` (при socket-активации, по умолчанию в Ubuntu 22.10+, порт слушает systemd, и в `ss` процесса sshd не видно), без данных — 22. Если правило закрыло бы один из них, настройка firewall отказывается и объясняет почему.
  - Если ufw не активен, SSH разрешается заранее, а ufw включается последним, после всех правил панели. Своё правило SSH пользователя (например, только со своего IP) не расширяется, на активном ufw SSH не трогается.
  - `uninstall.sh` берёт правила панели из `ufw show added` (видно и на неактивном ufw) и удаляет их по описанию вместе с `(v6)`. Правило SSH, добавленное панелью, остаётся: иначе активный ufw после удаления закрыл бы SSH, а повторная установка, увидев активный ufw, его не вернула бы.
  - Чужие сайты nginx ищутся по полному списку файлов из `nginx -T` (без него — `sites-enabled` и `conf.d`): считается любой файл с блоком `server`, кроме файлов панели и стандартных заглушек `default` и `conf.d/default.conf` (пакет nginx.org). vhost панели удаляется всегда, nginx останавливается, только если чужих сайтов нет.
  - Три shell-теста с подменёнными `ufw`, `iptables`, `sshd`, `ss`, `nginx` и `systemctl` проверяют определение портов SSH, отказ закрыть SSH, порядок правил при включении ufw, сохранность правил SSH пользователя, связку uninstall + install на активном и неактивном ufw и подсчёт чужих сайтов (`conf.d`, include без `listen`, закомментированные блоки, `upstream`, файлы панели).

Теперь слабый пароль из `WIZ_ADMIN_PASSWORD` или `.env` заменяется, а без пароля он генерируется только для новой БД. #### Nginx после `uninstall.sh --remove-nginx`

- **Было.** Удаление убирало vhost панели по `DOMAIN` и default-deny, перезагружало nginx, а затем всегда удаляло `snippets/cloudflare-realip.conf`, `cloudflare-origin-lock.conf`, `cloudflare-origin-allow.conf` и geo `conf.d/adminpanelaz-cloudflare-origin.conf`. Их подключают и vhost портала, и vhost других доменов панели (и могут подключать чужие сайты). Работающий nginx этого не замечал, но при следующем перезапуске или перезагрузке сервера падал с `open() "…/snippets/cloudflare-realip.conf" failed`. `--remove-nginx` передаёт и `install.sh --reinstall`, так что прерванная переустановка оставляла nginx в том же состоянии. Воспроизведено старой функцией на временном каталоге с vhost портала: настоящий `nginx -t` после удаления падал.
- **Стало.**
  - Общий файл Cloudflare удаляется, только если его не подключает ни один оставшийся файл в каталоге nginx (включая symlink на файлы вне него). Закомментированные строки и `/etc/nginx/backups` не считаются. geo остаётся, пока его переменную использует origin lock или другой сайт, allow — вместе с geo.
  - Про оставленный файл выводится предупреждение со списком файлов, которые его используют. vhost портала и чужие сайты не удаляются: удаление с `--remove-nginx` при переустановке не должно терять портал.
  - `nginx -t` и reload выполняются один раз после всех удалений. Если `nginx -t` не прошёл, nginx не перезагружается, выводится предупреждение. Если удалять было нечего, nginx не трогается.
  - Пути `/etc/nginx` и `/etc/ssl` в этой функции переопределяются (`NGINX_DIR`, `SSL_DIR`). Shell-тест работает на временных каталогах и проверяет результат настоящим `nginx -t`; он отказывается запускаться, если функция снова пишет в `/etc` напрямую.
  - На этом сервере `cloudflare-realip.conf` кроме vhost панели подключает vhost портала `portal_claymore-dev_com`: прежний `uninstall.sh --remove-nginx` оставил бы nginx, который не поднимется после перезагрузки.

#### Обновление из панели через `npm ci`

- **Было.** Установщик и меню ставили зависимости интерфейса через `npm ci`, а обновление из раздела «Обновления» — через `npm install`. Он не обязан держаться `package-lock.json`: может поставить другие версии и изменить lock-файл в рабочем каталоге, после чего `git pull` следующего обновления спотыкается о локальные изменения.
- **Стало.** Обновление из панели выполняет `npm ci` в `frontend`. Сбой показывается как «Ошибка: npm ci» с выводом npm, сборка и перезапуск не выполняются. Подпись шага в разделе «Обновления» — «pip install и npm ci». Ключ `npm_install` в подробностях ответа сохранён для совместимости.

#### ESLint и промежуточные сборки

- **Было.** `eslint.config.js` игнорировал только `dist`. `npm run build` собирает в `dist.next` и подменяет `dist` через `dist.old`; после прерванной сборки или замены эти каталоги остаются, и `npx eslint .` проверял собранный код.
- **Стало.** Игнорируются `dist`, `dist.next` и `dist.old`. Vitest-тест проверяет это через API ESLint (`isPathIgnored`) и то, что `src` по-прежнему проверяется.

### 1.8. Надёжность бэкенда

#### Восстановление бэкапа поверх рабочей базы

- **Было.** БД панели, БД CIDR и `.env` из архива записывались прямо поверх рабочих файлов, без проверки. Повреждённая или обрезанная база в архиве затирала рабочую, и панель не поднималась. Копии прежних файлов не оставалось. Запись шла на месте: сбой посередине оставлял наполовину записанный файл или смесь старых и новых файлов. Файлы получали права по umask (`644`).
- **Стало.**
  - БД из архива проверяется до любых изменений: заголовок SQLite и `PRAGMA integrity_check`. Битая база отклоняется с `400`, и ни рабочие файлы, ни узлы не трогаются.
  - Перед заменой текущие БД и `.env` копируются в `<каталог бэкапов>/.pre-restore/<время>/` (каталог `700`, файлы `600`, хранятся 3 последние копии). БД копируется через online backup SQLite, поэтому данные из WAL тоже попадают в копию.
  - Каждый файл пишется во временный файл рядом и подменяется атомарным `rename` с правами `600`. Старые WAL/SHM удаляются, чтобы SQLite не применил их к новой базе.
  - Если запись одного из файлов не удалась, уже заменённые возвращаются из копии. Сбой отката пишется в лог с путём к копии.
  - Если на диске не хватает места на копию и новые файлы, восстановление отклоняется (`507`) ещё до изменений на узлах.
  - Копии видны в «Настройки → Резервные копии → Копии перед восстановлением»: дата, размер, состав и общий объём (три копии рабочей базы занимают около 1 ГБ). Копию можно удалить или откатиться к ней. Откат возвращает только базу, CIDR и `.env`, узлы не трогает. Перед откатом текущее состояние тоже сохраняется как копия, поэтому откат можно отменить.
  - На время замены фоновые задачи приостанавливаются во всех воркерах. Каждый шаг фонового цикла держит разделяемый `flock` на `<БД>.bg-gate.lock`. Восстановление сначала берёт `<БД>.bg-intent.lock`, после чего новые шаги пропускаются, затем ждёт текущие (до 30 секунд) и держит обе блокировки до перезапуска панели: ядро снимает их вместе с процессом. Если шаг не успел завершиться, восстановление отклоняется (`409`) до изменений на узлах и в файлах. При сбое восстановления пауза снимается сразу. Если после восстановления не удался сам перезапуск (`systemctl restart` вернул ошибку или бросил исключение), пауза тоже снимается и ошибка пишется в лог: иначе планировщики стояли бы до ручного перезапуска.
  - Откат к копии не удаляет саму эту копию. Раньше откат к самой старой из трёх копий сначала сохранял текущее состояние как новую копию, а лимит «три последние» тут же удалял старейшую — ту, к которой откатывались. Теперь копия, к которой идёт откат, при очистке пропускается (в этот момент копий может стать четыре). Задачи, запущенные из интерфейса (пул `bg-task`), и обработка обновлений Telegram-бота не приостанавливаются: их запускает сам администратор, а перезапуск после восстановления их прерывает.

#### Миграции с пересозданием таблиц

- **Было.** Миграции были обёрнуты в транзакцию SQLAlchemy, но драйвер SQLite не открывает транзакцию перед `CREATE`/`DROP`/`ALTER` и коммитит их сразу. Откатывались только вставки данных. Если панель падала посреди «создать `<таблица>_new` → скопировать → удалить старую → переименовать», в базе оставалась `<таблица>_new`, и следующий старт падал с «table already exists». Мы воспроизвели это в тесте. Политики OpenVPN и WireGuard переносились двумя шагами, а проверка смотрела только на OpenVPN, поэтому после сбоя между ними WireGuard не переносился никогда. Каждый воркер uvicorn запускал миграции одновременно с остальными.
- **Стало.**
  - Каждая миграция идёт в одной настоящей транзакции (`BEGIN IMMEDIATE … COMMIT`), DDL тоже откатывается.
  - Пересоздание таблицы перепроверяет состояние уже внутри транзакции и удаляет остаток `_new` от прежнего сбоя. Политики OpenVPN и WireGuard проверяются по отдельности.
  - Воркеры выполняют всю подготовку БД при старте (создание таблиц, миграции панели и CIDR, начальное заполнение) по очереди под файловой блокировкой `adminpanel.db.migrate.lock` (права `600`). Ожидание блокировки пишется в лог.
  - Проверено на копии рабочей базы: схема не меняется, миграции занимают около 0,5 с.

#### Рост истории VPN-сессий и refresh-токенов

- **Было.** Ночная чистка удаляла старые сэмплы трафика, метрики и журнал, но не историю сессий и не refresh-токены. Каждое переподключение OpenVPN создаёт новую запись сессии: на рабочем сервере за 7 недель набралось 138 тыс. завершённых сессий на 47 конфигов (около 2,2 тыс. в день). Сборщик трафика каждую минуту загружал в память все сессии узла, поэтому нагрузка росла вместе с таблицей. Refresh-токены тоже только копились.
- **Стало.**
  - Ночная чистка удаляет завершённые сессии старше 30 дней. Срок настраивается: Настройки → Обслуживание VPN → «Хранение и карта» → «Сессии VPN, дн.» (`TRAFFIC_SESSION_RETENTION_DAYS`). Активные сессии не удаляются.
  - Сборщик и пересчёт базы сессий загружают только активные сессии (по частичному индексу) и сессии из текущего снимка. На рабочей базе это 2 мс вместо примерно 0,9 с каждую минуту. Вернувшийся клиент WireGuard по-прежнему продолжает свою прежнюю запись, если вернулся в пределах срока хранения.
  - Видимые последствия: в карточке клиента число сессий и источников считается за срок хранения. Файл БД после чистки сам не уменьшается, SQLite переиспользует освободившееся место.
  - Refresh-токены, истёкшие больше 7 дней назад, удаляются: истёкший токен и так не принимается.

#### Автоматическая ротация ключей узлов

- **Было.** Цикл выбирал узлы по `nodes.updated_at <= сейчас − NODE_API_KEY_ROTATION_DAYS`, но `updated_at` обновляется при каждой проверке состояния узла (на рабочем сервере он совпадает с `last_seen_at`). Поэтому ключ удалённого узла при включённой ротации не менялся никогда. Исключение вне обработки одного узла (например, ошибка БД при выборке) тихо завершало задачу до перезапуска панели. HTTP-вызовы агентов (таймаут 30 с на узел) шли прямо в event loop. Прокси-узлы попадали в выборку, хотя у них нет API ротации.
- **Стало.**
  - Возраст ключа хранится в отдельной колонке `nodes.api_key_rotated_at`. Её обновляют автоматическая и ручная ротация, а также замена ключа в карточке узла. Для существующих узлов отсчёт идёт от даты добавления.
  - Ошибка итерации пишется в лог, и цикл продолжает работу. Ротация выполняется в пуле потоков.
  - Прокси-узлы исключены из выборки, ручная ротация для них отклоняется до обращения к агенту.
  - На рабочем сервере ротация выключена (`NODE_API_KEY_ROTATION_DAYS=0` по умолчанию), обновление ключи не меняет. Если её включить, узел «2 serv» (добавлен 13.09) получит новый ключ на первой проверке после наступления срока.

#### Фоновые задачи при нескольких воркерах

- **Было.** При `UVICORN_WORKERS>1` каждый воркер запускал все планировщики: сбор трафика, бэкапы, напоминания, истечение доступа, доставку вебхуков, монитор ресурсов. Задачи выполнялись по несколько раз. Каждый воркер при старте синхронизировал firewall и помечал все незавершённые задачи как прерванные. Поэтому воркер, перезапущенный вместо упавшего, «прерывал» задачи, которые ещё шли в соседних воркерах. Запланированная перезагрузка сервера жила в памяти принявшего её воркера: отмена, попавшая в другой воркер, отвечала «не найдена», и сервер перезагружался.
- **Стало.**
  - Фоновые задачи и монитор ресурсов запускает один воркер-лидер, который держит `flock` на `adminpanel.db.leader.lock` (права `600`). Остальные воркеры раз в 15 с пробуют взять блокировку. Если лидер упал или остановился, задачи подхватывает другой воркер. Ядро снимает блокировку и при аварийном завершении процесса.
  - Одноразовые действия старта (синхронизация firewall, миграция unit'ов systemd и старых списков CIDR, пометка прерванных задач и перезагрузок) выполняет только лидер при старте панели. Воркер, подхвативший лидерство позже, их пропускает: соседние воркеры в это время ещё работают.
  - Перезагрузка хранится в таблице `server_reboot_requests`, таймер остаётся в запланировавшем воркере. Перед выполнением таймер атомарно переводит запись из `pending` в `executing`, поэтому отмена из любого воркера успевает сработать. Дубль для узла отсекается уникальным частичным индексом. У записи есть владелец — процесс воркера (PID и время старта из `/proc`, чтобы повторно выданный PID не считался тем же процессом). Прерванными помечаются записи завершившихся воркеров и записи `pending`, просроченные больше чем на 2 минуты. Записи работающих воркеров не трогаются, даже если лидером при старте стал воркер, перезапущенный вместо упавшего.
  - Фоновые задачи получили такого же владельца. При старте прерванными помечаются только задачи завершившихся воркеров.
  - Пошаговые диалоги Telegram-бота (ввод значений настроек, создание unlock-кодов) и состояние входа через Telegram OIDC (PKCE, `redirect_uri`) хранились в памяти воркера. Следующее сообщение или callback, попавшие в другой воркер, диалог не продолжали, вход завершался ошибкой «сессия истекла». Теперь это состояние лежит в таблице `shared_state` БД панели со сроком жизни: диалог 1 час, вход 10 минут. Истёкшие записи удаляются при следующей записи. Состояние OIDC забирается атомарным `DELETE … RETURNING`, поэтому один `state` нельзя использовать дважды. Без настройки из lifespan (тесты, скрипты) состояние остаётся в памяти процесса.

#### Проверка лимитов трафика

- **Было.** Расход клиента за период (сутки, неделя, месяц) считался так: сначала `SELECT DISTINCT common_name` по всем сэмплам узла, чтобы найти варианты написания имени, затем загрузка каждого сэмпла клиента за период в память и суммирование в Python. На рабочем сервере в `user_traffic_sample` 1,1 млн строк, у самых активных клиентов 70–115 тыс. сэмплов. Одна проверка месячного лимита занимала около 1,1 с. У клиента OpenVPN их три (всего, UDP, TCP), и они повторяются при каждом пересчёте политики и открытии карточки.
- **Стало.**
  - Варианты имени берутся из таблицы итогов `user_traffic_stat_protocol` (48 строк). Коллектор пишет итог и сэмпл под одним и тем же именем, чистка трафика удаляет их вместе, а ночная чистка удаляет только старые сэмплы. Поэтому имена в итогах — надмножество имён в сэмплах (на рабочей базе расхождений 0).
  - Сумма считается одним запросом `SUM` по новому индексу `(common_name, created_at)`. Условие по узлу записано как `node_id + 0`, иначе SQLite выбирает индекс `(node_id, created_at)` и проходит сэмплы всех клиентов узла за период.
  - Прежний индекс по одному `common_name` удалён: новый начинается с того же столбца.
  - На копии рабочей базы: 37–50 мс вместо 1,1 с, результаты совпадают с прежним расчётом во всех 48 проверенных комбинациях (клиент, период, протоколы). Миграция индекса занимает около 1 с.
  - Агрегаты по часам не понадобились: при таком времени запроса они только усложнили бы сбор и чистку.

#### Блокировка event loop

- **Было.** Панель работает в одном event loop на воркер. Синхронная работа внутри `async`-кода останавливает все запросы, пока не закончится. Так работали:
  - фоновые циклы автобэкапа (архив БД около 300 МБ и отправка в Telegram), ночного обновления CIDR (загрузки, минуты), обновления IP Cloudflare, синхронизации сертификатов с узлов и напоминаний пользователям;
  - живой поток мониторинга (опрос агентов каждые несколько секунд) и WebSocket монитора сервера (замер трафика интерфейса спит 0,35 с на каждом тике);
  - потоки установки AZ-AWG2 и обновления AZ-WARP (ожидание каждой строки от агента);
  - `async`-эндпоинты восстановления AZ-AWG2, загрузки бэкапа с восстановлением и импорта CSV;
  - обработка обновлений Telegram-бота (БД, агенты узлов, бэкапы, отправка файлов).
- **Стало.**
  - Циклы вызывают тело итерации через `asyncio.to_thread`.
  - SSE-потоки читают синхронный генератор по шагу в отдельном потоке (`iterate_in_thread`) и закрывают его, когда страница закрыта. Закрытие встаёт в очередь за незавершённым чтением, а не выполняется параллельно с ним. Мониторинг и WebSocket собирают данные в пуле потоков.
  - Эндпоинты загрузки стали обычными синхронными маршрутами: FastAPI выполняет их в пуле потоков.
  - Обновления бота обрабатываются в отдельном потоке `telegram-bot` с постоянным event loop. HTTP-клиент бота привязан к этому loop. Обработчик открывает свою сессию БД: сессия запроса закрывается, когда Telegram обрывает запрос, а бот ещё работает. Команды бота идут по очереди друг за другом, панель при этом отвечает. Если Telegram оборвёт долгий запрос вебхука, начатое действие доводится до конца.
  - Запросы к БД в middleware проверки IP-ограничений и активной сессии тоже вынесены из event loop, см. «Остатки P3 надёжности бэкенда».


#### Остатки P3 надёжности бэкенда

- **Записи о перезагрузках сервера.** Строки `server_reboot_requests` не удалялись. Теперь ночная чистка удаляет завершённые записи (выполнена, отменена, прервана, ошибка) старше 30 дней. Запланированные и выполняемые перезагрузки не трогаются.
- **Приватный `_is_vpn_node`.** Функцию из `node_manager` импортировали больше двадцати модулей, в том числе `node_key_rotation`, то есть она давно стала общей. Переименована в `is_vpn_node`, поведение не менялось.
- **Гонка таймера перезагрузки и отмены.** Теста не было. Добавлены три: отмена успевает между срабатыванием таймера и сменой статуса, таймер успевает между проверкой и сменой статуса в отмене, и 30 одновременных срабатываний с отменой. Во всех случаях победитель ровно один: либо перезагрузка отменена и не выполнялась, либо выполнена один раз, а отмена вернула «уже нельзя отменить». Код менять не пришлось: обе стороны меняют статус условным `UPDATE … WHERE status = 'pending'`.
- **Общий пул потоков.** Все фоновые циклы уходили в пул `asyncio.to_thread` по умолчанию (7 потоков на 3 CPU), и многоминутный автобэкап, обновление CIDR или чистка ретенции занимали потоки, которые нужны мониторингу каждые несколько секунд. Теперь автобэкап, чистка runtime-бэкапов CIDR, плановое обновление CIDR и ночная ретенция идут в отдельный пул `long-task` из трёх потоков (`run_long_task`, копирует contextvars, как `to_thread`). Короткие циклы мониторинга остались в общем пуле, задачи из интерфейса — в своём пуле `bg-task`.
- **Запросы к БД в middleware.** Проверка IP-ограничений и обновление активной сессии открывали сессию SQLAlchemy и ходили в SQLite прямо в event loop, на каждый запрос. Теперь эта работа идёт через `run_in_threadpool` (пул anyio, в котором FastAPI выполняет синхронные маршруты), а в event loop остаётся только формирование ответа. Поведение не изменилось: жёсткий отказ, отказ с записью попытки, редирект на `/ip-blocked` для страниц.

#### Удаление пользователя отвечало `500`

- **Было.** Перед удалением пользователя `_purge_user_before_delete` передавал его профили преемнику и чистил токены, журналы и ключи входа, но не трогал погашения промокодов (`unlock_code_redemptions.user_id`) и поля «кто создал» у промокодов и портальных ссылок (`unlock_codes`, `client_portal_tokens`, `user_portal_tokens.created_by_user_id`). У этих внешних ключей нет `ON DELETE`, и удаление пользователя, который гасил промокод или создавал код либо ссылку, падало с `500`. На этом сервере так нельзя было удалить только Claymore: погашения и созданные коды и ссылки есть только у него.
- **Стало.**
  - Погашения пользователя удаляются. Если бы вместо этого обнулялся `user_id`, погашение стало бы клиентским и могло бы нарушить уникальность (код, клиент, узел).
  - У созданных пользователем промокодов и портальных ссылок поле «кто создал» обнуляется, сами коды и ссылки продолжают работать.
  - Тест берёт из моделей все внешние ключи на `users.id`, вставляет строку в каждую такую таблицу и удаляет пользователя через маршрут. Если появится новая таблица, а очистку для неё забудут, тест упадёт. Он же проверяет, что профили переходят администратору, а строки администратора не меняются.

#### Порог Buffer Guard сбрасывался при каждом запуске

- **Было.** Миграция заменяла порог 500 за 60 секунд (прежнее заводское значение) на рекомендованный для режима, но маркера у неё не было. Она выполнялась при каждом запуске панели, поэтому 500/60, выставленные администратором сознательно, после перезапуска снова менялись на рекомендованные.
- **Стало.** Миграция выполняется один раз и ставит маркер `migration_openvpn_buffer_guard_factory_thresholds_done` в `app_settings` в той же транзакции. На этом сервере вреда не было: сейчас у узлов пороги 40/60 и 120/60, значения 500/60 нет ни у одного.

#### Временный бан Buffer Guard снимался через минуту

- **Было.** В режиме `kill_restart_temp_ban` Buffer Guard добавлял клиента в файл `banned_clients`, а срок бана хранил в событии (`ban_expires_at`). Сверка политик OpenVPN, которая идёт после каждого сбора трафика (раз в минуту), строит файл по политике клиента в БД и про этот бан не знала. Поэтому клиент с политикой (почти любой) пропадал из файла на следующей сверке. По истечении срока Buffer Guard удалял клиента из файла напрямую, и так же снималась блокировка администратора или бан из более нового события.
- **Стало.**
  - Сверка политики OpenVPN (`reconcile_openvpn`) считает клиента забаненным, пока у него на этом узле есть событие Buffer Guard с `ban_expires_at` в будущем, так же как уже работал короткий бан после отключения клиента. Это касается всех мест, где вызывается сверка: лимиты трафика, срок доступа, синхронизация реплик.
  - По истечении срока Buffer Guard не правит файл сам, а запускает ту же сверку. Клиент убирается из файла, только если его не держат блокировка администратора, истёкший доступ, лимит трафика или более новый бан. Если запись на узел не удалась, срок в событии остаётся, и снятие повторится на следующем цикле.
  - На этом сервере режим с баном не включён ни на одном узле и событий Buffer Guard нет, поэтому после обновления ничего не меняется.

#### Ручная проверка Buffer Guard отключала автозащиту

- **Было.** Автоматический проход пропускал узел, если у него было любое событие Buffer Guard моложе паузы (`cooldown_minutes`, по умолчанию 15 минут). Событие пишет и кнопка «Проверить сейчас», и сбой чтения журнала. Поэтому после ручной проверки или одного сбоя `journalctl` (таймаут, недоступный агент) автозащита узла молчала 15 минут, даже если клиент продолжал забивать буферы.
- **Стало.**
  - Паузу запускают только автоматические события с превышением порога (уведомление, отключение, перезапуск, бан). Ручная проверка и сбой чтения журнала её не запускают, ручная проверка по-прежнему работает и во время паузы.
  - Чтобы сбой журнала, который повторяется, не присылал уведомление каждые 20 секунд, он сообщается и записывается в события один раз за паузу, отдельно по каждому юниту. При паузе 0 и при ручной проверке сбой сообщается каждый раз, как раньше. Остальные юниты узла в это время проверяются как обычно.
  - На этом сервере охрана включена на узле «Germani» в режиме «только уведомление», событий пока нет. Поведение при срабатывании по порогу не меняется.

#### Сбой отключения клиента в Buffer Guard

- **Было.** При превышении порога Buffer Guard сначала отправлял уведомление, потом отключал клиента. Ошибку агента при отключении (узел недоступен, таймаут) никто не ловил: проход по узлу обрывался, событие не записывалось, пауза не включалась, и через 20 секунд всё повторялось — новое уведомление, новая попытка, перезапуск сервера так и не наступал. Если агент отвечал `success: false` (например, нет сокета управления), событие получало итог «клиент отключён». Та же потеря события грозила при ошибке повторного чтения журнала перед перезапуском, а неудачный перезапуск записывался как «сервер перезапущен».
- **Стало.**
  - Ошибка отключения, повторного чтения журнала или перезапуска записывается в действия события как неудачная (`success: false` и текст ошибки), проход продолжается, событие пишется и включает паузу.
  - Итог события считается только по успешным действиям: бан, перезапуск, отключение. Если ни одно действие не удалось — «автоматические действия не удались».
  - В режимах с перезапуском эскалация идёт и после неудачного отключения: если после паузы ошибки в журнале не прекратились, сервер перезапускается. Если журнал после отключения прочитать не удалось, перезапуск не выполняется, и это видно в уведомлении.
  - Уведомление уходит после действий и перечисляет их итог, например «150 ENOBUFS in antizapret-udp; отключить клиента не удалось: Сокет antizapret-udp недоступен; сервер перезапущен».
  - На этом сервере действия с отключением не включены ни на одном узле (узел «Germani» — только уведомление, у узла «2 serv» охрана выключена). Для режима уведомлений меняется только момент отправки: после записи итога, а не до.

#### Остатки P3 Buffer Guard

- **Неизвестный режим.** Если в `openvpn_buffer_guard_settings.mode` оказывалось значение, которого нет в списке (ручная правка, база от другой версии), проход считал его режимом «отключение и перезапуск», то есть самым жёстким из автоматических. Теперь такой режим означает «только уведомление». API сохранить неизвестный режим по-прежнему не даёт.
- **Чистка событий.** Таблица `openvpn_buffer_guard_events` только росла. Теперь ночная чистка удаляет события старше 30 дней. События с заполненным `ban_expires_at` не удаляются: по ним ещё снимается временный бан.
- **Ожидание эскалации и восстановление бэкапа.** Перед повторной проверкой журнала проход спал `escalate_after_seconds` (по умолчанию 30 с) внутри фонового шага. Восстановление бэкапа ждёт завершения фоновых шагов тоже 30 с, поэтому попадание на это ожидание срывало восстановление по таймауту. Теперь ожидание идёт отрезками по 0,5 с и прерывается, как только восстановление запросило паузу (`background_pause_requested` в `background_gate`): эскалация отменяется, в событии и уведомлении — «идёт восстановление бэкапа, эскалация отменена». Воркер в этом случае не переходит к следующим узлам.
- **Старый агент узла.** Маршрут выборки журнала `/openvpn/buffer-guard/journal-sample` появился в этом релизе. На узле со старым агентом он отвечал `404`, исключение обрывало проход, и каждые 20 секунд в журнал панели падала трассировка. Теперь `404`/`405` на этом маршруте означают «Агент узла не поддерживает Buffer Guard: обновите агент узла»: воркер пишет это предупреждение в журнал один раз за время работы процесса (после обновления агента узел снова проверяется, и предупреждение сбрасывается), а «Проверить сейчас» отвечает `409` с этим текстом. Другие ошибки агента (недоступен, таймаут) так не маскируются.
- На этом сервере событий Buffer Guard нет, неизвестных режимов нет (узлы в режимах «только уведомление» и «отключение и перезапуск»). Агент узла «2 serv» сообщает версию 1.8.0, а этот номер был и у агента 2.25.1 без маршрута журнала, и в начале этого релиза уже с ним, поэтому по базе не понять, поддерживает ли он Buffer Guard. Охрана на этом узле выключена, воркер его не опрашивает. Если нажать «Проверить сейчас» на старом агенте, появится сообщение «обновите агент».

### 1.9. Frontend

#### Изменения уходили не в тот узел

- **Было.** Активный узел — одна настройка на всю панель. Её меняют другая вкладка, другой администратор, Telegram-бот и Mini App, а каждый запрос на изменение применялся к узлу, активному на сервере в момент запроса. Вкладка узнавала о смене только через опрос (раз в 45 секунд и при возврате на вкладку) и молча переключалась. Форма, загруженная для узла A, после этого сохранялась на узел B.
- **Стало.**
  - Запросы интерфейса на изменение (`POST`, `PUT`, `PATCH`, `DELETE`) передают узел, который показывает вкладка, в заголовке `X-Expected-Node-Id`. Если активен другой узел, сервер отвечает `409` (`active_node_changed`) с именем текущего узла и ничего не выполняет. Проверка встроена в `get_active_node`, через который работают все разделы.
  - Фоновые задачи, запущенные из интерфейса (например, `doall` и применение маршрутизации), выполняются с тем же ожидаемым узлом. Если узел сменили, пока задача стояла в очереди, она завершается с этой ошибкой, а не выполняется на другом сервере. Текст ошибки задачи берётся из сообщения, без `409: {…}`.
  - Запрос, который сам меняет активный узел (выбор узла, удаление активного узла), дальше работает с новым узлом. Автовыбор узла при пустой настройке проверку не отключает.
  - Вкладка больше не переключается молча. Если опрос или ответ `409` показывают, что узел сменили в другом месте, над страницей появляется предупреждение с кнопками «Перейти на „B“» и «Вернуть „A“» (второй кнопки у пользователей без прав администратора нет). Ответ опроса, пришедший во время выбора узла в этой же вкладке, отбрасывается.
  - Запросы без заголовка (Telegram-бот, Mini App, скрипты, старый интерфейс в открытой вкладке) работают как раньше.

#### Бесконечный спиннер при недоступном сервере

- **Было.** После перезагрузки страницы токена в памяти нет, и загрузка всегда начиналась с `POST /auth/refresh`. Если сервер не отвечал (перезапуск панели, обрыв сети), ошибка запроса не обрабатывалась, и спиннер «Загрузка...» крутился бесконечно. Зависший сервер держал спиннер тоже бесконечно: таймаута не было. Ответ 5xx на обновление токена (например, `502` от nginx во время перезапуска) сбрасывал сессию и отправлял на вход, в том числе при фоновом обновлении раз в 25 минут.
- **Стало.**
  - Проверка сессии при загрузке ограничена 15 секундами. На вход отправляет только отказ сервера (`401`/`403` или отказ в обновлении токена). Если сервер недоступен, молчит или отвечает ошибкой, показывается экран «Панель недоступна» с причиной и кнопкой «Повторить».
  - Обновление токена прерывается через 20 секунд, чтобы зависший запрос не блокировал остальные. При 5xx, `408`, `429` и сетевой ошибке сессия сохраняется, а запрос возвращает ошибку сервера вместо `401`.

#### Белый экран на `/login?tg_error=%25`

- **Было.** Страница входа ещё раз прогоняла через `decodeURIComponent` значение `tg_error`, которое браузер уже декодировал. `%25` превращался в `%`, повторное декодирование бросало `URIError`, и вместо страницы входа был белый экран. Сообщение со знаком `%` показывалось искажённым или тоже роняло страницу. Так же падала ссылка `/login#token=%`.
- **Стало.** Параметры разбираются один раз, некорректная escape-последовательность остаётся как есть. Текст ошибки ограничен 300 символами, пустой не показывается.

#### Потеря сессии

- **Было.** Если сервер отказывал в обновлении токена (срок входа истёк, сессию отозвали), `apiFetch` очищал токен и бросал `401`, но пользователь в интерфейсе оставался. Каждая страница показывала свою ошибку, а переход на вход происходил только после перезагрузки. Отзыв сессии через heartbeat выкидывал на вход без пояснения.
- **Стало.** Отказ в обновлении токена обрабатывается в одном месте, для всех запросов, включая QR, бэкап AWG2 и фоновое обновление: интерфейс сбрасывает пользователя и переходит на страницу входа с пояснением «Сессия завершена: срок входа истёк или сессию отозвали». То же пояснение показывается при отзыве сессии через heartbeat. Недоступный сервер (5xx, сеть) сессию не завершает.

#### Сессии после ввода капчи нельзя было отозвать

- **Было.** Сервер создавал запись веб-сессии при любом входе, но страница входа сохраняла её id только при входе без капчи (и отдельно для 2FA и passkey). После входа с капчей вкладка не отправляла `X-Web-Session-Id` и не опрашивала heartbeat, поэтому «Отозвать» в списке активных сессий помечал запись, а вкладка продолжала работать.
- **Стало.** Id сессии сохраняют сами функции входа (пароль, капча, 2FA, passkey), так что ни один путь его не теряет.

#### Токен Mini App и гонка обновления

- **Было.** Токен Mini App лежал в `localStorage` и переживал закрытие Mini App. При истечении каждый запрос, получивший `401`, сам запускал обновление: очищал токен и отправлял свой `POST /auth`. Несколько параллельных запросов давали несколько авторизаций, запросы между ними уходили без токена, а при непривязанном TG ID администратор получал уведомление на каждую попытку.
- **Стало.**
  - Токен хранится только в памяти. При запуске Mini App получает его заново по данным Telegram, а старая копия в `localStorage` удаляется.
  - Параллельные запросы ждут одного общего обновления, как в панели. Старый токен не сбрасывается, пока `/auth` не ответил.
  - Если токен уже обновил другой запрос, запрос повторяется с новым токеном без ещё одного `/auth`.

#### Графики в начальной загрузке

- **Было.** Страницы и так загружались лениво, но `manualChunks` в `vite.config.ts` принудительно собирал recharts в отдельный чанк вместе со всем, от чего он зависит, включая React. Входной скрипт импортировал React из этого чанка, и `index.html` делал `modulepreload` для `recharts-*.js` (482 КБ) и `victory-vendor-*.js` (63 КБ) на каждой странице, включая вход: 800 КБ JS до первого экрана. Кроме того, «Файлы» брали `formatBytes` из модуля с графиками, а «Трафик» и WARP подключали графики статически, хотя показывают их только в карточке клиента и на вкладке трафика.
- **Стало.**
  - `manualChunks` убран. Входной скрипт весит 400 КБ, кода графиков в нём нет.
  - `formatBytes` и `totalTraffic` вынесены в `lib/trafficFormat.ts`. Графики в карточке клиента «Трафика» и на вкладке трафика WARP загружаются через `lazy()`.
  - `npm run check:bundle` (шаг CI после сборки) падает, если код recharts попадает во входной скрипт или в статические импорты любой страницы, кроме «Мониторинга» и «Монитора сервера».

#### Отзыв веб-сессии на сервере

- **Было.** «Отозвать» в списке активных сессий только помечал запись `revoked_at`, и вкладка выходила сама при следующем heartbeat. Access- и refresh-токены этой сессии на сервере оставались действительными: клиент, который не опрашивает heartbeat (скрипт, старая вкладка), или украденная refresh-cookie продолжали работать до конца срока (до 7 дней с обновлением).
- **Стало.**
  - Каждый вход создаёт одну веб-сессию, и её id служит `family_id` refresh-токенов этого входа. Тот же id вшивается в access-токен (claim `sid`), в том числе после обновления и после смены пароля.
  - Отзыв сессии отзывает refresh-токены её семейства (причина `session`, это не считается кражей токена) и сразу отклоняет её access-токены. Вкладка получает `401` и переходит на вход с пояснением «Сессия завершена».
  - Отозванная запись не удаляется очисткой устаревших сессий, пока не истекут выданные access-токены (`ACCESS_TOKEN_EXPIRE_MINUTES`).
  - Входы, выполненные до обновления, становятся отзываемыми на первом обновлении токена, см. раздел 1.5 «Веб-сессия определялась по заголовку».

#### Вход через Telegram без сессии

- **Было.** Виджет Telegram, OIDC-колбэк и `POST /api/auth/telegram/oidc/token` выдавали только access-токен: без refresh-cookie и без записи веб-сессии. Такой вход не был виден в списке активных сессий, его нельзя было отозвать, и через 30 минут приходилось входить снова.
- **Стало.**
  - Все три пути выдают ту же пару, что и вход по паролю: access-токен с `sid`, refresh-cookie того же семейства и запись веб-сессии.
  - Редирект передаёт id сессии рядом с токеном (`/login#token=…&session=…`), и страница входа его сохраняет. Id принимается только как безопасное для заголовка значение (до 64 символов `A-Za-z0-9_-`).
  - Если id не пришёл, старый id вкладки стирается, чтобы heartbeat не проверял чужую сессию.

#### Удаление активного узла из своей вкладки

- **Было.** После удаления активного узла сервер делает активным локальный узел (или первый VPN-узел). Вкладка, из которой узел удалили, узнавала об этом из опроса и принимала за смену в другом месте: появлялось предупреждение «Активный узел сменён в другом месте», запросы на изменение уходили с id удалённого узла и получали `409`, а «Вернуть „…“» пыталась активировать удалённый узел и получала `404`.
- **Стало.**
  - Удаление узла, который показывает вкладка, считается её собственным переключением, как выбор узла: вкладка без предупреждения переходит на узел, который сервер сделал активным, и называет в `X-Expected-Node-Id` его. Ответы опроса, пришедшие во время удаления, отбрасываются. Если новый активный узел узнать не удалось, вкладка не называет узел в запросах до следующего опроса. Так же при пакетном удалении.
  - Удалённый узел сразу пропадает из списка узлов вкладки. Если показываемый узел удалили в другом месте, в предупреждении нет кнопки «Вернуть» на него.

#### Переключатели AZ-WARP после неудачного сохранения

- **Было.** На вкладке «Настройки» AZ-WARP переключатели FullVPN и «Автопатч DNS при загрузке» сразу меняли положение, а при ошибке сохранения (узел недоступен, агент отказал) так и оставались в новом. Показывалось уведомление об ошибке, но переключатель и плитка FullVPN показывали состояние, которого на узле нет.
- **Стало.** При ошибке сохранения переключатель возвращается в прежнее положение, уведомление об ошибке показывается как раньше. После успешного сохранения настройки, как и раньше, перечитываются с узла.

#### Buffer Guard сохранял настройки одного узла на другой

- **Было.** Карточка OpenVPN Buffer Guard загружает настройки по id узла. Если узел переключали, пока шла загрузка, ответ по прежнему узлу приходил позже и становился черновиком нового узла, а «Сохранить» подставлял в запрос id текущего узла. Так пороги и режим узла A записывались на узел B. Пока грузились настройки нового узла, карточка показывала черновик прежнего. Так же поздний ответ перезаписывал последние события.
- **Стало.**
  - Ответ на загрузку настроек, событий или сохранение применяется, только если карточка всё ещё показывает тот же узел и после него не начат более новый запрос того же вида. Остальные ответы отбрасываются.
  - При смене узла черновик, настройки, события и ошибки сбрасываются сразу.
  - Черновик помнит узел, для которого загружен, и сохраняется только на него. Если карточка уже показывает другой узел, сохранение не выполняется.

### 1.10. Отдельные баги

#### AZ-бэкап удалённого узла в Telegram

- **Было.** И ручной бэкап (из панели и бота), и бэкап по расписанию отправляли в Telegram файл по `archive_path`, который вернул агент. Это путь на узле, на сервере панели такого файла нет, поэтому архив AntiZapret удалённого узла в Telegram не приходил (ошибка только в журнале). Для локального узла всё работало.
- **Стало.**
  - Перед отправкой архив скачивается с узла через агент (`GET /backups/antizapret/download`, эндпоинт принимает только имя архива) во временный файл на панели. После отправки во все чаты временный файл удаляется.
  - Для локального узла архив отправляется с места, без копирования.
  - В Telegram файл приходит под исходным именем архива.

#### Запись файлов AWG2

- **Было.** Запись профиля AWG2 (через панель и агент) проверяла только, что путь лежит внутри `/opt/antizapret-awg/clients`. Так можно было перезаписать любой файл в этом каталоге, например `expiry.tsv` со сроками клиентов, или создать скрипт. Для профилей OpenVPN/WireGuard список разрешённых расширений агент уже проверял.
- **Стало.** Записываются только профили, которые панель сама показывает: `{туннель}-{имя}-am.conf`, `{туннель}-{имя}.vpn` и `{туннель}-{имя}-vpnuri.txt`, и только прямо в `clients/antizapret` или `clients/vpn`. Остальное отклоняется с `403`. Чтение не изменилось.

#### Панель отвечает 500 во время сборки интерфейса

- **Было.** Панель отдаёт интерфейс прямо из `frontend/dist`, а Mini App из `backend/app/static/tg_mini`. `npm run build:all` (обновление из меню и из панели, установка) собирал прямо туда: vite сначала очищает каталог, и несколько секунд до записи нового `index.html` все страницы отвечали `500`. Если сборка падала на середине, интерфейс оставался сломанным до следующей удачной сборки.
- **Стало.**
  - Сборка идёт в соседний каталог (`dist.next`, `tg_mini.next`), там же доделывается страница Mini App. Готовый каталог встаёт на место двумя переименованиями (`scripts/swap-build.mjs`), панель подхватывает его без перезапуска.
  - Если в новой сборке нет `index.html` или переименование не удалось, старая сборка остаётся на месте, а команда завершается с ошибкой.
  - Если `index.html` всё же нет (например, первая установка ещё не собрала интерфейс), панель отвечает `503` с `Retry-After`, а не `500`.

## Часть 3. Что сделать после обновления (эксплуатация)

1. **Перезапустить node agent на удалённых узлах**: исправление путей к файлам, безопасный импорт PKI и профилей на репликах и проверка имени клиента в `/openvpn/management/kill` работают только в новом агенте. Со старым агентом отозванный OpenVPN-клиент на реплике отключается общей командой, которая закрывает его сессию только на одном сервере, а блокировки WireGuard и AmneziaWG возвращаются по одному клиенту (медленнее, но работает).
2. **Перегенерировать nginx** (`scripts/nginx-repair.sh` или переключение proxy-mode в настройках), чтобы включились реальный IP и новый origin lock. На claymore-dev.com уже сделано 26.09.
3. **Сменить `SECRET_KEY`**, если панель когда-либо была опубликована напрямую (uvicorn на `0.0.0.0` без nginx).
4. **Проверить, что узлы и скрипты не обращаются к панели напрямую по IP**: с включённым origin lock такие запросы получают `403`. Работать нужно через домен за Cloudflare, localhost или VPN-сети RFC1918.
5. После обновления все, кто залогинен через токены старого формата, остаются в системе до первой смены пароля. Чтобы завершить старые сессии сразу, достаточно сменить пароль.
6. **Сменить API-ключи агентов.** До этого обновления ключ лежал в unit-файле systemd, который мог прочитать любой локальный пользователь узла. Для node agent достаточно ротации ключа в карточке узла. Для proxy agent ротации нет: сгенерировать ключ (`openssl rand -hex 32`), записать его в `backend/proxy_agent.env` на прокси, перезапустить `adminpanelaz-proxy` и заменить ключ в карточке узла.
7. **Перегенерировать nginx на опубликованных панелях** (`scripts/nginx-repair.sh` или переключение proxy-mode), чтобы появился сервер по умолчанию и панель перестала открываться по IP сервера. Если на сервере есть чужой `default_server` или по IP отвечает чужой сайт, скрипт его не трогает.
8. **Обновить Node.js до 22+** на уже установленных панелях: сам по себе он не обновляется. Повторный `install.sh` поставит 24.x, вручную: `curl -fsSL https://deb.nodesource.com/setup_24.x | sudo bash - && sudo apt-get install -y nodejs`, затем пересобрать интерфейс (`cd frontend && npm ci && npm run build:all`). На claymore-dev.com сейчас Node 20.20.2.
9. **Баны сканеров за Cloudflare.** При публикации через Cloudflare соединения к серверу приходят с адресов Cloudflare, поэтому бан в firewall по IP посетителя не действует, работает только блокировка панелью. Баны в firewall срабатывают при прямой публикации и за nginx без Cloudflare. После обновления проверьте в диагностике пункт «Баны сканеров в firewall».
