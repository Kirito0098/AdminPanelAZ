# Кодревью AdminPanelAZ (сентябрь 2026): что исправлено и что осталось

Ревью всего проекта провели шесть параллельных ревьюеров. Нашли 5 критичных проблем и около 60 важных. Исправления лежат в ветке `release/2.26.0` и задеплоены на рабочий сервер. Пользовательское описание каждого изменения есть в `CHANGELOG.md`, раздел `[Unreleased]`. Этот документ объясняет логику: как было, как стало и что ещё предстоит сделать.

**Состояние на 26.09.2026:**

- Критичные проблемы: закрыты все 5.
- Важные: закрыто около 30, открыто около 30, см. часть 2.
- Надёжность бэкенда (раздел 2.1) закрыта целиком. Мелкие остатки из повторных ревью перечислены в конце раздела 2.1.
- Что сделать на сервере после обновления — часть 3.

Каждое исправление сделано по одной схеме:

1. Сначала регрессионный тест, который падает на старом поведении.
2. Затем исправление.
3. Мутационная проверка: если откатить ключевую строку, тест снова падает.
4. Повторное ревью пачки исправлений.

---

## Часть 1. Исправлено

### 1.1. Критичные

#### Чтение любого файла сервера через раздачу фронтенда

- **Было.** Обработчик, который отдаёт файлы SPA, склеивал путь из URL с каталогом `frontend/dist` и не проверял, что результат остался внутри него. Запрос вида `/..%2f..%2fbackend%2f.env` без авторизации отдавал `.env` с `SECRET_KEY`, базу данных и любые другие файлы. Уязвимы были установки с прямой публикацией (uvicorn на `0.0.0.0`). Nginx такие пути отклонял сам.
- **Стало.** Путь приводится к каноническому виду, и файл отдаётся, только если он действительно лежит внутри `frontend/dist`. Всё остальное получает `index.html` (обычный клиентский маршрут). Путь с нулевым байтом раньше давал ошибку 500, теперь тоже `index.html`.
- **После обновления.** На установках с прямой публикацией нужно сменить `SECRET_KEY`: Настройки → Безопасность → ротация секретов.

#### Скачивание чужих VPN-профилей

- **Было.** У download, QR-кода и одноразовой ссылки есть параметр `path`. Роль «Пользователь» могла подставить туда путь к профилю другого клиента и получить его вместе с приватным ключом.
- **Стало.** Для не-администратора `path` должен входить в список файлов его собственного конфига, иначе `403`. У администратора поведение не менялось.

#### Сбор трафика в HA-группах

- **Было.** Состояние сессий трафика было уникально по ключу сессии (публичный ключ WireGuard) глобально. В HA-группе один клиент подключён и к primary, и к реплике, поэтому вторая запись нарушала уникальность. Транзакция после ошибки не откатывалась, и все следующие узлы в цикле падали каскадом. В итоге учёт трафика, лимиты и алерты тихо останавливались.
- **Стало.** Уникальность считается по паре «узел + ключ сессии» (миграция при старте). Ошибка БД на одном узле откатывает только его транзакцию и пишется в лог как warning, остальные узлы собираются нормально. Недоступный узел, как и раньше, логируется на уровне debug.

#### `SECRET_KEY` при переустановке

- **Было.** «Переустановка» и повторный запуск мастера с `--force` генерировали новый `SECRET_KEY`. Зашифрованные этим ключом данные в сохранённой БД становились нечитаемыми: API-ключи узлов, SSH-ключи транспорта, секреты 2FA.
- **Стало.** Прежний ключ сохраняется при сбросе `.env`.

#### Права на секретные файлы

- **Было.** `.env` и файлы БД создавались с правами `644`, то есть их мог прочитать любой локальный пользователь. Резервные копии `.env` при переустановке были такими же открытыми.
- **Стало.**
  - При каждом старте панель выставляет `600` на `.env`, `adminpanel.db`, `cidr.db` и их WAL/SHM-файлы.
  - Установщик сразу создаёт `.env` с правами `600`.
  - Каталог резервных копий переустановки получает `700`, файлы в нём `600`. Восстановление из него тоже ставит `600`.

### 1.2. Безопасность доступа

#### WebSocket мониторинга сервера

- **Было.** Сокет принимал любой расшифровываемый JWT. Подходили промежуточный токен 2FA (выдаётся до ввода кода) и токен отключённого пользователя.
- **Стало.** Сокет принимает только access-токен активного администратора.

#### Область действия токена Telegram Mini App

- **Было.** Вход в Mini App по данным Telegram, без пароля и без 2FA, выдавал обычный токен панели. С ним были доступны все разделы: настройки, узлы, бэкапы, SSH-ключи.
- **Стало.**
  - У токена отдельный тип. Он принимается только в `/api/tg-mini` и в тех эндпоинтах панели, которые вызывает сама Mini App: конфиги, пользователи, шаблоны, client-access, unlock-ключи. Остальные разделы отвечают `401`.
  - Токен отзывается при отвязке или перепривязке Telegram.
  - Вход отклоняется для отключённого пользователя и для данных Telegram без ID.

#### IP клиента за прокси

- **Было.** Адрес клиента брался из самого левого элемента `X-Forwarded-For`. Этот элемент задаёт сам клиент, поэтому IP-ограничения и лимиты входа можно было обойти подделкой заголовка. От подделки защищали только флаги запуска uvicorn.
- **Стало.** Берётся самый правый недоверенный элемент (его дописывает nginx), доверенные прокси пропускаются. Тот же адрес использует подсказка гео-маршрутизации узлов.

#### Агент узла: доступ к файлам

- **Было.**
  - Эндпоинт скачивания бэкапа AntiZapret отдавал любой файл узла по абсолютному или относительному пути. Достаточно было знать API-ключ узла.
  - Чтение и запись профилей проверяли путь сравнением строк, поэтому проходили соседние файлы, например `antizapret/client.sh`.
- **Стало.**
  - Скачивание принимает только имя архива `backup*.tar.gz`, лежащего прямо в каталоге AntiZapret или в `/root`. Пути, `..` и symlink наружу отклоняются.
  - Профили должны лежать внутри каталога `client`. Записывать можно только `.ovpn` и `.conf`.
- **После обновления.** Перезапустить node agent на удалённых узлах.

### 1.3. Telegram

#### Экранирование HTML в уведомлениях

- **Было.** Логин, User-Agent, имена клиентов, узлов и архивов, тексты ошибок вставлялись в HTML-сообщения администраторам как есть. Логин вида `<a href=…>` превращался в ссылку в уведомлении, а ошибка узла с символом `<` ломала отправку.
- **Стало.** Все значения, которые приходят от пользователя или извне, экранируются.

#### Проверка IP на вебхуке

- **Было.** Вебхук проверял, что запрос пришёл с IP Telegram, и доверял заголовку `X-Real-IP` от кого угодно. При прямом доступе к uvicorn проверку обходили подделкой заголовка.
- **Стало.** `X-Real-IP` учитывается только от доверенного прокси: адрес должен точно совпадать со значением из `TRUSTED_PROXY_IPS`.

#### Бот в группах

- **Было.** Бот отвечал на команды в группах и каналах, поэтому конфиги, QR-коды и ссылки уходили в общий чат.
- **Стало.** Интерактивный бот работает только в личных чатах.

#### Повторная доставка update

- **Было.** Если обработчик работал медленно или падал, Telegram присылал тот же update повторно. Команды «восстановить бэкап» или «перезагрузить сервер» могли выполниться дважды.
- **Стало.**
  - Каждый `update_id` обрабатывается не больше одного раза. Учёт ведётся в таблице БД, поэтому он общий для нескольких воркеров uvicorn.
  - Ошибка обработчика пишется в лог, а Telegram получает `200`, чтобы не присылать update повторно.
  - Старые записи в таблице чистятся.

#### Бэкапы в боте по номеру в списке

- **Было.** Кнопки «Восстановить» и «Удалить» ссылались на номер архива в списке. Если между подтверждением и выполнением появлялся новый авто-бэкап, список сдвигался, и действие применялось к другому архиву.
- **Стало.** Кнопки ссылаются на хэш имени файла. Кнопки из старых сообщений отвечают «Архив не найден».

#### Видимость VPN-профилей при отправке файлов

- **Было.** Отправка конфига в чат (inline-режим, кнопка в боте, Mini App) не учитывала настройку «Видимость VPN-профилей». Скрытый вариант профиля уходил, если он был первым файлом или если его путь передавали явно.
- **Стало.** Отправка всегда фильтрует файлы по видимости отправителя. Явно указанный скрытый путь отклоняется, по умолчанию уходит первый видимый файл.

### 1.4. HA и узлы

#### Снятие блокировок WireGuard на репликах

- **Было.** При синхронизации крипто-состояния с primary (создание или удаление клиента, лечение дрейфа, Push full) реплика применяла конфиги primary целиком. Peer'ы, удалённые из runtime ручной или временной блокировкой, возвращались, и заблокированный клиент снова получал доступ.
- **Стало.**
  - После синхронизации блокировки переприменяются на реплике по её политикам доступа.
  - Push full делает это после копирования политик, для WireGuard и AWG2.
  - Если Push full прервался после восстановления, блокировки WireGuard всё равно возвращаются.
  - Сбой блокировки одного клиента не останавливает остальных и не отменяет копирование профилей. Синхронизация при этом помечается как неуспешная, с именами клиентов.

#### Импорт PKI, профилей и восстановление реплики из архива

- **Было.** Импорт easyrsa3 на реплику (синхронизация крипто-состояния с primary) сначала удалял `/etc/openvpn/easyrsa3` и только потом открывал архив. Битый, обрезанный или не тот архив оставлял узел без PKI, а OpenVPN читает CA прямо оттуда (`ca ../easyrsa3/pki/ca.crt`) и после перезапуска не поднялся бы. HA-restore при Push full удалял PKI, конфиги WireGuard и профили клиентов до распаковки архива primary. Импорт профилей OpenVPN и WireGuard удалял каталоги профилей перед распаковкой: сбой посередине (например, кончилось место) оставлял часть профилей удалённой.
- **Стало.**
  - Архив сначала целиком распаковывается во временный каталог рядом с целевым (та же файловая система) и проверяется: каталог easyrsa3 на месте, в архиве профилей есть файлы нужного типа, в архиве primary есть easyrsa3. Повреждённый архив отклоняется (`400` для импорта, ошибка Push full для реплики), текущие файлы не трогаются.
  - Заменяемые пути переименовываются в скрытые копии рядом, новые файлы ставятся на их место. При любом сбое записанное удаляется и копии возвращаются, в том числе для путей, которых раньше не было. После успеха копии удаляются.
  - Посторонние элементы архива (не easyrsa3 и не нужные каталоги профилей), как и раньше, игнорируются, даже если у них опасные имена (`../`, абсолютные пути).
  - `config/` и `knot-resolver` при HA-restore по-прежнему перезаписываются поверх, без отката: они не удаляются заранее, и сбой не оставляет узел без них.
  - Тесты больше не могут изменить файлы хоста: `conftest.py` отклоняет запись, удаление, переименование и распаковку в `/etc` и `/root/antizapret`. Защита появилась после того, как тест на старом коде (жёстко заданный `/etc/openvpn`) перезаписал `ca.crt` и `index.txt` рабочей PKI. Файлы восстановлены из архива `client.sh 8` от 25.09 и сверены с CA в клиентских профилях и выданными сертификатами; остальная PKI совпадала с архивом, запросов на изменение клиентов за эти две минуты не было.

#### Группа зависала в `pending`

- **Было.** Статус `pending` ставился до запуска задачи настройки группы (общий домен → Push full → проверка) или применения общего домена. Если задача падала с исключением, итоговый статус не записывался. Хватало обычного отказа проверки связи («узел недоступен») или ошибки агента при создании бэкапа на primary. То же случалось, если панель перезапускали посреди задачи. Группа оставалась в `pending` навсегда: повторная настройка и применение домена отвечали `409` «синхронизация уже выполняется», автолечение такие группы пропускало.
- **Стало.**
  - Обе задачи при любом исключении откатывают незафиксированные изменения шага, переводят группу в `failed` с текстом ошибки и завершаются ошибкой как задача.
  - Группа в `pending`, у которой задача уже не в очереди и не выполняется (или задачи нет), переводится в `failed` с ошибкой задачи, например «прервана перезапуском панели». Это делается при старте панели сразу после пометки прерванных задач и в каждом проходе воркера сверки HA-групп.

#### Одна недоступная реплика обрывала репликацию

- **Было.** Почти во всех циклах по репликам адаптер узла создавался до обработки ошибок этой реплики. Для узлов с транспортом SSH при создании адаптера поднимается туннель, при отсутствии API-ключа сразу выдаётся ошибка. Если так падала одна реплика, падала вся операция: реплики после неё не получали изменение, итоговый статус группы не записывался. Это касалось создания, удаления и перевыпуска сертификата клиента, отключения OpenVPN, копирования ключей, политик доступа, настроек AntiZapret, списков провайдеров, Push full, проверки группы и применения общего домена (второй этап).
- **Стало.**
  - Адаптер создаётся внутри обработки ошибок каждой реплики. Сбой записывается по этой реплике, цикл продолжается, итоговый статус группы отражает частичный сбой (`failed` с ошибкой первой реплики, как и раньше при частичных ошибках).
  - Push full обнуляет адаптер в начале каждой реплики: после сбоя подключения блокировки не переприменяются через адаптер предыдущей реплики, а только через адаптер той реплики, на которой был сбой, если он успел создаться.
  - Проверка группы помечает недоступную реплику расхождением `node_status` с текстом ошибки (в интерфейсе «Узел недоступен») и сверяет остальные.
  - Лишнее создание адаптера при отключении OpenVPN на репликах убрано: адаптер создаётся внутри самого отключения.

#### Перезапуск OpenVPN на репликах при операциях с клиентами

- **Было.** После каждого создания, перевыпуска сертификата или удаления OpenVPN-клиента реплика получала PKI primary и перезапускала все активные `openvpn-server@*` (при multihome — через повторное применение multihome с перезапуском). У всех клиентов на реплике обрывались соединения, при массовых операциях — на каждого клиента. На primary `client.sh` серверы не перезапускает: при удалении он делает `revoke` и `gen-crl` и отключает только этого клиента через management-сокеты.
- **Стало.**
  - Перед импортом панель читает архив PKI реплики и сравнивает CA, сертификат и ключ сервера (`antizapret-server`) с архивом primary. Серверы загружают их только при старте, поэтому перезапуск (и multihome) выполняется, только если они изменились, отсутствуют или состояние реплики прочитать не удалось.
  - `crl-verify` OpenVPN перечитывает сам при каждом новом подключении (файл читается от `nobody`, права 755/644 приходят из архива primary, как и на primary после `client.sh`).
  - Клиенты, отозванные с прошлой синхронизации и не выпущенные заново, отключаются на всех четырёх серверах (`kill` через management). Агенты до этой версии не умеют отключать по серверу — тогда используется общее отключение клиента. Если отключить не удалось, синхронизация реплики помечается неуспешной: в конфигах `reneg-sec 0`, и без отключения сессия отозванного клиента не закрылась бы.
  - Push full, применение общего домена и изменения конфигов по-прежнему перезапускают серверы: там меняется конфигурация, а не только клиенты.

#### Пул SSH-туннелей

- **Было.** Пул выдавал сохранённый туннель, не проверяя, живо ли SSH-соединение. Keepalive был выключен, поэтому обрыв без трафика не замечался вовсе. Мёртвая сессия не истекала по простою: регулярные проверки состояния узла обновляли её время использования, и все запросы к узлу шли в закрытый локальный порт до перезапуска панели. Открытие туннеля выполнялось под общей блокировкой пула: пока панель до 30 с ждала недоступный узел, запросы ко всем остальным SSH-узлам, даже через уже открытые туннели, стояли. Закрытие сессий (при очистке по простою и `drop`) тоже шло под этой блокировкой с тем же таймаутом. У `asyncssh.connect` не было `connect_timeout`, а соединение, открытие которого прервали по таймауту, не закрывалось.
- **Стало.**
  - Перед выдачей туннель проверяется (`is_closed()`); мёртвый закрывается и открывается заново. Keepalive 15 с × 3 замечает обрыв примерно за 45 с.
  - Общая блокировка защищает только словарь сессий. Открытие туннеля держит блокировку своего узла: параллельные запросы к одному узлу открывают один туннель, другие узлы не ждут.
  - Фоновая очистка (раз в 30 с) закрывает простаивающие и мёртвые сессии; запрос к узлу чужие сессии не закрывает. Закрытие идёт вне общей блокировки и ограничено 5 с.
  - Подключение ограничено `connect_timeout` (30 с); при отмене по таймауту и при остановке пула во время открытия соединение закрывается.

#### Переприменение блокировок WireGuard и AmneziaWG

- **Было.** Вернуть блокировки после синхронизации реплики, после снятия блокировки с одного клиента или при сверке политик можно было только по одному клиенту. На каждого заблокированного уходил отдельный запрос к агенту (на реплике до 30 с каждый), агент заново разбирал все конфиги интерфейсов и вызывал `wg set`/`awg set` на каждый пир. При сотнях заблокированных это сотни запросов и тысячи команд.
- **Стало.**
  - Все заблокированные клиенты уходят одним вызовом: локально или через новый эндпоинт агента `POST /clients/wireguard/runtime/block-batch` (и `/clients/amneziawg2/...`). Агент один раз читает конфиги и удаляет пиры одной командой `set` на интерфейс, до 200 пиров в команде.
  - Если команда на интерфейсе не прошла, пиры этой пачки удаляются по одному, чтобы ошибка одного пира не оставила подключёнными остальных. Результат по каждому клиенту такой же, как раньше при поштучной блокировке.
  - Агенты до этой версии отвечают `404`, и панель переходит на поштучную блокировку. Если пакетный запрос упал по другой причине (таймаут, агент недоступен), ошибка записывается каждому клиенту, и синхронизация реплики помечается неуспешной, как раньше.

### 1.5. Авторизация

#### Повторное использование refresh-токена

- **Было.** Refresh-токен менялся при каждом обновлении, но предъявление уже заменённого токена ни на что не влияло. Если cookie украли, злоумышленник и владелец могли жить параллельно. Два одновременных запроса с одним токеном получали две живые сессии.
- **Стало.**
  - У каждого входа своя «цепочка» токенов. Замена атомарная: условное обновление в БД, выигрывает ровно один запрос.
  - Если кто-то предъявляет заменённый токен, это признак кражи: вся цепочка этого входа отзывается.
  - Вкладки одного браузера делят cookie и иногда обновляются одновременно. Поэтому 30 секунд после замены старый токен ещё принимается: выдаётся access-токен без новой cookie. Работает это, только пока цепочка жива. После выхода, смены пароля или обнаруженной кражи окно не действует.
  - Токен, отозванный выходом, сменой пароля или ещё до обновления, просто получает `401` и не завершает другие сессии.
  - Неудачный refresh удаляет cookie, чтобы браузер не присылал мёртвый токен при каждом открытии страницы.

#### Смена пароля не отзывала выданные токены

- **Было.** После смены пароля старые access-токены панели и Mini App работали до истечения срока. Украденный токен переживал смену пароля.
- **Стало.**
  - У пользователя есть версия токенов. Она вшивается в access-токены и токены Mini App.
  - Любая смена пароля увеличивает версию и отзывает все refresh-токены. Это касается смены в настройках, принудительной при первом входе, администратором в карточке пользователя, через `reset-password.py` и пересоздания администратора установщиком. Все ранее выданные токены сразу получают `401`.
  - Текущая вкладка после смены пароля получает новый токен и остаётся в системе.
  - Токены, выданные до обновления (без версии), работают до первой смены пароля. Принудительного разлогина при обновлении нет.
  - Ту же проверку проходят потоки SSE (AWG2, AZ-WARP), мониторинг, документация OpenAPI и учёт активных веб-сессий. Функция, которая расшифровывала токен без проверки версии, удалена.
  - Версия увеличивается одной операцией в БД, так что две одновременные смены пароля не оставят рабочих старых токенов.

### 1.6. Nginx и Cloudflare

#### Реальный IP клиента за Cloudflare

- **Было.** Подстановка реального IP из `CF-Connecting-IP` работала только на вебхуке Telegram. Остальная панель видела адреса узлов Cloudflare. Лимиты входа и блокировки считались по ним, так что один атакующий мог заблокировать вход администратору, а аудит показывал адреса Cloudflare.
- **Стало.** Подстановка работает во всех location'ах панели и клиентского портала. Заголовок принимается только от диапазонов Cloudflare, поэтому при прямом обращении к серверу подделать IP нельзя.

#### «Доступ только через Cloudflare» (origin lock)

- **Было.** Защита была сделана списком `allow` (диапазоны Cloudflare, localhost, RFC1918) и `deny all` в тех же location'ах, где работает подстановка IP. Nginx подставляет IP раньше, чем проверяет `allow/deny`, поэтому проверялся уже адрес посетителя, и все получали `403`, включая вебхук. Мы проверили это на реальном nginx.
- **Стало.**
  - Проверяется адрес самого TCP-соединения, до подстановки: `geo` в `conf.d/adminpanelaz-cloudflare-origin.conf`, который генерируется из того же allow-списка.
  - Location'ы подключают короткую проверку «соединение не от Cloudflare → 403».
  - Автообновление списков IP Cloudflare перегенерирует `geo` и откатывает все файлы, если `nginx -t` или reload не прошли.

#### `nginx-repair` удалял vhost портала

- **Было.** Скрипт искал vhost'ы панели по `server_name` регулярным выражением с границей слова. Точка тоже считается границей, поэтому под поиск попадали `portal.<домен>` и другие поддомены. `nginx-repair` удалял их, в том числе при каждом переключении Cloudflare proxy-mode в настройках. 19.09 так пропали портал и `test.claymore-dev.com`, 26.09 снова портал (восстановлен из бэкапа).
- **Стало.** Совпадает только точное имя в `server_name`. Закомментированные строки не учитываются, а точка в домене не означает «любой символ».

#### Флаги Cloudflare при ручном запуске скриптов

- **Было.** Флаги proxy-mode и origin lock скрипты nginx читали только из переменных окружения. Панель их выставляет, а при ручном `nginx-repair` или установке origin lock молча выключался, хотя в настройках (БД и `.env`) был включён. Поэтому на рабочем сервере он не действовал.
- **Стало.** Если переменная не передана, значение берётся из `.env`. Явно переданное значение по-прежнему важнее.

#### Панель открывалась по IP сервера

- **Было.** `nginx_install_site` удалял `sites-enabled/default`, а своего сервера по умолчанию не ставил. Nginx отдаёт запрос с неизвестным `Host` (в том числе голый IP) первому vhost'у на порту, то есть панели: `http://IP` редиректил на `https://IP`, и после предупреждения браузера о сертификате открывалась панель.
- **Стало.**
  - Вместе с vhost панели (установка, `nginx-repair.sh`, переключение Cloudflare proxy-mode, portal) ставится `sites-available/00-adminpanelaz-default-deny` на те же порты: HTTP — `return 444`, HTTPS — `ssl_reject_handshake on` на nginx ≥ 1.19.4, на старом nginx — свой самоподписанный сертификат (`/etc/ssl/…/adminpanelaz-default-deny.*`, ключ `600`) и `return 444`.
  - Сервер по умолчанию ставится только туда, где без него по IP отвечала бы панель: на порт, где первым vhost'ом идёт панель или портал. Порядок берётся из `nginx -T`, без него — как в `nginx.conf` Debian: `conf.d`, затем `sites-enabled`. Если первым идёт чужой сайт или на порту уже есть любой `default_server`, порт не трогается, и поведение чужих сайтов не меняется.
  - Порты собираются со всех vhost панели и портала сразу, поэтому установка портала не затирает порты панели. Адрес и IPv6 из `listen` панели повторяются в сервере по умолчанию.
  - Если в `server_name` панели IP-адрес (публикация без домена), HTTPS-порт не закрывается. Клиент, подключаясь по IP, не передаёт SNI, и `ssl_reject_handshake` отклонял бы саму панель.
  - У файла своя проверка записи и `nginx -t`: при ошибке откатывается только он, публикация панели не падает.
  - При переходе на прямую публикацию файл удаляется и nginx перезагружается без него, иначе он занял бы HTTPS-порт uvicorn. Подсчёт «других сайтов» перед остановкой nginx теперь читает настраиваемый каталог сайтов, а не жёстко `/etc/nginx/sites-enabled`. `uninstall.sh` удаляет файл и сертификат.
  - Shell-тест проверяет выбор портов, чужие `default_server` и порядок загрузки сайтов, IP-режим, объединение портов панели и портала, откат и прямую публикацию на подменённом nginx. При наличии nginx он ставит default-deny по живому серверу во временном каталоге: голый IP отклоняется по HTTP и HTTPS, домен панели отвечает, а панель с IP в `server_name` открывается.
  - Чтобы закрыть доступ по IP на уже опубликованной панели, нужно перегенерировать nginx (часть 3).

#### NAT порта 80 во время certbot standalone

- **Было.** Перед certbot standalone установщик снимал правила NAT для порта 80 внешнего интерфейса, но перед этим сохранял полный снимок `iptables-save` и после certbot возвращал его целиком через `iptables-restore`. Это откатывало все таблицы, в том числе правила, которые за время certbot добавили fail2ban, VPN или docker. Ошибки восстановления глушились. Если установку прерывали во время certbot, правила не возвращались вовсе. Отбор правил шёл по подстроке: `eth0` совпадал с `eth01`, `--dport 80` с `--dport 8080`.
- **Стало.**
  - Снимаются только правила `nat PREROUTING` с точным совпадением интерфейса по умолчанию, `-p tcp` и `--dport 80`, и возвращаются только они, одной транзакцией `iptables-restore --noflush`, на прежние позиции. Остальные правила, в том числе появившиеся за время certbot, не трогаются. Правило, которое кто-то уже вернул сам, не дублируется.
  - Правила возвращаются и при прерывании: общая обёртка `nginx_certbot_standalone` ставит EXIT-trap (bash выполняет его и при SIGINT/SIGTERM), затем выполняет прежний trap и восстанавливает его.
  - nginx обёртка останавливает сама, уже под этим trap'ом. Если установку прервали во время certbot или ожидания освобождения порта, nginx, остановленный для certbot, запускается обратно. Nginx, который до этого не работал, не запускается.
  - Если вернуть правила не удалось, установщик выводит готовые команды `iptables -t nat -A PREROUTING …` для ручного восстановления.
  - Shell-тест с подменёнными `iptables`/`iptables-restore` проверяет отбор правил, порядок, одновременные изменения цепочки, сбой и прерывание certbot, сохранность прежнего trap. При запуске от root он дополнительно проверяет настоящий iptables в отдельном сетевом namespace, не трогая файрвол сервера.

### 1.7. Установщик

- **SIGPIPE при выборе Python.** Установщик мог завершиться с кодом 141 ещё до появления меню: `head -n1` в конвейере с `pipefail` обрывал канал. Заменено на чтение первой строки без обрыва канала ([PR #14](https://github.com/Kirito0098/AdminPanelAZ/pull/14)).

#### API-ключи агентов в unit-файлах systemd

- **Было.** Установщик подставлял `NODE_AGENT_API_KEY` и `PROXY_AGENT_API_KEY` в строку `Environment=` unit-файлов `adminpanelaz-node.service` и `adminpanelaz-proxy.service`. Unit-файлы лежат в `/etc/systemd/system` с правами `644`, а переменные `Environment=` любой пользователь видит и через `systemctl show`. С ключом можно управлять агентом узла. При этом агент брал ключ из `node_agent.env` (`EnvironmentFile=` в systemd перекрывает `Environment=`), поэтому после ротации в unit-файле оставался старый ключ.
- **Стало.**
  - Ключа в шаблонах unit'ов больше нет. Установка unit'а записывает ключ в `backend/node_agent.env` / `proxy_agent.env` с правами `600` (общая функция в `scripts/lib-agent-key.sh`), и только если там его нет или стоит плейсхолдер. Ключ, сменённый ротацией, не затирается.
  - `refresh-systemd-units.sh`, который вызывается при обновлении панели и агента, берёт ключ из старого unit'а, переносит его в env-файл и переустанавливает unit без ключа.
  - Unit с `AGENT_API_KEY=` считается устаревшим: при старте панели, node agent и proxy agent он переустанавливается из шаблона, даже если обновление шло вручную (`git pull` и перезапуск). Обновление через интерфейс переустанавливает и unit proxy agent, в том числе на серверах только с прокси.
  - `lib-agent-key.sh` сохраняет symlink на env-файл, узнаёт те же плейсхолдеры, что `install.sh`, и не перезаписывает файл, если его не удалось прочитать. Временный файл называется `.tmp_*` и игнорируется git.
  - Ключ, лежавший в unit'е, мог прочитать любой локальный пользователь, поэтому после обновления его нужно сменить (см. часть 3).
  - Скрипты установки unit'ов принимают `SYSTEMD_UNIT_DIR`. Shell-тест ставит unit'ы во временный каталог с подменёнными `id` и `systemctl` и отказывается запускаться, если скрипт эту переменную не поддерживает.

#### Firewall при смене режима публикации

- **Было.** В режимах `http_direct` и `uvicorn_*` порт панели открывался правилом `iptables -A … -j ACCEPT` (или `ufw allow`), в режимах `nginx_*` закрывался правилом `DROP` (`ufw deny`), тоже дописанным в конец. Правило прежнего режима никто не удалял. После перехода на Nginx старый `ACCEPT` стоял выше и срабатывал первым, так что `IP:8000` оставался открыт; при обратном переходе старый `DROP` закрывал панель снаружи. То же при переустановке `install.sh` в другом режиме (там порт открывается веткой HTTPS).
- **Стало.**
  - Открытие порта (`firewall_iptables_open_port`, `firewall_ufw_open_port`) сначала удаляет все `DROP` для этого порта, закрытие — все `ACCEPT`, затем добавляет своё правило, если его ещё нет.
  - Для ufw правило удаляется по описанию (`ufw delete allow|deny <порт>/tcp`): так снимается и пара `(v6)`, и это работает на неактивном ufw, где `ufw status numbered` пуст. Удаляются только правила «со всех адресов»: разрешения с IP панели для агентов не трогаются.
  - Shell-тест с поддельными `iptables` и `ufw` (shell-функции, настоящий файрвол тест изменить не может) проверяет обе стороны перехода, переустановку, повтор, дубли и сохранность чужих правил.

#### Права каталога бэкапов

- **Было.** Архивы бэкапов создавались по umask: файлы `644`, каталог `BACKUP_ROOT` `755` (так было и на рабочем сервере). В архивах лежат БД панели и `.env`, поэтому их мог прочитать любой локальный пользователь.
- **Стало.**
  - `BackupManager` делает каталог `700`. Архив, его метаданные и временные файлы создаются сразу с `600` (`os.open` с режимом, без окна с `644`). Загруженный с компьютера архив после переноса тоже получает `600`.
  - При старте панели `restrict_backup_dir_permissions` закрывает каталог и уже лежащие архивы `adminpanelaz_*` вместе с их `.json`. Посторонние файлы в каталоге не трогаются.

#### Неатомарная запись `.env`

- **Было.** `EnvFileService` (все сохранения настроек панели, включая Cloudflare, публикацию и ротацию секретов), запись настроек mTLS в `node_agent.env` и сохранение ротированного ключа агента перезаписывали файл на месте через `write_text`. Сбой или нехватка места посреди записи оставляли обрезанный файл, и панель или агент не поднимались.
- **Стало.**
  - Общий `app/services/atomic_file.py`: запись во временный файл в том же каталоге (`600`), `fsync`, `os.replace`, `fsync` каталога. При ошибке временный файл удаляется, прежний остаётся нетронутым. Symlink на `.env` сохраняется, обновляется целевой файл.
  - Им же пользуются восстановление бэкапа (раньше там была своя копия без `fsync` каталога) и метаданные бэкапов.
  - Временный файл называется `.tmp_*` и игнорируется git: остаток после сбоя с секретами внутри не попадёт в коммит и не помешает `git pull` на узле.
  - Если сбоит только `fsync` каталога после `rename`, это пишется в журнал, а не возвращается ошибкой: новые данные уже на месте.
  - `EnvFileService` читает и пишет `.env` под `flock` (`.env.lock`), поэтому воркеры, одновременно сохраняющие разные ключи, не теряют изменения друг друга.
  - Агент создаёт `node_agent.env`, если его нет: ключа в unit'е больше нет, и без файла ротированный ключ пропал бы после перезапуска.
  - Найдено попутно: `test_cloudflare_proxy_api` при каждом полном прогоне писал `CLOUDFLARE_IPS_AUTO_UPDATE=true` в рабочий `backend/.env` (значение совпало с настройкой в БД, вреда не было). Тест исправлен, а `tests/conftest.py` теперь роняет любой тест, который пишет в `backend/.env`, `node_agent.env` или `proxy_agent.env`.
#### Повторная установка агента

- **Было.** `setup_node_env` и `setup_proxy_env` пересоздавали `node_agent.env` / `proxy_agent.env` из примера и генерировали новый ключ, если его не передали явно; мастер тоже по умолчанию предлагал сгенерировать ключ. Настройки mTLS из файла пропадали. `install.sh --reinstall` вызывал `uninstall.sh --remove-system-config`, который удалял `/etc/adminpanelaz/mtls`. После любой из этих операций панель не могла достучаться до узла, пока его не перепривяжут вручную.
- **Стало.**
  - Перед пересозданием env-файла установщик забирает из него ключ (если это не плейсхолдер) и строки mTLS. Явно переданный ключ (`NODE_AGENT_API_KEY=…` или ввод в мастере) по-прежнему важнее.
  - mTLS переносится, только если сертификат агента подписан указанным CA, не истёк и соответствует ключу (`openssl verify` и сравнение открытых ключей). Иначе ключ сохраняется, mTLS выключается, а установщик предупреждает, что узел нужно перепривязать.
  - Если на сервере уже есть настоящий ключ, мастер первым вопросом предлагает оставить его (по умолчанию «да»).
  - `uninstall.sh` получил флаг `--keep-agent-pki`, и `--reinstall` его передаёт: `/etc/adminpanelaz/mtls` остаётся, остальная системная конфигурация удаляется как раньше. Обычное удаление с `--remove-system-config` по-прежнему убирает и PKI.
  - Shell-тест с настоящими сертификатами из временного CA проверяет перенос ключа и mTLS, чужой CA, неподходящий ключ, отсутствующий и истёкший сертификат, плейсхолдер, прокси, вопросы мастера и флаги переустановки.
#### Firewall и SSH, nginx и чужие сайты

- **Было.**
  - С включённым в мастере ufw установщик сначала выполнял `ufw --force enable` (входящие по умолчанию запрещены), а разрешающие правила добавлял потом. Правила для SSH не было вовсе: если ufw до этого не был настроен, после установки на сервер нельзя было войти по SSH, а порт панели открывался уже после включения.
  - Порт backend, node agent или proxy agent мог совпасть с портом SSH, и правило `DROP`/`deny` закрывало SSH.
  - `uninstall.sh` искал правила панели в `ufw status numbered` по шаблону `[N]` и пропускал номера 1–9 (ufw выводит `[ 1]`), а на неактивном ufw не находил ничего.
  - Перед остановкой nginx при переходе на прямую публикацию чужие сайты искались только в `sites-enabled`. Сайт в `conf.d` или в другом include не замечался, и nginx останавливался вместе с ним.
- **Стало.**
  - Порты SSH определяются по текущей сессии (`SSH_CONNECTION`), `sshd -T`, слушающим сокетам (`ss`) и активному `ssh.socket` (при socket-активации, по умолчанию в Ubuntu 22.10+, порт слушает systemd, и в `ss` процесса sshd не видно), без данных — 22. Если правило закрыло бы один из них, настройка firewall отказывается и объясняет почему.
  - Если ufw не активен, SSH разрешается заранее, а ufw включается последним, после всех правил панели. Своё правило SSH пользователя (например, только со своего IP) не расширяется, на активном ufw SSH не трогается.
  - `uninstall.sh` берёт правила панели из `ufw show added` (видно и на неактивном ufw) и удаляет их по описанию вместе с `(v6)`. Правило SSH, добавленное панелью, остаётся: иначе активный ufw после удаления закрыл бы SSH, а повторная установка, увидев активный ufw, его не вернула бы.
  - Чужие сайты nginx ищутся по полному списку файлов из `nginx -T` (без него — `sites-enabled` и `conf.d`): считается любой файл с блоком `server`, кроме файлов панели и стандартных заглушек `default` и `conf.d/default.conf` (пакет nginx.org). vhost панели удаляется всегда, nginx останавливается, только если чужих сайтов нет.
  - Три shell-теста с подменёнными `ufw`, `iptables`, `sshd`, `ss`, `nginx` и `systemctl` проверяют определение портов SSH, отказ закрыть SSH, порядок правил при включении ufw, сохранность правил SSH пользователя, связку uninstall + install на активном и неактивном ufw и подсчёт чужих сайтов (`conf.d`, include без `listen`, закомментированные блоки, `upstream`, файлы панели).

#### Пароль администратора в мастере с `-y`

- **Было.** По умолчанию мастер держал `WIZ_ADMIN_PASSWORD=admin`, и с `-y` этот пароль уходил в `DEFAULT_ADMIN_PASSWORD`. В production панель отказывается стартовать со слабым паролем, и установка падала. Итог установки при незаданном пароле тоже показывал `admin`. Случайный пароль (`random_hex | cut -c1-16`) изредка состоял из одних цифр и не проходил политику «буквы и цифры».
- **Стало.**
  - С `-y` мастер генерирует случайный пароль и показывает его сразу и в конце установки. Надёжный пароль из `WIZ_ADMIN_PASSWORD` сохраняется, слабый заменяется с предупреждением.
  - Интерактивный ввод отклоняет пароль, который панель не примет: короче 8 символов, без букв или цифр, совпадающий с логином.
  - Генератор повторяет попытку, пока в пароле не окажутся и буквы, и цифры.
  - Пустой пароль мастера (установка только узла или прокси) не затирает `DEFAULT_ADMIN_PASSWORD`, а итог установки в этом случае пишет, что пароль не менялся.
  - Установка с `WIZ_*` из окружения без мастера падала на `set -u`, если `WIZ_ADMIN_PASSWORD` не задан. Теперь слабый пароль из `WIZ_ADMIN_PASSWORD` или `.env` заменяется, а без пароля он генерируется только для новой БД. Если БД уже есть, пароль не пишется: `seed-admin-user.py --bootstrap` с пустым паролем оставляет пароль существующего администратора.

#### Обновление из меню, CI и версия Node.js

- **Было.**
  - `adminpanel-menu.sh --update` (пункт меню «Проверить обновления») делал `git pull`, `pip install` и обновлял unit'ы, но не пересобирал интерфейс, в отличие от обновления из панели. После перезапуска новый backend работал со старым собранным фронтендом.
  - Shell-тесты `test-nginx-portal-hardening.sh` и `test-nginx-portal-readiness.sh` не запускались в CI. Оба по умолчанию подключали библиотеку к рабочему `backend/.env`.
  - Установщик принимал Node.js 20+ и ставил 20.x из NodeSource; CI собирал фронтенд на Node 20. Node 20 больше не получает обновлений безопасности.
- **Стало.**
  - Обновление из меню после `pip install` выполняет `npm ci` и `npm run build:all`, если интерфейс на этом сервере уже собирали (есть `frontend/dist`; на сервере только с агентом шаг пропускается). Если сборка не удалась или npm не найден, команда завершается с ошибкой и выводит команды для ручной пересборки: повторный `--update` сборку уже не запустит, потому что код обновлён.
  - Все shell-тесты подключены к CI, portal-тесты работают со временным `.env`.
  - Установщик требует Node.js 22+ и по умолчанию ставит 24.x (Active LTS). Кандидат из apt принимается, только если его мажорная версия не ниже 22 (раньше версия проверялась регуляркой по `apt-cache show`). Пакет `npm` из apt ставится, только если его нет после `nodejs`: в сборке NodeSource он уже есть, и пакет Debian с ней конфликтует. Зависимости интерфейса и установщик, и меню ставят через `npm ci`, строго по `package-lock.json`. `frontend/package.json` объявляет `engines.node >=22`. CI собирает и тестирует фронтенд на Node 22 и 24.
  - Shell-тесты: обновление из меню на временных git-репозиториях с подменённым `npm` (сборка в нужном каталоге и порядке, пропуск без `frontend/dist` и без обновлений, сбой `npm ci` или сборки, отсутствие npm) и выбор версии Node (поддерживаемая версия не трогается, Node 20 обновляется через NodeSource 24.x, apt принимается с 22+, в том числе с epoch, отказ при старой версии после установки).

### 1.8. Надёжность бэкенда

#### Восстановление бэкапа поверх рабочей базы

- **Было.** БД панели, БД CIDR и `.env` из архива записывались прямо поверх рабочих файлов, без проверки. Повреждённая или обрезанная база в архиве затирала рабочую, и панель не поднималась. Копии прежних файлов не оставалось. Запись шла на месте: сбой посередине оставлял наполовину записанный файл или смесь старых и новых файлов. Файлы получали права по umask (`644`).
- **Стало.**
  - БД из архива проверяется до любых изменений: заголовок SQLite и `PRAGMA integrity_check`. Битая база отклоняется с `400`, и ни рабочие файлы, ни узлы не трогаются.
  - Перед заменой текущие БД и `.env` копируются в `<каталог бэкапов>/.pre-restore/<время>/` (каталог `700`, файлы `600`, хранятся 3 последние копии). БД копируется через online backup SQLite, поэтому данные из WAL тоже попадают в копию.
  - Каждый файл пишется во временный файл рядом и подменяется атомарным `rename` с правами `600`. Старые WAL/SHM удаляются, чтобы SQLite не применил их к новой базе.
  - Если запись одного из файлов не удалась, уже заменённые возвращаются из копии. Сбой отката пишется в лог с путём к копии.
  - Если на диске не хватает места на копию и новые файлы, восстановление отклоняется (`507`) ещё до изменений на узлах.
  - Копии видны в «Настройки → Резервные копии → Копии перед восстановлением»: дата, размер, состав и общий объём (три копии рабочей базы занимают около 1 ГБ). Копию можно удалить или откатиться к ней. Откат возвращает только базу, CIDR и `.env`, узлы не трогает. Перед откатом текущее состояние тоже сохраняется как копия, поэтому откат можно отменить.
  - На время замены фоновые задачи приостанавливаются во всех воркерах. Каждый шаг фонового цикла держит разделяемый `flock` на `<БД>.bg-gate.lock`. Восстановление сначала берёт `<БД>.bg-intent.lock`, после чего новые шаги пропускаются, затем ждёт текущие (до 30 секунд) и держит обе блокировки до перезапуска панели: ядро снимает их вместе с процессом. Если шаг не успел завершиться, восстановление отклоняется (`409`) до изменений на узлах и в файлах. При сбое восстановления пауза снимается сразу. Задачи, запущенные из интерфейса (пул `bg-task`), и обработка обновлений Telegram-бота не приостанавливаются: их запускает сам администратор, а перезапуск после восстановления их прерывает.

#### Миграции с пересозданием таблиц

- **Было.** Миграции были обёрнуты в транзакцию SQLAlchemy, но драйвер SQLite не открывает транзакцию перед `CREATE`/`DROP`/`ALTER` и коммитит их сразу. Откатывались только вставки данных. Если панель падала посреди «создать `<таблица>_new` → скопировать → удалить старую → переименовать», в базе оставалась `<таблица>_new`, и следующий старт падал с «table already exists». Мы воспроизвели это в тесте. Политики OpenVPN и WireGuard переносились двумя шагами, а проверка смотрела только на OpenVPN, поэтому после сбоя между ними WireGuard не переносился никогда. Каждый воркер uvicorn запускал миграции одновременно с остальными.
- **Стало.**
  - Каждая миграция идёт в одной настоящей транзакции (`BEGIN IMMEDIATE … COMMIT`), DDL тоже откатывается.
  - Пересоздание таблицы перепроверяет состояние уже внутри транзакции и удаляет остаток `_new` от прежнего сбоя. Политики OpenVPN и WireGuard проверяются по отдельности.
  - Воркеры выполняют всю подготовку БД при старте (создание таблиц, миграции панели и CIDR, начальное заполнение) по очереди под файловой блокировкой `adminpanel.db.migrate.lock` (права `600`). Ожидание блокировки пишется в лог.
  - Проверено на копии рабочей базы: схема не меняется, миграции занимают около 0,5 с.

#### Рост истории VPN-сессий и refresh-токенов

- **Было.** Ночная чистка удаляла старые сэмплы трафика, метрики и журнал, но не историю сессий и не refresh-токены. Каждое переподключение OpenVPN создаёт новую запись сессии: на рабочем сервере за 7 недель набралось 138 тыс. завершённых сессий на 47 конфигов (около 2,2 тыс. в день). Сборщик трафика каждую минуту загружал в память все сессии узла, поэтому нагрузка росла вместе с таблицей. Refresh-токены тоже только копились.
- **Стало.**
  - Ночная чистка удаляет завершённые сессии старше 30 дней. Срок настраивается: Настройки → Обслуживание VPN → «Хранение и карта» → «Сессии VPN, дн.» (`TRAFFIC_SESSION_RETENTION_DAYS`). Активные сессии не удаляются.
  - Сборщик и пересчёт базы сессий загружают только активные сессии (по частичному индексу) и сессии из текущего снимка. На рабочей базе это 2 мс вместо примерно 0,9 с каждую минуту. Вернувшийся клиент WireGuard по-прежнему продолжает свою прежнюю запись, если вернулся в пределах срока хранения.
  - Видимые последствия: в карточке клиента число сессий и источников считается за срок хранения. Файл БД после чистки сам не уменьшается, SQLite переиспользует освободившееся место.
  - Refresh-токены, истёкшие больше 7 дней назад, удаляются: истёкший токен и так не принимается.

#### Автоматическая ротация ключей узлов

- **Было.** Цикл выбирал узлы по `nodes.updated_at <= сейчас − NODE_API_KEY_ROTATION_DAYS`, но `updated_at` обновляется при каждой проверке состояния узла (на рабочем сервере он совпадает с `last_seen_at`). Поэтому ключ удалённого узла при включённой ротации не менялся никогда. Исключение вне обработки одного узла (например, ошибка БД при выборке) тихо завершало задачу до перезапуска панели. HTTP-вызовы агентов (таймаут 30 с на узел) шли прямо в event loop. Прокси-узлы попадали в выборку, хотя у них нет API ротации.
- **Стало.**
  - Возраст ключа хранится в отдельной колонке `nodes.api_key_rotated_at`. Её обновляют автоматическая и ручная ротация, а также замена ключа в карточке узла. Для существующих узлов отсчёт идёт от даты добавления.
  - Ошибка итерации пишется в лог, и цикл продолжает работу. Ротация выполняется в пуле потоков.
  - Прокси-узлы исключены из выборки, ручная ротация для них отклоняется до обращения к агенту.
  - На рабочем сервере ротация выключена (`NODE_API_KEY_ROTATION_DAYS=0` по умолчанию), обновление ключи не меняет. Если её включить, узел «2 serv» (добавлен 13.09) получит новый ключ на первой проверке после наступления срока.

#### Фоновые задачи при нескольких воркерах

- **Было.** При `UVICORN_WORKERS>1` каждый воркер запускал все планировщики: сбор трафика, бэкапы, напоминания, истечение доступа, доставку вебхуков, монитор ресурсов. Задачи выполнялись по несколько раз. Каждый воркер при старте синхронизировал firewall и помечал все незавершённые задачи как прерванные. Поэтому воркер, перезапущенный вместо упавшего, «прерывал» задачи, которые ещё шли в соседних воркерах. Запланированная перезагрузка сервера жила в памяти принявшего её воркера: отмена, попавшая в другой воркер, отвечала «не найдена», и сервер перезагружался.
- **Стало.**
  - Фоновые задачи и монитор ресурсов запускает один воркер-лидер, который держит `flock` на `adminpanel.db.leader.lock` (права `600`). Остальные воркеры раз в 15 с пробуют взять блокировку. Если лидер упал или остановился, задачи подхватывает другой воркер. Ядро снимает блокировку и при аварийном завершении процесса.
  - Одноразовые действия старта (синхронизация firewall, миграция unit'ов systemd и старых списков CIDR, пометка прерванных задач и перезагрузок) выполняет только лидер при старте панели. Воркер, подхвативший лидерство позже, их пропускает: соседние воркеры в это время ещё работают.
  - Перезагрузка хранится в таблице `server_reboot_requests`, таймер остаётся в запланировавшем воркере. Перед выполнением таймер атомарно переводит запись из `pending` в `executing`, поэтому отмена из любого воркера успевает сработать. Дубль для узла отсекается уникальным частичным индексом. У записи есть владелец — процесс воркера (PID и время старта из `/proc`, чтобы повторно выданный PID не считался тем же процессом). Прерванными помечаются записи завершившихся воркеров и записи `pending`, просроченные больше чем на 2 минуты. Записи работающих воркеров не трогаются, даже если лидером при старте стал воркер, перезапущенный вместо упавшего.
  - Фоновые задачи получили такого же владельца. При старте прерванными помечаются только задачи завершившихся воркеров.
  - Пошаговые диалоги Telegram-бота (ввод значений настроек, создание unlock-кодов) и состояние входа через Telegram OIDC (PKCE, `redirect_uri`) хранились в памяти воркера. Следующее сообщение или callback, попавшие в другой воркер, диалог не продолжали, вход завершался ошибкой «сессия истекла». Теперь это состояние лежит в таблице `shared_state` БД панели со сроком жизни: диалог 1 час, вход 10 минут. Истёкшие записи удаляются при следующей записи. Состояние OIDC забирается атомарным `DELETE … RETURNING`, поэтому один `state` нельзя использовать дважды. Без настройки из lifespan (тесты, скрипты) состояние остаётся в памяти процесса.

#### Проверка лимитов трафика

- **Было.** Расход клиента за период (сутки, неделя, месяц) считался так: сначала `SELECT DISTINCT common_name` по всем сэмплам узла, чтобы найти варианты написания имени, затем загрузка каждого сэмпла клиента за период в память и суммирование в Python. На рабочем сервере в `user_traffic_sample` 1,1 млн строк, у самых активных клиентов 70–115 тыс. сэмплов. Одна проверка месячного лимита занимала около 1,1 с. У клиента OpenVPN их три (всего, UDP, TCP), и они повторяются при каждом пересчёте политики и открытии карточки.
- **Стало.**
  - Варианты имени берутся из таблицы итогов `user_traffic_stat_protocol` (48 строк). Коллектор пишет итог и сэмпл под одним и тем же именем, чистка трафика удаляет их вместе, а ночная чистка удаляет только старые сэмплы. Поэтому имена в итогах — надмножество имён в сэмплах (на рабочей базе расхождений 0).
  - Сумма считается одним запросом `SUM` по новому индексу `(common_name, created_at)`. Условие по узлу записано как `node_id + 0`, иначе SQLite выбирает индекс `(node_id, created_at)` и проходит сэмплы всех клиентов узла за период.
  - Прежний индекс по одному `common_name` удалён: новый начинается с того же столбца.
  - На копии рабочей базы: 37–50 мс вместо 1,1 с, результаты совпадают с прежним расчётом во всех 48 проверенных комбинациях (клиент, период, протоколы). Миграция индекса занимает около 1 с.
  - Агрегаты по часам не понадобились: при таком времени запроса они только усложнили бы сбор и чистку.

#### Блокировка event loop

- **Было.** Панель работает в одном event loop на воркер. Синхронная работа внутри `async`-кода останавливает все запросы, пока не закончится. Так работали:
  - фоновые циклы автобэкапа (архив БД около 300 МБ и отправка в Telegram), ночного обновления CIDR (загрузки, минуты), обновления IP Cloudflare, синхронизации сертификатов с узлов и напоминаний пользователям;
  - живой поток мониторинга (опрос агентов каждые несколько секунд) и WebSocket монитора сервера (замер трафика интерфейса спит 0,35 с на каждом тике);
  - потоки установки AZ-AWG2 и обновления AZ-WARP (ожидание каждой строки от агента);
  - `async`-эндпоинты восстановления AZ-AWG2, загрузки бэкапа с восстановлением и импорта CSV;
  - обработка обновлений Telegram-бота (БД, агенты узлов, бэкапы, отправка файлов).
- **Стало.**
  - Циклы вызывают тело итерации через `asyncio.to_thread`.
  - SSE-потоки читают синхронный генератор по шагу в отдельном потоке (`iterate_in_thread`) и закрывают его, когда страница закрыта. Закрытие встаёт в очередь за незавершённым чтением, а не выполняется параллельно с ним. Мониторинг и WebSocket собирают данные в пуле потоков.
  - Эндпоинты загрузки стали обычными синхронными маршрутами: FastAPI выполняет их в пуле потоков.
  - Обновления бота обрабатываются в отдельном потоке `telegram-bot` с постоянным event loop. HTTP-клиент бота привязан к этому loop. Обработчик открывает свою сессию БД: сессия запроса закрывается, когда Telegram обрывает запрос, а бот ещё работает. Команды бота идут по очереди друг за другом, панель при этом отвечает. Если Telegram оборвёт долгий запрос вебхука, начатое действие доводится до конца.
  - Запросы к БД в middleware проверки IP-ограничений и активной сессии тоже вынесены из event loop, см. «Остатки P3 надёжности бэкенда».


#### Остатки P3 надёжности бэкенда

- **Записи о перезагрузках сервера.** Строки `server_reboot_requests` не удалялись. Теперь ночная чистка удаляет завершённые записи (выполнена, отменена, прервана, ошибка) старше 30 дней. Запланированные и выполняемые перезагрузки не трогаются.
- **Приватный `_is_vpn_node`.** Функцию из `node_manager` импортировали больше двадцати модулей, в том числе `node_key_rotation`, то есть она давно стала общей. Переименована в `is_vpn_node`, поведение не менялось.
- **Гонка таймера перезагрузки и отмены.** Теста не было. Добавлены три: отмена успевает между срабатыванием таймера и сменой статуса, таймер успевает между проверкой и сменой статуса в отмене, и 30 одновременных срабатываний с отменой. Во всех случаях победитель ровно один: либо перезагрузка отменена и не выполнялась, либо выполнена один раз, а отмена вернула «уже нельзя отменить». Код менять не пришлось: обе стороны меняют статус условным `UPDATE … WHERE status = 'pending'`.
- **Общий пул потоков.** Все фоновые циклы уходили в пул `asyncio.to_thread` по умолчанию (7 потоков на 3 CPU), и многоминутный автобэкап, обновление CIDR или чистка ретенции занимали потоки, которые нужны мониторингу каждые несколько секунд. Теперь автобэкап, чистка runtime-бэкапов CIDR, плановое обновление CIDR и ночная ретенция идут в отдельный пул `long-task` из трёх потоков (`run_long_task`, копирует contextvars, как `to_thread`). Короткие циклы мониторинга остались в общем пуле, задачи из интерфейса — в своём пуле `bg-task`.
- **Запросы к БД в middleware.** Проверка IP-ограничений и обновление активной сессии открывали сессию SQLAlchemy и ходили в SQLite прямо в event loop, на каждый запрос. Теперь эта работа идёт через `run_in_threadpool` (пул anyio, в котором FastAPI выполняет синхронные маршруты), а в event loop остаётся только формирование ответа. Поведение не изменилось: жёсткий отказ, отказ с записью попытки, редирект на `/ip-blocked` для страниц.

## Часть 3. Что сделать после обновления (эксплуатация)

1. **Перезапустить node agent на удалённых узлах**: исправление путей к файлам и безопасный импорт PKI и профилей на репликах работают только в новом агенте. Со старым агентом отозванный OpenVPN-клиент на реплике отключается общей командой, которая закрывает его сессию только на одном сервере, а блокировки WireGuard и AmneziaWG возвращаются по одному клиенту (медленнее, но работает).
2. **Перегенерировать nginx** (`scripts/nginx-repair.sh` или переключение proxy-mode в настройках), чтобы включились реальный IP и новый origin lock. На claymore-dev.com уже сделано 26.09.
3. **Сменить `SECRET_KEY`**, если панель когда-либо была опубликована напрямую (uvicorn на `0.0.0.0` без nginx).
4. **Проверить, что узлы и скрипты не обращаются к панели напрямую по IP**: с включённым origin lock такие запросы получают `403`. Работать нужно через домен за Cloudflare, localhost или VPN-сети RFC1918.
5. После обновления все, кто залогинен через токены старого формата, остаются в системе до первой смены пароля. Чтобы завершить старые сессии сразу, достаточно сменить пароль.
6. **Сменить API-ключи агентов.** До этого обновления ключ лежал в unit-файле systemd, который мог прочитать любой локальный пользователь узла. Для node agent достаточно ротации ключа в карточке узла. Для proxy agent ротации нет: сгенерировать ключ (`openssl rand -hex 32`), записать его в `backend/proxy_agent.env` на прокси, перезапустить `adminpanelaz-proxy` и заменить ключ в карточке узла.
7. **Перегенерировать nginx на опубликованных панелях** (`scripts/nginx-repair.sh` или переключение proxy-mode), чтобы появился сервер по умолчанию и панель перестала открываться по IP сервера. Если на сервере есть чужой `default_server` или по IP отвечает чужой сайт, скрипт его не трогает.
8. **Обновить Node.js до 22+** на уже установленных панелях: сам по себе он не обновляется. Повторный `install.sh` поставит 24.x, вручную: `curl -fsSL https://deb.nodesource.com/setup_24.x | sudo bash - && sudo apt-get install -y nodejs`, затем пересобрать интерфейс (`cd frontend && npm ci && npm run build:all`). На claymore-dev.com сейчас Node 20.20.2.
