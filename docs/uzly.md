# Узлы (VPN-серверы)

## Зачем эта страница

Если у вас **несколько VPN-серверов**, здесь их добавляют, проверяют связь и выбирают, с каким сервером работать. Одна панель может управлять несколькими серверами.

## Кто может пользоваться

Только **администратор**.

## Как открыть

Боковое меню → **Узлы**.  
Также активный узел можно переключить в **шапке** панели — это влияет на все остальные разделы.

---

## Основные понятия

| Термин | Простыми словами |
|--------|------------------|
| **Узел** | Один VPN-сервер с AntiZapret |
| **Активный узел** | Сервер, с которым вы работаете прямо сейчас (конфиги, синхронизация) |
| **Локальный узел** | AntiZapret на том же сервере, где стоит панель |
| **Удалённый узел** | Отдельный VPN-сервер, подключённый к панели по сети |
| **Прокси-узел** | Отдельный RU VPS с AntiZapret `proxy.sh` + агент панели (`proxy_agent`). Это **не** VPN-сервер и **не** список адресов OpenVPN |

> Один и тот же логин клиента на **разных** серверах — это **разные** записи. Это не один профиль на двух серверах.

### Прокси-узлы и «несколько адресов» OpenVPN — разные вещи

| Что | Где | Зачем |
|-----|-----|--------|
| **Несколько адресов OpenVPN** | **Конфиг AntiZapret → OpenVPN (панель)** или **Прокси** (меню «Сеть») на **VPN-узле** | Несколько `remote` в `.ovpn` (IP/домены одного VPN) |
| **Прокси-узел** | **Узлы** / **Прокси**, тип «Прокси» (модуль **Прокси-узлы**) | Связь панели с машиной, где уже крутится `proxy.sh` |

Панель **не ставит и не запускает** `proxy.sh`. Сначала сами установите прокси по инструкции AntiZapret ([Настроить прокси-сервер](https://github.com/GubernievS/AntiZapret-VPN#настроить-прокси-сервер)), затем поставьте агент — [установка proxy_agent](proxy-agent.md).

Модуль **Прокси-узлы** по умолчанию **выключен** (**Настройки → Разделы панели**). Пока выключен — создание прокси-узлов и связанные кнопки недоступны. Прокси-узел **нельзя активировать** как VPN (конфиги, синхронизация клиентов к нему не относятся). Когда модуль включён и агент отдаёт mappings, в **NOC Мониторинг** панель восстанавливает домашний IP клиента (или показывает IP прокси с пометкой) — см. [noc-monitoring.md](noc-monitoring.md#подключения-через-прокси-узел).

**Полная схема** (что где лежит, чеклист, DESTINATION, allow-ips, NOC): [proxy-nodes.md](proxy-nodes.md).

## Пошаговые сценарии

### Первый запуск: подключить VPN-сервер

1. Откройте **Узлы**
2. Нажмите **Добавить узел**
3. Укажите имя, адрес сервера и ключ API (их даёт установщик на VPN-сервере)
4. Выберите **способ связи**: HTTP, HTTPS + mTLS или SSH tunnel (SSH доступен, если включён модуль **SSH transport узлов**)
5. Для SSH — заполните SSH-хост/порт/пользователя и приватный ключ в той же форме
6. Сохраните и при необходимости нажмите **Здоровье** (health check)
7. Нажмите **Активировать**, чтобы работать с этим сервером
8. Перейдите в **Клиенты** → **Синхронизировать**, чтобы подтянуть клиентов с диска

### Переключиться на другой сервер

1. В шапке или на странице **Узлы** выберите нужный узел
2. Нажмите **Активировать**
3. Все действия с конфигами теперь относятся **только к нему**

### Подключить прокси-узел (модуль включён)

1. На RU VPS уже выполнен `proxy.sh` (вручную, не из панели)
2. Склонируйте или скопируйте репозиторий на RU (обычно `/opt/AdminPanelAZ`) — [proxy-agent.md](proxy-agent.md#репозиторий-на-ru-vps)
3. Установите `proxy_agent`: `sudo ./install.sh --proxy-only --with-systemd -y` — см. [proxy-agent.md](proxy-agent.md)
4. **Настройки → Разделы панели** → включите **Прокси-узлы** и сохраните
5. На **Узлы** → **Добавить узел** → тип **Прокси**, адрес, порт **9101**, API-ключ из установки
6. **Здоровье** / **Статус**: видно, найдены ли правила прокси и текущий DESTINATION (также на странице **Прокси**)
7. При необходимости измените DESTINATION в карточке (панель правит iptables через агент, не вызывает `proxy.sh`)

### Проверить, жив ли сервер

1. На странице **Узлы** найдите нужный сервер
2. Нажмите **Здоровье** (health check)
3. Статус покажет, доступен ли сервер и агент на нём

## Действия с узлом

| Кнопка | Что делает | Когда использовать |
|--------|------------|-------------------|
| **Активировать** | Делает узел текущим для работы | Перед созданием клиентов или синхронизацией |
| **Здоровье** | Проверяет связь с агентом (health check) | Если что-то не работает |
| **Обновить** | Обновляет node agent на VPN-сервере — см. [Обновление агента на узле](#обновление-агента-на-узле) | После обновления панели |
| **Перезапуск** | Перезапускает node agent без обновления (VPN-службы не затрагиваются) | Агент завис или не отвечает |
| **Способ связи** (выпадающий список) | HTTP, HTTPS + mTLS или SSH tunnel | Для защищённого соединения между панелью и сервером |
| **Ключ** | Генерирует новый API-ключ — см. [API-ключ агента](#api-ключ-агента-где-хранится-и-как-сменить) | После обновления до 2.26.0, при компрометации ключа |
| **Изменить** (у локального узла — **Имя**) | Редактирует имя, адрес, ключ | После смены адреса или ключа |
| **Удалить** | Убирает узел из панели | Сервер больше не нужен (VPN на нём не удаляется) |

У локального узла нет **Способа связи**, **Ключа** и **Удалить**. У прокси-узла — только **Здоровье**, **Способ связи**, **Изменить** и **Удалить**: обновление и ключ proxy_agent меняются на самом RU VPS ([proxy-agent.md](proxy-agent.md)).

Для нескольких выбранных узлов есть панель действий: **Проверить здоровье**, **Rolling update** (обновить агент на выбранных VPN-узлах по очереди, в фоне), **Включить mTLS**, **Удалить**.

### LAN-ноды (приватные IP)

По умолчанию после install нельзя добавить узел с адресом `192.168…` / `10…` (`ALLOW_INTERNAL_NODES=false`). Панель + нода на **одном** хосте и ноды по **публичному** IP этого не требуют.

Для нескольких машин в одной LAN в `backend/.env`:

```env
ALLOW_INTERNAL_NODES=true
```

Затем: `sudo systemctl restart adminpanelaz`.

### mTLS

mTLS включается per-node из UI: **Способ связи** → **HTTPS + mTLS** в карточке узла или **Включить mTLS** для выбранных узлов. Глобальный `NODE_AGENT_MTLS_ENABLED` в `.env` устарел.

### API-ключ агента: где хранится и как сменить

Панель обращается к агенту с API-ключом. Ключ хранится **только** в env-файле агента с правами `600`:

| Агент | Файл (в каталоге репозитория на сервере, обычно `/opt/AdminPanelAZ`) | Переменная |
|-------|------------------|------------|
| node agent (VPN-узел) | `backend/node_agent.env` | `NODE_AGENT_API_KEY` |
| proxy_agent (прокси-узел) | `backend/proxy_agent.env` | `PROXY_AGENT_API_KEY` |

В unit-файлах systemd (`/etc/systemd/system/adminpanelaz-node.service`, `adminpanelaz-proxy.service`) ключа больше нет: эти файлы и `systemctl show` может прочитать любой пользователь сервера. До 2.26.0 ключ лежал там. Старый unit переписывается из шаблона, а ключ из него переносится в env-файл (если там ключа ещё нет) при обновлении агента кнопкой **Обновить**, при старте агента или панели и командой `sudo ./scripts/refresh-systemd-units.sh`. Ключ, уже сменённый ротацией, старым значением из unit'а не затирается.

> **После обновления до 2.26.0 смените ключи агентов** — старый ключ мог быть прочитан из unit-файла. Сначала [обновите агент](#обновление-агента-на-узле) до 1.11.0, затем нажмите **Ключ** в карточке каждого удалённого VPN-узла. Ключ proxy_agent меняется вручную: [proxy-agent.md](proxy-agent.md#смена-api-ключа).

**Ручная смена (VPN-узел).** **Ключ** → **Сгенерировать ключ**. Панель создаёт новый ключ и передаёт его агенту: агент сразу переходит на новый ключ и сам записывает его в `node_agent.env`, панель сохраняет его у себя. Узел должен быть на связи, на сервере ничего править не нужно. У локального узла и прокси-узлов кнопки нет: для прокси панель ротацию отклоняет.

**Автоматическая ротация.** По умолчанию выключена. Включается в `backend/.env` панели: `NODE_API_KEY_ROTATION_DAYS=N` (`0` — выкл.), затем `sudo systemctl restart adminpanelaz`. Раз в `NODE_API_KEY_ROTATION_CHECK_HOURS` часов (по умолчанию 24) панель меняет ключ удалённых VPN-узлов, у которых ключ старше `N` дней. Возраст ключа считается от последней смены — автоматической, ручной или замены ключа в карточке через **Изменить**; у узлов без такой отметки (добавлены до 2.26.0) — от даты добавления. Недоступный узел пропускается до следующей проверки. Прокси-узлы и локальный узел в автоматическую ротацию не входят. Фоновая задача **Ротация API-ключей узлов** в **Настройки → Разделы панели** должна быть включена (по умолчанию включена).

**Переустановка агента.** Повторный `sudo ./install.sh` на узле (в том числе `--reinstall`) оставляет ключ из существующего `node_agent.env` / `proxy_agent.env` — мастер спрашивает «На сервере уже есть NODE_AGENT_API_KEY — оставить его…?». Настройки mTLS тоже сохраняются, если сертификат агента подписан тем же CA, не истёк и подходит к ключу; иначе mTLS выключается с предупреждением — перепривяжите узел в панели. `--reinstall` вызывает `scripts/uninstall.sh --keep-agent-pki`, поэтому `/etc/adminpanelaz/mtls` не удаляется.

### Обновление агента на узле

**Обновить** в карточке VPN-узла открывает окно **Обновление узла**: версия агента (`Agent:`) и насколько рабочая копия на узле отстаёт от удалённой. **Проверить** — проверить заново, **Применить** → **Подтвердить** — обновить. Узел должен быть на связи.

Что делает узел (правила ветки — начиная с агента `1.11.0`; агент `1.8.0` из 2.25.1 при первом обновлении ещё тянет `origin/main`):

1. `git fetch origin` и fast-forward до upstream текущей ветки (ветка `main` без upstream обновляется с `origin/main`). Если история на GitHub переписана, локальных изменений нет и все локальные коммиты уже есть на сервере git, — `git reset --hard` на тот же upstream; неотправленные коммиты не стираются — обновление отказывается: «В локальной ветке есть коммиты, которых нет на сервере git: … — синхронизируйте вручную».
2. Если рабочая копия не на ветке (detached HEAD) или у ветки нет upstream, обновление не выполняется — обновите вручную или привяжите ветку: `git branch -u origin/<ветка>`.
3. Ставит зависимости Python из `backend/requirements.txt` и переписывает unit `adminpanelaz-node` из шаблона (ключ переезжает в `node_agent.env`).
4. Через пару секунд сам перезапускает агент (`systemctl restart adminpanelaz-node`) — отдельно нажимать **Перезапуск** не нужно. Подождите 5–30 секунд и нажмите **Здоровье**.

**Rolling update** делает то же самое для выбранных VPN-узлов по очереди.

**После обновления панели до 2.26.0** обновите агент на всех VPN-узлах до **1.11.0**. До этого функции AZ-WARP 1.5, файлы WARP/RPZ/Lua в редакторе, `WARP_MTU` и OpenVPN Buffer Guard на узле недоступны, а блокировки WireGuard идут по одному клиенту. Если узел показывает агент `1.9.0` или `1.10.0` (промежуточные тестовые сборки 2.26.0), обновите его ещё раз. Затем смените ключ — [см. выше](#api-ключ-агента-где-хранится-и-как-сменить).

### SSH-туннель (модуль `node_ssh_transport`, по умолчанию выкл.)

Подробная инструкция с примерами ключей: **[node-ssh-transport.md](node-ssh-transport.md)**.

1. **Настройки → Разделы панели** → включите **SSH transport узлов**.
2. На узле `node_agent` / `proxy_agent` слушает **127.0.0.1** (порты **9100** / **9101**); в `~/.ssh/authorized_keys` SSH-пользователя добавьте **публичный ключ**, парный приватному ключу из формы панели.
3. При **Добавить узел** выберите transport **SSH** и укажите SSH host/port/user и приватный ключ — либо переключите уже существующий узел в picker карточки. Панель поднимает local forward и ходит к API агента по HTTP через localhost.

## Резервный сервер (HA — высокая доступность)

Если один VPN-сервер недоступен, клиенты могут подключаться к запасному. Для этого настраивают **группу синхронизации**.

### Как это работает простыми словами

1. Есть **основной** сервер — на нём создают и меняют клиентов
2. Есть **запасной** сервер — на него копируют все настройки и клиентов с основного
3. Оба сервера должны быть установлены одинаково
4. В DNS у домена VPN должно быть **два IP-адреса** (основной и запасной) — это настраивается у регистратора домена, не в панели

### Настройка группы синхронизации

1. На странице **Узлы** найдите блок **HA · синхронизация** (виден, когда в панели не меньше двух узлов)
2. **Создать группу**: укажите основной узел, запасные и домены (OpenVPN и при необходимости отдельный для WireGuard/AmneziaWG)
3. Нажмите **Синхронизировать** — полный цикл: домен → полная копия с основного на запасной (Push full) → проверка
4. **Проверить** — отдельная проверка, что оба сервера совпадают (без изменений)
5. Только после успешной проверки добавляйте второй IP в DNS

> **Синхронизировать** (полная копия, Push full) на запасном сервере **перезаписывает** все данные. Не нажимайте без понимания. Подробности: [NodeSync.md](NodeSync.md).

## Частые вопросы

**Клиенты не появляются в панели после добавления узла**  
Выберите узел как активный и на странице **Клиенты** нажмите **Синхронизировать**.

**Узел показывает «офлайн»**  
Проверьте, работает ли VPN-сервер, открыт ли порт, верный ли API-ключ (на сервере — в `backend/node_agent.env`). Нажмите **Здоровье**.

**Узел стал «офлайн» после перезапуска AntiZapret, хотя сервер работает**  
Проверьте, не указан ли в адресе узла IP из `ANTIZAPRET_OUT_IP` / `VPN_OUT_IP` в `setup`. Свежий AntiZapret-VPN блокирует весь входящий трафик на эти адреса (Out IP protection) — укажите основной IP сервера. Подробнее: [antizapret-config.md](antizapret-config.md#out-ip-protection).

**Редактор файлов просит обновить node agent**  
Файлы WARP, RPZ и DNS-политик (`custom.lua`) поддерживаются начиная с node agent 1.11.0. Обновите node agent на узле кнопкой **Обновить** — см. [Обновление агента на узле](#обновление-агента-на-узле) и [edit-files.md](edit-files.md#узлы-со-старым-node-agent).

**Можно ли один профиль на двух серверах?**  
В обычном режиме — нет, это разные записи. В режиме HA клиенты синхронизируются между серверами группы, но это отдельная настройка.

**Прокси-узел и «адреса подключения» — это одно и то же?**  
Нет. Адреса подключения — список remote для `.ovpn` на VPN-узле. Прокси-узел — отдельная машина с `proxy.sh` и `proxy_agent`.

**Почему нет кнопки «Установить proxy.sh»?**  
Панель сознательно не ставит прокси AntiZapret. Только мониторинг и смена DESTINATION через агент. Полная инструкция: [proxy-nodes.md](proxy-nodes.md).

---

## Будьте осторожны

- **Синхронизировать** в HA-группе (Push full) уничтожает текущие данные на запасном сервере и заменяет их копией с основного
- **Удалить узел** убирает его только из панели — VPN на самом сервере продолжит работать
- **Rolling update** (массовое обновление) затрагивает все выбранные серверы — делайте в спокойное время
