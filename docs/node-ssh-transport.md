# SSH-транспорт узлов

Как подключить VPN- или прокси-узел к панели через **SSH-туннель**, когда порт агента (9100 / 9101) нельзя или не хочется открывать в интернет.

Связанные разделы: [Узлы](uzly.md) · [Модули](nastrojki/moduli.md)

---

## Зачем это нужно

Обычная схема: панель ходит к `node_agent` по HTTP/HTTPS на публичный IP:порт.

**SSH-транспорт:** панель сама открывает SSH к серверу и делает *local forward* до агента на `127.0.0.1`. Снаружи достаточно SSH (обычно порт 22); агент может слушать только localhost.

```
Панель (controller)
    │  SSH (ключ)
    ▼
VPN / RU сервер
    │  туннель → 127.0.0.1:9100
    ▼
node_agent (или proxy_agent :9101)
```

---

## Что подготовить на сервере узла

1. Установлен и запущен агент:
   - VPN: `adminpanelaz-node` (порт **9100**)
   - прокси: `adminpanelaz-proxy` (порт **9101**)
2. Агент слушает **127.0.0.1** (рекомендуется для SSH).
3. Есть SSH-доступ (пользователь + порт).
4. В `~/.ssh/authorized_keys` этого пользователя добавлен **публичный** ключ, парный **приватному**, который вы вставите в панель.

Проверка на узле:

```bash
sudo systemctl status adminpanelaz-node   # или adminpanelaz-proxy
ss -ltnp | grep 9100                     # или 9101
```

---

## Включение в панели

1. **Настройки → Модули** → включите **SSH transport узлов** (`node_ssh_transport`).
2. Откройте **Узлы**.

Дальше один из вариантов:

### А. Уже есть узел (HTTP / mTLS)

1. В строке узла в колонке **Транспорт** выберите **SSH tunnel**.
2. Откроется диалог **«Переключить на SSH?»**.
3. Заполните поля (ниже) → **Сохранить SSH**.
4. Нажмите **Здоровье** — статус должен стать «В сети».

### Б. Новый узел сразу по SSH

1. **Добавить узел** → **Способ связи: SSH tunnel**.
2. Укажите имя, хост (для отображения), порт агента, API-ключ и блок SSH-полей.
3. **Добавить**.

---

## Поля диалога «Переключить на SSH?»

| Поле | Что указать |
|------|-------------|
| **SSH-хост** | IP или домен, куда панель откроет SSH (часто совпадает с адресом узла) |
| **SSH-порт** | Обычно `22` |
| **SSH-пользователь** | Например `root` или отдельный пользователь с доступом к агенту |
| **Приватный ключ** | Содержимое приватного ключа OpenSSH (`BEGIN OPENSSH PRIVATE KEY` / `BEGIN RSA PRIVATE KEY`). **Обязателен** при первом включении SSH; при смене ключа вставьте новый, иначе оставьте пустым |
| **Passphrase** | Только если ключ защищён паролем; иначе пусто |

Внутренний адрес агента по умолчанию: **127.0.0.1** и текущий порт узла (9100 / 9101). Менять их в UI обычно не нужно.

## Как сгенерировать ключ (пример)

На машине, с которой удобно работать (или прямо на панели):

```bash
ssh-keygen -t ed25519 -f ./panel-node-ssh -N ""
```

- `panel-node-ssh` — **приватный** ключ → вставить в форму панели  
- `panel-node-ssh.pub` — **публичный** → одна строка в `authorized_keys` на узле

```bash
# на VPN/прокси сервере
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'содержимое panel-node-ssh.pub' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Проверка с панели (или любой машины с этим ключом):

```bash
ssh -i panel-node-ssh -p 22 root@IP_УЗЛА 'echo ok'
```

## Безопасность (кратко)

- Приватный ключ хранится в БД панели **в зашифрованном виде**; в API и UI он обратно не отдаётся.
- При **первом** успешном подключении панель запоминает отпечаток SSH host key (TOFU). Если сервер сменит ключ — связь оборвётся, пока не обновите/сбросите pin (смена SSH-хоста сбрасывает сохранённый ключ).
- Не открывайте порт агента в интернет, если используете только SSH-транспорт.

## Частые проблемы

| Симптом | Что проверить |
|---------|----------------|
| Узел offline после переключения | SSH с панели на хост/порт/user; `authorized_keys`; агент `active` и слушает `127.0.0.1` |
| Ошибка про модуль / 403 | Включён ли **SSH transport узлов** в Модулях |
| Host key / MITM | Сменился ключ сервера после первого подключения — сбросьте pin (например сменой SSH-хоста и обратно) или перенастройте SSH |
| Агент недоступен через туннель | Порт агента в карточке узла совпадает с реальным; firewall на localhost не режет |

Логи панели: `journalctl -u adminpanelaz -f` (ищите `node_ssh`).

## Вернуться на HTTP или mTLS

Перед каждым переключением панель **проверяет**, доступен ли агент в целевом режиме (`POST …/transport/preflight`):

1. **SSH → HTTP** — probe HTTP на публичный `host:port`. Если агент слушает только `127.0.0.1` или ещё на mTLS — переход будет отклонён.
2. **HTTP → HTTPS + mTLS** — агент должен отвечать по HTTP (provision идёт напрямую). Прямой **SSH → mTLS** запрещён.
3. **→ SSH** — поднимается временный туннель и проверяется HTTP к агенту на `127.0.0.1`. Если агент на mTLS — сначала переведите его на обычный HTTP.
