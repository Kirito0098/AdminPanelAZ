# OpenVPN Buffer Guard — адекватные дефолты и рекомендации по режимам

**Дата:** 2026-09-19  
**Статус:** approved (дизайн согласован в чате)  
**Ветка:** `feat/openvpn-buffer-guard`  
**Базовый spec:** [2026-09-17-openvpn-buffer-guard-design.md](./2026-09-17-openvpn-buffer-guard-design.md)  
**Контекст:** дефолт `threshold_count=500` / `60 с` и режим `kill_restart` рассчитаны на уже тяжёлый шторм. На типичном VPS (1GB RAM / 1 CPU) фон ENOBUFS ~до 15/мин; пользователи панели часто не понимают порог и оставляют заводские значения — Guard «молчит» до катастрофы. Нужны ранние предупреждения по умолчанию и понятные рекомендации при смене режима.

## Цель

1. Новый узел / отсутствующая строка настроек получает **безопасный для новичка** дефолт: только уведомления + ранний порог.
2. В UI для каждого режима видна **рекомендация порога** и кнопка **«Применить рекомендацию»** (без автоподстановки при смене режима).
3. Узлы, где до сих пор лежит **заводской** `500` / `60 с`, однократно получают порог по текущему режиму.

## Не цели

- Автосмена порога при смене режима в селекте.
- Профили «мягкий / обычный / жёсткий» вместо числа.
- Runtime-подстройка под фактические RAM/CPU.
- Изменение логики детекта, worker, kill/restart/ban.
- Миграция любых вручную изменённых порогов (≠ 500).

## Решения

| Вопрос | Выбор |
|--------|--------|
| Подход | Константы + UI-подсказка + кнопка (вариант A) |
| При смене режима | Только подсказка; порог не трогать |
| Дефолтный режим | **`notify`** (было `kill_restart`) |
| Дефолтный порог | **`40`** за **`60` с** |
| Источник правды для рекомендаций | Backend-константы; `GET settings` отдаёт `recommended_threshold` |
| Старые строки `500`/`60` | Одноразовая миграция → порог из таблицы по **текущему** `mode` |

## Рекомендуемые пороги (окно 60 с)

Ориентир: фон ≤15 ENOBUFS/мин на 1GB/1CPU; реальный каскад 17.09 — порядки тысяч/мин.

| Режим | `recommended_threshold` | Смысл |
|--------|------------------------:|--------|
| `notify` | **40** | Раннее предупреждение, выше фона |
| `kill` | **80** | Запас от ложного кика |
| `kill_restart` | **120** | Запас перед restart юнита |
| `kill_restart_temp_ban` | **150** | Самый осторожный перед баном |

`window_seconds` по умолчанию остаётся **60**. Остальные поля (`escalate_after_seconds=30`, `cooldown_minutes=15`, `temp_ban_minutes=60`, `watch_units`) — без изменений.

## DEFAULT_SETTINGS (замена)

| Поле | Было | Станет |
|------|------|--------|
| `enabled` | `false` | `false` |
| `mode` | `kill_restart` | **`notify`** |
| `threshold_count` | `500` | **`40`** |
| `window_seconds` | `60` | `60` |

## Миграция существующих строк

При старте панели / DB migration helper:

```
IF threshold_count == 500 AND window_seconds == 60:
  threshold_count = recommended_threshold(mode)
```

- Срабатывает один раз на такие строки (после изменения порог уже ≠ 500).
- Любой порог ≠ 500 считается ручным и **не** меняется.
- `mode` и `enabled` миграция не меняет.

## API

`GET /openvpn-buffer-guard/settings?node_id=`:

- Существующие поля без breaking rename.
- Добавить **`recommended_threshold: int`** — значение для **текущего** `mode` строки (после нормализации mode).
- Опционально (не обязательно в v1 этого diff): `recommended_by_mode: { notify: 40, ... }` — если удобнее фронту без дублирования; минимум — одно поле `recommended_threshold`.

`PUT` — без автоподстановки; клиент шлёт явный `threshold_count`.

## UI (`OpenVpnBufferGuardCard`)

1. Под полем порога: текст вида  
   «Для режима „…“ рекомендуем **N** за 60 с (типичный VPS 1GB/1CPU)».
2. Кнопка **«Применить рекомендацию»**:
   - пишет в draft `threshold_count = recommended_threshold` (из ответа API или пересчёта при смене mode на клиенте из того же источника);
   - Save по-прежнему отдельный;
   - disabled, если draft уже равен рекомендации.
3. Смена `mode` в select **не** меняет `threshold_count`.
4. Обновить `MODE_HINTS`: одна короткая строка с рекомендуемым порогом для режима.
5. В warning/intro карточки уточнить: по умолчанию режим — только уведомления; для автокика смените режим и при желании нажмите «Применить рекомендацию».

## Тесты

1. `get_settings` / create defaults → `mode=notify`, `threshold_count=40`.
2. Миграция: строка `500`+`60`+`kill_restart` → `120`; `499`+`60` не трогается.
3. `recommended_threshold(mode)` для всех четырёх режимов.
4. GET settings включает `recommended_threshold`, согласованный с mode.
5. (По возможности) UI/unit: кнопка выставляет draft threshold в N.

## Критерии приёмки

- Новый узел без строки настроек: UI показывает `notify`, порог `40`, рекомендация `40`.
- Смена режима на `kill_restart` → подсказка `120`, порог в поле остаётся прежним до кнопки/Save.
- «Применить рекомендацию» + Save сохраняет рекомендованный порог.
- Строка с заводским `500/60` после миграции имеет порог из таблицы; кастомный порог не изменён.
- Docs и CHANGELOG отражают новые числа.
