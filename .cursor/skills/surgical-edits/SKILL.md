# Surgical edits: одна реализация вместо двух

Задача «доработать» почти никогда не значит «добавить рядом». Синдром, который здесь лечится, —
**additive bias**: модель боится сломать работающее, поэтому оставляет старое и приписывает новое.
Итог: две кнопки с одним смыслом, два эндпоинта с одной логикой, два обработчика на одно событие,
и оба живые.

**Правило:** на одну задачу — одна реализация. Существующая переписывается, заменённая удаляется
в том же диффе.

## Куда писать: ладдер

1. **Найди существующее место.** `rg` по имени экрана/фичи, `search_graph` / `trace_path` по символу,
   поиск маршрута, эндпоинта, обработчика. Пока не нашёл — не пишешь.
2. **Перепиши его.** Тот же компонент, та же функция, тот же обработчик, тот же маршрут.
3. **Удали заменённое.** Старый обработчик, старый путь данных, осиротевший пропс, ставший
   ненужным `import`, мёртвую ветку, мёртвый экспорт, закомментированный «на всякий случай» код.
4. **Обнови всех вызывающих сразу.** `rg` по старому имени → правка во всех файлах, включая тесты.
5. **Параллельную реализацию добавляй только если** старое поведение обязано остаться доступным:
   внешний потребитель не может обновиться, нужен флаг миграции, A/B. Тогда назови это в ответе,
   укажи условие удаления и покрой оба пути.

## Симптомы, по которым ловишь себя

- добавляешь файл `X2`, `newX`, `v2`, `Enhanced`, `Simple` рядом с `X`;
- вторая кнопка/пункт меню/вкладка с тем же смыслом;
- второй `useEffect`, который пишет то же состояние, что первый;
- второй эндпоинт `/api/x/new` поверх `/api/x`;
- второй форматтер, вторая fetch-обёртка, второй набор констант;
- оставил старую ветку «для совместимости», хотя никто, кроме этой панели, её не вызывает;
- в диффе появилось больше, чем изменилось.

## Инварианты — до и после

Перед правкой выпиши, что существующий код гарантирует (порядок вызовов, кэш, права, ретраи,
момент записи в storage, формат ответа API). После правки пройди по списку и подтверди каждый.
Не можешь подтвердить — не правка, а новая фича: вернись к плану в чате.

## Рефакторинг ≠ фича

Не смешивай в одном диффе переписывание старого и новое поведение. Сначала приводишь место
в порядок (поведение не меняется), прогоняешь проверки, потом добавляешь поведение. Иначе при
поломке не понять, что именно сломалось.

## Комментарии

Не пересказывай код и не оставляй следы задачи: `// добавлено для X`, `// старое поведение`,
`// TODO: убрать после релиза`. История — в git.

## Definition of done

1. `rg` по старому символу/маршруту/классу → **0 вхождений** (кроме git-истории).
2. В диффе нет новых файлов рядом с заменёнными.
3. Прогоны по затронутой части выполнены в этой сессии, вывод в чате — без «должно работать».
4. `git diff` читается построчно: каждая строка трассируется к задаче; добавленных «на будущее»
   строк нет.

## Когда правило не про эту задачу

Новая фича с нуля, которой в кодовой базе нет вообще. Тогда сначала план в чате и «да»
пользователя — см. `AGENTS.md`, раздел «Мелочь ≠ фича». Этот скилл про **доработку**, а не
про запрет нового кода.
